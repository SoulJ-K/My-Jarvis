## 문서 작성·읽기 규칙

- **기록 범위:** 실행 구조, 기능 사이의 책임, 저장·복구 경계와 검증 방법을 기록한다. 제품 범위·완료 기준은 PRD, 행동 표현은 Character & Growth Design, 선택 이유·변경 관계는 Decision Log와 ADR-001, 날짜별 실행 결과·실패·재검사는 개발 기록에 맡긴다.
- **갱신 시점:** 승인된 기술 선택이나 기능 연결·저장·복구 구조가 달라질 때 해당 절을 제자리에서 갱신한다. 최근 변경 요약은 새 변경 때 교체하고, 이력은 기존 결정·개발 기록에 남긴다. 검토용 제안은 승인된 구조와 분리한다.
- **상태 구분:** 현재 연결 구조, 합의된 기준, 잠정 구현값, 미승인 제안을 구분한다. 설계 설명·파일 존재는 동작 검증의 증거가 아니며 자동 검사·사용자 조작·자연 경과 확인은 각각의 범위로 읽는다.
- **근거 보존:** 변경한 구조에는 관련 결정 번호와 실제 파일·검사 기록을 연결한다. 과거 결과는 날짜·조건·실패·미검증 한계를 보존하고 후속 결과로 소급 덮어쓰지 않는다. 다른 문서로 옮길 내용은 보존 여부를 확인한 뒤 중복을 줄인다.
- **참조 유지:** 기존 단계 번호와 외부에서 연결하는 문서 내부 위치를 유지한다. 근거 문서가 함께 정리되면 통합 담당이 참조와 상태를 재대조한다. 문서 정리 자체는 앱 검사 완료를 뜻하지 않는다.
- **원본과 사본:** 최종 원본은 `/Users/rkfrk/Desktop/My Jarvis`의 프로젝트 문서다. GitHub는 승인된 변경 기록을 확인하는 곳이고 Notion은 읽고 확인하는 사본이다. 수정은 프로젝트 문서에서 하고 검토 후 사본에 반영한다. 워크트리 수정본은 통합 담당의 검수 후 원본에 반영한다.
- **표시 방식:** 제목·이 규칙·최근 변경 요약·현재 확인할 사항은 항상 보이게 둔다. 주제별 본문은 중첩 없이 접되 현재 유효한 구조와 기준을 담고 있음을 유지한다. Notion으로 가져올 때 접기·펼침 상태의 보존은 별도 변환·화면 확인 전에는 보장하지 않는다.

## 문서 기준과 상태 읽는 법

기준 문서는 [README](../README.md), [PRD](Jarvis_Pet_PRD.md), [Decision Log](Jarvis_Pet_Decision_Log.md), [Character & Growth Design](Jarvis_Pet_Character_and_Growth_Design.md)이다. 실제 날짜별 구현·통합·검사와 발견한 문제는 [개발 기록](Jarvis_Pet_Development_Log.md)에 둔다. 기능 범위와 완료 판단은 PRD 17~18장, 행동 표현은 Character & Growth Design, 결정 이유와 변경 이력은 Decision Log를 따른다. 이 설계안이 기존 요구사항을 바꾸지는 않는다.

| 상태 | 이 문서에서의 뜻 |
|---|---|
| 실제 구현 완료 | 코드를 작성하고 명시한 범위에서 동작까지 검증한 상태. **검증한 범위만 개발 기록에 명시한다. 코드 작성만으로 사용자 경험 완료를 뜻하지 않는다.** |
| 설계만 완료 | 설명이나 계획을 문서로 정리한 상태. 사용자 승인이나 실제 동작 검증을 뜻하지 않는다. 본 문서의 미승인 제안도 이 상태와 구분한다. |
| 구조만 고려 | 나중의 연결을 막지 않도록 책임과 데이터 경계만 정리한 상태. 동작 코드·화면을 미리 만들 필요는 없다. |
| 미래 확장 | v0.1에서 구현하지 않는 범위. 별도 결정 후 검토한다. |
| 추천·미정 | 아직 사용자와 결정하거나 실기기에서 검증해야 하는 기술 선택 또는 세부값. |

v0.1은 **알 → 부화 → 아기 생활**까지다. 어린이·청소년·성체 전환, 복잡한 작업 수행, 여러 AI 연결은 현재 구현하지 않는다. 아기 경험 기록은 필수이고, 이를 성격과 이후 성장에 반영하는 구체 규칙은 후속 설계다. LLM은 문장을 생성·해석하는 언어 모델을 뜻하며, **Pet Brain의 기본 생활에는 외부·로컬 LLM 모두 필요하지 않아야 한다.**

이후 중요한 기술 선택·범위 변경·구조 변경·구현 단계 완료를 이 문서와 관련 기준 문서에 반영한다. 작은 코드 변경마다 문서를 늘리거나 `final`, `new`, 새 버전 파일을 만들지 않는다. 새 문서가 필요하면 이름·이유·담을 내용을 먼저 제안한다.

병렬로 진행할 수 있는 작업은 역할과 변경 대상 파일을 먼저 제안하고 사용자 확인 후 에이전트에 나눠 맡긴다. 담당 파일을 분리한다. **개별 워크트리 수정·검사 → 결과 인계 → 별도 통합 워크트리에서 순차 통합·연결 검사 → 통합 담당의 원본 반영·확인 → 사용자 실사용 확인**을 기본 순서로 한다. 개별 담당자는 원본에 직접 반영하지 않는다. 인계 항목·검사 책임·완료 상태의 기준은 [AGENTS.md 13.1~15절](../AGENTS.md), 결정 이유는 [Decision Log D-056](Jarvis_Pet_Decision_Log.md#d-056-개별-검사와-통합-검사를-거쳐-통합-담당이-원본에-반영한다)을 따른다. 이 절차의 문서화가 현재 작업들의 통합·검사 완료를 뜻하지 않는다.

## 1. 현재 기술 구성과 미도입 후보

기술 스택은 **앱을 만들 때 함께 사용하는 도구들의 조합**이다. Jarvis Pet에는 데스크톱 창, 화면 표현, 펫 규칙, 저장, 검사를 맡을 도구가 필요하다.

### 1.1 데스크톱 앱 후보 비교

| 후보 | 무엇인가 | Jarvis Pet에 맞는 점 | 부담·차이 | 현재 판단 |
|---|---|---|---|---|
| Electron | 웹 화면 기술을 데스크톱 창 안에서 실행하는 도구 | 창·트레이·알림을 연결하고 화면과 핵심 로직을 TypeScript로 작성할 수 있다. | 브라우저 실행 환경을 포함하므로 앱 크기와 상시 메모리 사용을 측정해야 한다. | **사용자가 첫 검증 경로로 선택. 최종 채택은 검증 후.** |
| Tauri | 운영체제의 웹 화면 엔진과 Rust 기반 앱 관리 부분을 결합하는 도구 | 설치 크기와 자원 사용을 줄일 대안으로 검토할 가치가 있다. | Rust와 화면 기술을 함께 다루며, 운영체제별 창 제약을 확인해야 한다. | Electron 검증 결과에 따라 재검토 가능한 후보 |
| Electron + Java/Spring Boot | 화면과 별도로 Java 프로그램을 실행해 핵심 처리를 맡기는 구성 | 사용자의 기존 Java/Spring 경험을 활용하기 좋다. | 두 프로그램의 실행·종료·통신·묶음을 관리해야 한다. | v0.1에서는 추가하지 않는 안 추천 |

Electron은 앱 관리 영역과 화면 영역을 나누고 창·메뉴·트레이 같은 데스크톱 기능을 제공한다. 이 프로젝트에서는 먼저 창 조작 가능성을 확인하고, 통과하면 한 언어로 작은 제품을 완성하는 방향을 추천한다. [Electron 실행 구조](https://www.electronjs.org/docs/latest/tutorial/process-model)

Tauri의 macOS 투명 창은 공식 문서상 `macOSPrivateApi` 설정이 필요한 제약이 있다. 비공개 운영체제 기능 사용으로 Mac App Store 등록에 제한이 생길 수 있으므로, 경량성만 보고 선택하지 않는다. 현재 개인용 v0.1에 앱스토어 배포를 추가한다는 뜻은 아니다. [Tauri 창 설정](https://v2.tauri.app/reference/config/#transparent)

첫 검증 환경은 macOS로 정했다. **Windows 지원 목표는 유지하지만, macOS 검증 성공을 Windows 검증 성공으로 표현하지 않는다.** 선택 이유와 제한은 Decision Log D-035를 따른다.

Java 서버, 게임 엔진, 일반 대화용 로컬 모델은 기본 구성에 추가하지 않는다. **모듈은 관련 기능을 묶은 코드 단위**이며 별도 서버나 프로그램을 뜻하지 않는다. 후보 목록 자체는 설치·구현 승인이 아니다.

### 1.3 개발 도구 버전과 설치 기록

프로젝트별로 도구 버전을 지정해 다른 프로젝트의 변경과 분리한다. `package.json`과 연관 패키지 버전을 기록한 `package-lock.json`을 함께 관리하고, 내려받은 `node_modules/`는 제외한다. Node.js와 npm의 기존 설치를 사용한 결정은 D-037을 따른다.

2026-09-26 설치 당시 환경·버전 명령·취약점 조회 결과와 한계는 [개발 기록의 개발 도구 준비](Jarvis_Pet_Development_Log.md#개발-도구-준비--d-037)에 보존되어 있다. ## 2. 전체 아키텍처

아키텍처는 **각 부분이 무엇을 책임지고 서로 어떻게 연결되는지 정한 설계**다. 화면이나 AI가 바뀌어도 같은 펫의 기억과 생활을 유지하기 위해 필요하다.

### 2.1 전체 흐름과 실행 위치

```text
사용자
  ↓ 클릭·드래그·짧은 문장
화면: 펫 / 입력창 / 알림 표시
  ↓ 제한된 요청 창구
앱 진행 관리자: 입력 검증 / 처리 순서 / 저장 조율
  ├─ Pet Brain: 생애·생활·감정·관계·행동·경험 정책
  ├─ 기본 비서: 요청 해석·알람·타이머·리마인더
  ├─ 저장 담당 → SQLite (D-039 선택)
  ├─ 운영체제 창·알림 담당
  └─ [구조만 고려] AIService
         ├─ AIProvider: 대화·추론 연결
         └─ 작업 도구 연결: Codex 등, 권한 확인 후 사용
```

**프로세스는 프로그램이 분리되어 실행되는 단위**다. Electron에서는 앱을 관리하는 메인 프로세스와 화면을 그리는 렌더러 프로세스를 구분한다.

| 영역 | 담당 | 맡기지 않는 일 |
|---|---|---|
| 메인 프로세스 | Pet Brain, 시간 관리, 저장, 창 관리, 요청 검증 | 매 장면의 그림 계산 |
| 렌더러 | 펫·구슬·먹이 그리기, 입력창과 알림 표시 | 데이터베이스 직접 수정, 임의 파일·프로그램 실행 |
| Preload | 화면에 필요한 요청만 제공하는 연결 창구 | 운영체제 기능 전체를 화면에 공개 |

**IPC는 분리된 실행 영역끼리 메시지를 전달하는 방식**이다. 접수창구에 신청서를 전달하는 것과 비슷하다. 화면이 “타이머 등록”을 요청하면 메인 영역이 검사하고 저장한 결과를 반환한다. 화면이 직접 저장 파일을 고치지 않는다.

Pet Brain의 현재 원본은 메인 영역에서 관리하고 중요한 변경을 저장한다. 화면은 사용자에게 표현할 정보만 받는다. 화면이 닫히거나 다시 만들어져도 펫과 예약을 복원할 수 있게 하기 위해서다. 요청에는 식별자를 붙여 같은 등록 버튼이 중복 처리되는 일을 막는 안을 추천한다. 제한된 연결 구조는 [Electron 실행 구조](https://www.electronjs.org/docs/latest/tutorial/process-model)를 참고한다.

초기에는 가벼운 규칙과 작은 저장을 한 앱 안에서 처리한다. 느린 연산이나 대량 저장이 실제로 발견되면 별도 작업 영역을 검토하되, 지금부터 분산 서버나 복잡한 메시지 시스템을 만들지 않는다.

### 2.2 Pet Brain의 책임과 내부 모듈

Pet Brain은 **현재 상태와 발생한 일을 받아 다음 상태와 반응을 결정하는 로컬 규칙**이다.

예: 졸린 아기에게 먹이를 준다 → 배고픔을 완화한다 → 짧게 만족한다 → 식사 경험을 기록한다 → 원래 졸렸으므로 쉬거나 잠든다.

| 모듈 | 책임 | v0.1 범위 |
|---|---|---|
| 생애 흐름 | 알·부화·첫 교감·이름 짓기 진행 | 알 → 아기 한 번 |
| 생활 상태 | 배고픔·졸림·수면과 시간 경과 | 두 가지 필요와 자연스러운 복귀 |
| 감정 | 기쁨·불편함·호기심의 발생과 진정 | 최소 감정 표현 |
| 관계 | 익숙함·신뢰·잠시 거리두기와 회복 | 수치 비노출, 행동 차이 |
| 행동 선택 | 현재 가능한 행동 중 하나 선택 | 쉬기·짧은 이동·커서 쫓기·구슬 놀이 |
| 기억·경험 정책 | 무엇을 기억으로 남길지 판단 | 이름·기질·상태·관계, 아기 돌봄 경험 |

Pet Brain은 파일에 직접 쓰거나 그림을 재생하거나 외부 AI를 기다리지 않는다. 다음 상태, 남길 경험, 표현할 행동을 반환하고 앱 진행 관리자가 저장과 화면 전달을 조율한다. 처리는 순서대로 하여 먹이 주기와 타이머 갱신처럼 동시에 들어온 요청이 상태를 덮어쓰지 않게 한다.

행동 선택은 현재 상태와 사건의 우선순위 규칙으로 시작한다. 복잡한 계획 시스템이나 성격 학습 엔진은 만들지 않는다. **펫이 졸리거나 잠시 거리를 두더라도 기본 알림의 정확성을 낮추지 않는다.** 알림 전달은 별도 비서 담당이 책임진다.

### 2.3 알 / 부화 / 아기 상태 흐름

**상태 머신은 현재 단계와 다음 단계로 넘어갈 조건을 적은 규칙표**다. 신호등처럼 허용된 순서로 진행한다. 구슬보다 아기가 먼저 나오거나 재시작 때문에 이름 짓기를 건너뛰지 않도록 사용한다.

```text
알 생활
  ↓ 시간 기본 조건 + 돌봄의 제한적 영향
부화 준비 완료, 사용자 기다림
  ↓ 사용자가 볼 수 있는 상황에서 시작
부화 전조 → 알에 금 → 감정구슬 등장 → 껍질 갈라짐
  ↓
아기 등장·주변 살피기 → 첫 교감 → 이름 짓기
  ↓
아기 생활: 쉬기 / 짧은 이동 / 식사 / 수면 / 두 가지 놀이
```

성장 단계와 연출 진행 지점을 따로 저장한다. 알부터 사용한 `petId`라는 식별자는 부화 후에도 같다. 구슬 역시 새로 뽑는 장식이 아니라 같은 아기의 물건으로 유지한다.

- 부화 준비는 돌봄 없이 24시간이 지나면 가능하다. 1시간 이상 간격을 둔 클릭·쓰다듬기마다 30분씩, 최대 6시간만 앞당긴다. 돌봄을 필수 통과 조건으로 만들지 않는다.
- 사용자가 없을 때 조건이 충족되면 준비 상태로 기다린다. 잠금 해제·최근 입력은 사용자가 실제로 보는지의 보조 신호일 뿐이다.
- 준비된 알의 첫 장면은 사용자가 메뉴의 **부화 함께 보기**를 선택할 때 시작한다. 준비 판단만으로 장면을 진행하지 않는다.
- 완료한 연출 지점을 저장한다. 중간 종료 시 마지막 완료 지점 이후를 다시 보여주며 아기·이름·구슬을 중복 생성하지 않는다.
- 절전·잠금·화면 사라짐 때 중요한 연출을 보류하는 안을 추천한다. 사용자가 못 본 구간을 완료 처리하지 않도록 재개 규칙을 검증한다.
- 이름을 저장하기 전에는 이름 짓기 단계가 끝난 것으로 처리하지 않는다. 첫 이름은 앞뒤 공백을 정리한 1~20자다.
- 아기 이후 성장 조건이나 어린이 연출은 v0.1에 만들지 않는다.

### 2.4 펫 렌더링과 애니메이션

**렌더링은 상태와 그림 자료를 실제 화면으로 그리는 작업**이다. Pet Brain이 “기쁨 표현”을 결정하면 화면이 가능한 몸짓으로 보여준다. 규칙과 그림을 나누면 같은 펫의 표현을 바꿔도 관계 계산을 고치지 않아도 된다.

**스프라이트 시트는 여러 동작 그림을 한 이미지에 모은 것**이다. 작은 만화책을 넘기듯 순서대로 보여준다. 이미지와 함께 동작별 위치·속도·반복 여부를 적은 설명 파일을 두는 안을 추천한다.

- 펫 본체·감정구슬·먹이를 나눠 그린다. 손이나 꼬리가 없는 외형에 해당 동작을 강요하지 않는다.
- 구슬은 놀이·감정 표현에 필요한 때 나타난다. 배고픔·졸림 표시기로 사용하지 않는다. 전체 색상표는 미정이다.
- 그림을 자주 바꾸는 주기와 생활 상태 계산·저장 주기를 분리한다. 화면 한 장을 그릴 때마다 저장하지 않는다.
- 작은 투명 펫 창과 입력 시 열리는 대화 창을 나누는 안을 추천한다. 평소 다른 앱의 키보드 입력을 빼앗지 않게 한다.
- 화면에서 클릭을 받을 부분을 펫·먹이 등 필요한 영역으로 제한한다. 빈 공간을 클릭하면 뒤의 앱으로 전달되어야 한다.
- 모니터 분리·화면 배율 변경 시 펫이 화면 밖에 남지 않도록 현재 화면의 안전한 영역으로 되돌린다.

투명 창의 빈 공간이 자동으로 클릭을 통과하는 것은 아니다. 펫 클릭·먹이 드래그·뒤 앱 클릭이 함께 성립하는지를 첫 시제품에서 확인해야 한다. [Electron 투명 창 제약](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles#limitations)

### 2.5 입력창과 간단한 대화 UX

**UX는 사용자가 기능을 찾고 사용하고 결과를 이해하는 전체 경험**이다. 아기는 짧게 말하되 비서 기능의 결과는 정확히 알 수 있어야 한다.

자연어 처리는 **문장에서 사용자가 원하는 일을 해석하는 과정**이다. 현재 v0.1의 입력은 짧은 한국어 표현을 정해진 규칙으로 해석한다(D-055·D-058). 모든 문장을 알아듣는 챗봇을 만들지 않는다.

```text
입력창 열기 → 입력 → 요청 해석
  ├─ 정보 부족: 한 가지를 되묻고 기다림
  ├─ 지원 요청: 검증 → 처리·저장 → 결과 표시
  └─ 모르는 요청: 실행하지 않고 가능한 요청 안내
결과 읽을 시간 제공 → 자동 닫기
```

| 예시 | 제안하는 반응 |
|---|---|
| “안녕”, “잘했어” | 현재 상태와 관계에 맞는 짧은 몸짓; 요청 결과는 입력창에 표시 |
| “5분 타이머” | 로컬 등록 후 종료 예정 시각을 정확히 표시 |
| “알람 맞춰줘” | 입력창에서 필요한 시각 정보를 요청 |
| “3시에 알려줘” | 날짜·오전/오후가 불명확하면 추측 실행하지 않고 확인 |
| “이따 알려줘” | 구체 시간을 되묻기 |
| 지원하지 않는 복잡한 요청 | 이해한 척 실행하지 않고 지원 범위 안내 |

알은 말하지 않는다. 알 상태의 입력 안내·등록 결과는 앱 안내로 표현하고 알은 움직임만 보인다. 아기의 상태·감정은 표정과 움직임으로 표현하며 곁에 자동 문구를 띄우지 않는다. 수면 중에는 머리 옆의 작은 `zZ`만 보인다. 사용자가 연 입력창의 업무 결과와 필요한 알림 안내는 유지한다(D-058).

입력 중·한글 조합 중·되묻기 중·오류 확인 중에는 자동으로 닫지 않는다. Enter 전송과 Esc 닫기를 제공하며, 한글 글자를 완성하는 Enter가 전송으로 처리되지 않게 한다. 실제 검사 범위와 Escape 검사 보완 이력은 개발 기록을 따른다. 화면을 열 때만 입력 초점을 받고 평소 다른 앱의 입력을 방해하지 않는다. 되묻기를 취소하면 예약을 만들지 않는다.

아기 클릭은 입력창 열기로 연결한다. 알의 짧은 반응·쓰다듬기·이동은 D-042의 조작 경계로 구분하고, 실제 손동작에서 드러난 문제와 수정 범위는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다. 정확한 좌표 클릭을 요구하지 않고 먹이를 넉넉한 범위에 놓도록 한다. UI 구현 세부값을 별도 제품 완료 조건으로 늘리지 않는다.

### 2.6 알람 / 타이머 / 리마인더 구조

**스케줄러는 언제 어떤 일을 해야 하는지 확인하는 시간 담당**이다. 펫의 감정이나 화면 갱신과 분리해 알림 시각을 관리한다.

| 종류 | 시간의 의미 | 예 |
|---|---|---|
| 타이머 | 시작부터 일정 시간이 지남 | 5분 뒤 |
| 알람 | 특정 날짜·시각 | 내일 오전 7시 |
| 리마인더 | 특정 날짜·시각과 할 일 내용 | 내일 오후 3시 서류 확인 |

예약을 먼저 저장하고 성공했을 때만 “등록됨”을 표시한다. 가까운 예약을 기다리면서 주기적인 재확인과 재시작·절전 복귀 시 확인을 함께 사용한다. 정해진 시간에 예약 식별자로 전달 기록을 남기고 운영체제 알림과 앱 내부 표시를 요청한다. 등록 목록 확인과 취소도 최소한으로 제공한다.

화면에서 초를 하나씩 빼는 방식만 쓰지 않는다. 원래 길이, 시작 시각, 예정 시각을 저장한다. 실행 중의 타이머는 **단조 시계**, 즉 사용자가 시스템 시각을 바꿔도 뒤로 가지 않는 경과 시간 기준을 사용한다(D-043). 재시작 이후에는 저장된 실제 날짜·시각이 필요하며, 절전 포함 방식도 운영체제에서 검증해야 한다.

| 앱·기기 상태 | 설계상 동작 제안 | 지원 상태 |
|---|---|---|
| 앱 실행, 컴퓨터 깨어 있음 | 예정 시각 판단과 알림 요청 | 구조는 단계 6·7, 조건별 후속 실기기 결과는 5.8절의 개발 기록 참조 |
| 펫·입력창만 숨김, 앱 계속 실행 | 메인 영역에서 시간 관리 유지 | 숨김과 종료를 명확히 구분할 필요 |
| 화면 잠금 | 앱 실행 여부와 운영체제 알림 설정에 따름 | 일부 사용자 관찰 있음. 종류·배너·소리별 확인 범위는 5.8절 참조 |
| 컴퓨터 절전 | 절전 중 일반 앱 코드의 정시 실행을 가정하지 않음. 복귀 후 지난 항목 확인 | 절전 중 전달 보장 없음 |
| 앱 완전 종료·컴퓨터 꺼짐 | 재실행 시 지난 항목 복구 | 종료 중 정시 전달은 별도 결정·운영체제 연동 없이는 보장 불가 |

**현재 v0.1 결정:** 5분 타이머는 D-043, 일회성 알람·리마인더는 D-046의 후속 결정에 따라 앱이 완전히 종료된 동안 정시 전달을 약속하지 않는다. 다시 열면 지난 미확인 항목으로 보여준다. 위 표의 화면 잠금·물리 절전 경계와 실제 운영체제 표시 성공은 각각의 실기기 기록으로 판단한다. 늦은 알림을 정상 시각 전달로 기록하거나 아기의 서툼으로 정당화하지 않는다.

시스템 시각 변경, 시간대 이동, 일광절약시간으로 같은 현지 시각이 두 번 오거나 사라지는 경우를 구분한다. 정확한 재해석 정책은 미정이다. 사용자가 등록한 날짜·현지 시각·시간대와 계산된 전달 시각을 함께 보관하고 모호함은 확인하는 안을 추천한다.

데이터베이스 기록과 운영체제 알림 표시는 하나의 저장 묶음으로 처리할 수 없다. 표시 요청 후 기록 전에 종료되면 중복 가능성, 기록 후 표시 요청 전에 종료되면 누락 가능성이 생긴다. 따라서 운영체제 알림이 **정확히 한 번** 보였다고 보장하지 않는다. 앱 안에서는 예약 식별자로 하나의 알림 항목을 유지하고 전달 시도·실패·사용자 확인을 나누며, 재시작 때 미확인 항목을 복구하는 안을 추천한다. 운영체제에 요청을 보낸 것과 사용자가 읽은 것은 다르다.

알림 권한 거부·집중 설정으로 표시가 억제된 경우를 숨기지 않고 앱 내 미확인 항목으로 남긴다. 한꺼번에 밀린 알림을 과도하게 쏟지 않는 표현 방식도 정해야 한다. 반복 예약, 중요도 등급, 10분 뒤 재알림은 이 최소 구현안에 넣지 않는다. 후자의 두 항목은 기준 문서에서도 필수 완료 범위가 아니다.

### 2.7 AIService / AIProvider와 Codex 확장 지점

**추상화는 특정 제품의 구현 대신 공통 역할을 정하는 것**이다. 기기가 바뀌어도 같은 콘센트를 쓰는 것과 비슷하다. AI 연결이 바뀌어도 펫의 기억과 규칙을 그대로 유지하기 위해 필요하다.

| 경계 | 역할 | v0.1 상태 |
|---|---|---|
| AIService | 사용자 제약, 필요한 기억, 보낼 정보 최소화, 요청·결과 조율 | 구조만 고려 |
| AIProvider | 특정 AI의 대화·추론 기능을 공통 요청·응답으로 연결 | 첫 제공자·인증·모델 미정 |
| 작업 도구 연결 | 작업 시작·진행·취소·승인·결과를 연결 | Codex 조건부 후속 후보 |

기본 대화와 비서 요청은 로컬 규칙으로 처리한다. AI 미연결은 정상 상태다. AIService가 펫의 생활을 시작시키는 전제 조건이 되어서는 안 된다. v0.1에서 실제 연결이 없다면 빈 제공자 관리 화면이나 여러 제공자의 형식뿐인 코드를 만들 필요도 없다.

후속 연결에서는 사용자 요청 → 허용 조건 확인 → 필요한 기억만 구성 → AI 응답 또는 작업 결과 → 검증 → 필요한 로컬 반응 순서로 처리한다. 외부 AI의 응답이 펫 상태·관계·권한을 직접 덮어쓰거나 임의 명령으로 실행되어서는 안 된다.

Codex는 일반 대화 모델과 구분한다. 사용자가 시작한 코드·파일 작업의 도구로 검토하며, 공식 연결 방식과 운영체제별 동작·구독 범위는 도입 시 다시 확인한다. 기존 조사 결론은 Decision Log D-019를 따른다. **일반 ChatGPT 구독을 앱의 대화 API 사용권으로 가정하지 않는다.** 여러 AI 자동 선택은 미래 범위다.

선택 순서는 사용자 명시 제약 > 고급 설정 > 작업별 선호 > 자동 판단이다. 사용자가 금지한 AI·시점·정보 전송을 자동 판단이 뒤집지 못한다. 인증값을 공식 클라이언트에서 추출하거나 비공식 내부 경로를 사용하지 않는다. 비용이 드는 연결은 사용자가 선택할 때 별도로 안내한다.

### 2.8 안전한 권한 구조

**권한은 특정 대상에 특정 행동을 해도 되는 허용 범위**다. 펫의 이해·제안·수행 능력이 성장해도 권한은 자동으로 넓어지지 않는다.

| 작업 | v0.1 제안 |
|---|---|
| 앱 전용 저장소에 상태·경험 저장 | 기본 앱 기능으로 제한 |
| 사용자가 요청한 로컬 알림 등록·취소 | 입력을 검증한 뒤 처리 |
| 운영체제 알림 표시 | 운영체제의 허용 상태 확인 |
| 임의 파일 읽기·수정·삭제, 프로그램 실행 | 실행 경로 자체를 제공하지 않음 |
| 외부 AI 정보 전송 | 후속 연결 도입 시 별도 사용자 선택 |
| 성장에 따라 실행 허용 확대 | 허용하지 않음 |

화면에는 필요한 요청만 노출하고 메인 영역에서 요청 종류·발신 창·값을 다시 검사한다. 외부 페이지나 임의 스크립트를 앱 화면에서 실행하지 않고, 입력 문장을 HTML 코드로 해석하지 않는다. 화면에 운영체제 접근 권한 전체를 주지 않는 것이 기본이다. 구현 시 공식 [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security)을 확인한다.

향후 파일 작업은 대상 폴더·허용 행동·해당 작업·유효 기간을 묶어서 허용하고 실행 직전에 다시 확인하는 방향이다. 요청 취소나 권한 철회도 반영해야 한다. 이 전체 권한 관리 기능은 후속 범위이며 v0.1에 선구현하지 않는다. 향후 비밀 인증값을 보관할 때에는 일반 데이터베이스 평문 대신 운영체제의 인증정보 보관 기능을 검토한다.

### 2.9 현재 연결 구조의 세부 규칙

이 절은 창·입력·생활·부화의 현재 연결 규칙을 기능별로 설명한다. D-055·D-057~D-061의 선택과 구현값을 보존하며 새 제품 기준을 추가하지 않는다. 날짜별 검사·개별/통합 상태·실패와 미검증 항목은 5.3~5.7절에서 개발 기록으로 연결한다.

**창 복구와 알림 결과 — D-057**

- `windows.ts`·`app.ts`: 화면 오류 때 같은 창 재로딩을 최대 두 번 시도하고 30초 정상 동작하면 횟수를 초기화한다. 명시적 종료 중에는 재시도하지 않는다. 로컬 `pet-diagnostics.log`에는 고정 사건 코드와 시각만 약 16KB 한도로 기록한다. 절전·잠금 복귀 때 위치도 다시 확인한다. 실제 사라짐 원인과 주 실행 프로세스 종료의 해결을 보장하지 않는다.
- `notifications.ts`: 표시 뒤 실패 신호를 기록하고, 사용자 미클릭을 실패로 취급하지 않는다. 앱 종료 때 이미 표시된 알림을 임의로 닫지 않는다. 당시 가짜 알림 검사와 실제 표시 확인은 개발 기록의 날짜별 결과를 구분해 읽는다.

**단일 입력·요청 해석·닫힘 — D-055·D-057·D-058**

단일 입력과 확인 후 날짜 알림 저장을 유지한다. 문법 확대·자동 문구 제거·초읽기는 D-057 이후 D-058에서 연결한 범위다.

입력창 중복 열기는 `prompt-window.ts`가 표시 여부와 입력 초점을 함께 판단한다. 이미 입력 중이면 유지하고, 다른 창 뒤에 가려졌다면 작성 내용과 선택 위치를 보존하며 앞으로 가져온다. 실제로 숨겨졌던 창을 열 때만 열림 안내를 보낸다(D-057 후속).

- `time-parser.ts`·`prompt.ts`: 한국어 시각·반·`분에`와 자연스러운 내용 순서를 일회성 알림으로 해석한다. 날짜 생략은 오늘로 확인하고, 오전·오후 후보가 하나만 미래이면 그 후보를 보여준다. 두 후보면 선택 버튼으로 되묻고, 모두 지났으면 날짜·시간을 다시 받는다. 확인 카드의 명시적 등록 전에는 저장하지 않는다.
- `prompt.ts`: 기존 성공 결과의 8초 자동 닫힘을 남은 시간으로 표시한다. 단순히 가려진 창을 다시 앞으로 가져와도 마감 시각을 늘리지 않는다. 입력·한글 조합·클릭·키 조작은 닫힘을 취소하고 성공 결과를 유지한다. 이후 목록 취소·확인 결과를 예전 등록 문구로 덮어쓰지 않는다. 날짜 알림 확인 단계에는 초읽기를 추가하지 않는다.

**아기 생활과 관계 표현 — D-057·D-058**

- `baby-social.ts`·`baby-life-repository.ts`: 수면 중 반복 접촉의 거리 두기 종료 시점을 예정 기상 뒤 기존 2분까지 보존한다. 저장 형식은 유지하고, 졸린 상태의 기상에도 거리 두기를 표현한다. 터치 기상·드래그 돌봄은 추가하지 않았다.
- `pet.ts`·`styles.css`: 자동 생활·감정 문구를 제거하고 수면 중에만 작은 청록색 `zZ`를 머리 옆에 표시한다. 화면 읽기 도구용 상태 설명과 저장 실패 안내는 유지한다. 움직임 줄이기 설정에서는 밝기 변화도 멈춘다.
- `baby-life.ts`·`windows.ts`: 아기의 투명 생활 창은 420×300이며 알 창 크기는 유지한다. 먹이 위치까지 8~20초 동안 다가간 뒤 입에서 5.5초 동안 먹이가 줄어들고, 식사 완료 경험은 끝난 뒤 기록한다. 도달 불가능한 가장자리는 가까운 도달 가능 위치로 조정한다. 먹은 자리에는 현재 앱 실행 동안 머물고 재시작 후 위치는 초기화한다. 과거 식사의 선택 필드 누락은 기존 시간 규칙으로 읽는다. 창 안 이동에 맞춰 클릭·커서 기준을 보정하며 이동은 돌봄으로 세지 않는다. 사용자의 추가 결정에 따라 이름표와 감정구슬도 몸을 따라간다. 긴 이름과 구슬은 생활 공간 밖으로 잘리지 않도록 배치한다.

**수면 후 기상 — D-059**

[D-059](Jarvis_Pet_Decision_Log.md)에 사용자 선택과 표시 순서를 기록한다. `wake-motion.ts`는 현재 화면 문서에서 관측한 수면→기상 전환만 한 번 감지하고 재로딩 뒤 이미 깨어 있으면 재생하지 않는다. `wake-motion.css`는 기존 위치 이동과 분리된 짧은 몸짓을 정의한다. `pet.ts`는 기상 중 식사·거리두기·재회 움직임을 잠시 보류하고 종료 때 최신 상태를 다시 그린다. `zZ`는 생활 상태에 맞춰 즉시 감추고, 운영체제의 움직임 줄이기 설정에서는 몸짓을 생략한다. 저장 자료·수면 계산·돌봄 및 관계 사건은 변경하지 않는다.

**알 외형과 같은 창 부화 — D-060·D-061**

D-060의 사용자 선택에 따라 `index.html`의 기존 투명 펫 창에 부화 장면을 겹친다. 메뉴 선택 전에는 알 생활을 유지한다. `HatchSequence`는 전조·금·구슬·껍질·아기·첫 교감을 보인 뒤 각 장면의 저장이 성공해야 자동으로 다음 장면을 그리며, 실패 시 멈추고 다시 시도 버튼을 보여준다. 기존 `LifecycleRepository`의 완료 지점·개체 식별자·준비 시간·돌봄 단축 정책은 그대로 사용한다. 브라우저 미리보기는 펫 저장 자료를 읽거나 쓰지 않는다.

알과 아기의 그림은 약 80%로 줄이고 보이는 그림에 맞춰 클릭 영역을 줄인다. 먹이 좌표와 입·이름표·감정구슬·수면 기호의 연결은 별도 기준으로 유지한다. 창은 아기 등장 지점까지 180×200이며, 그 지점이 저장된 뒤 420×300으로 넓힌다. 화면 가장자리에서는 작업 영역 안으로 새 창을 제한하고, 실제 이동 차이를 그림 위치에 더해 펫의 화면상 중심을 유지한다. 이름 카드는 첫 교감 뒤 아기 아래에 둔다. 화면 아래 끝에서 공간이 부족하면 이름 단계에서만 아기를 필요한 만큼 위로 옮긴다(2026-10-01 사용자 선택). 카드 높이 54px·하단 여백 8px·아기와의 간격 2px를 확보한다. 이름 저장 직후 첫 생활 프레임은 부화 아기의 화면상 위치에서 시작한다. 이는 저장되지 않는 일시적 표시 위치이며, 같은 펫의 생활·경험 기록은 기존 저장소에 남는다.

D-061에 통합 보완과 검증 한계를 기록한다. `pet.ts`의 첫 아기 위치 설정과 수면 후 기상 우선순위를 함께 유지하고, 기상·부화 화면 자산을 함께 로드한다. 부화 전조는 크기와 회전을 분리해 80% 외형을 유지한다. 화면 아래 끝에서는 사용자 선택에 따라 이름 단계에서만 아기를 필요한 만큼 위로 옮긴다.

## 3. 핵심 데이터 모델

데이터 모델은 **무엇을 어떤 항목으로 기억할지 정한 설계**다. 아래 3.1~3.3절의 표는 개념과 후보 필드를 설명하며 실제 저장 형식 전체와 일치한다고 보지 않는다. 현재 연결된 저장 정보는 다음과 같이 구분한다. 관계·감정의 일부 내부 값은 잠정 구현값이고, 최종 수치·기질 차이·성격 반영·경험 보존 기간은 미정이다.

| 현재 저장 정보 | 저장 책임·근거 | 후보와의 구분 |
|---|---|---|
| 개체 식별·단계·이름·부화 진행, 알 경과·돌봄 | 펫 저장소와 생애·알 생활 저장 담당, ADR-001 v1~v3 | 모든 외형·기질·화면 위치 후보가 구현됐다는 뜻은 아님 |
| 아기 생활 상태와 실제 경험, 감정·관계의 최소 상태 | `baby-life-repository.ts`, ADR-001 v4~v5, D-048·D-049 | 실제 식사·접촉·완료 수면과 칭찬·놀이 등 최소 사건. 전체 대화·성격 공식을 저장하지 않음 |
| 타이머·날짜 알림과 전달·확인 상태 | `timer-repository.ts`, `schedule-repository.ts`, D-043·D-046 | 펫 파일과 별도 관리. 후보 표의 모든 필드·기능을 약속하지 않음 |

### 3.1 펫의 현재 상태

| 모델 후보 | 주요 항목 제안 | 필요한 이유 |
|---|---|---|
| 개체 정보 | `petId`, 생성·탄생 시각, 이름, 외형 식별자, 기질 생성 기준값 | 알과 아기가 같은 개체임을 유지 |
| 생애 진행 | 성장 단계, 부화 준비 상태, 연출 완료 지점, 첫 교감·이름 짓기 완료 여부 | 중간 종료 후 이어가기 |
| 생활 상태 | 배고픔, 졸림, 수면 여부, 마지막 계산 시각 | 몸의 필요를 감정과 별도로 관리 |
| 감정 | 종류, 내부 강도, 발생 원인·시각, 진정 기준 | 순간 반응과 자연스러운 복귀 |
| 관계 | 내부 익숙함·신뢰, 일시적 거리두기, 최근 상호작용 시각 | 장기적인 행동 차이와 회복 |
| 선천 기질 | 약한 반응 경향, 생성 규칙 버전 | 재실행할 때 기질이 다시 바뀌지 않게 함 |
| 화면 정보 | 화면 식별자, 펫 위치·방향 | 모니터 변경 후 안전한 위치 복원 |

“배고프고 졸리지만 칭찬에는 기쁘고 사용자와 친숙함”이 동시에 가능해야 한다. 하나의 행복도에 모든 의미를 넣지 않는다. 내부 계산값을 쓰더라도 화면에 숫자·게이지·관계 등급으로 노출하지 않는다. 화면으로 보낼 정보는 몸짓·표정·구슬 표현 중심으로 제한한다.

후천 성격 전체를 계산하거나 성장 결과를 미리 확정하지 않는다. v0.1은 약한 선천 기질, 최소 관계 반응, 이후 해석할 수 있는 경험 기록을 우선한다.

### 3.2 아기 경험 기록 — v0.1 필수

경험 기록은 **현재 상태와 별도로 보존하는 실제 사건**이다. 배고픔이 해소되었다는 상태만 있으면 어떤 돌봄을 받았는지 나중에 알 수 없다.

| 항목 후보 | 의미·예시 |
|---|---|
| 경험 식별자 | 같은 식사를 중복 기록하지 않기 위한 값 |
| 펫 식별자 | 경험의 주인 |
| 발생 시각·당시 성장 단계 | 아기 때 발생했는지 판단 |
| 경험 종류 | 식사·놀이·칭찬·터치 등 후보 |
| 필요한 상황 | 수면 중이었는지, 졸렸는지 등 최소 정보 |
| 실제 결과 | 먹기 완료, 잠시 피함, 구슬 보여주기 등 |
| 기록 형식 버전 | 나중에도 옛 기록의 의미를 해석하기 위한 번호 |

예: 아기 / 식사 / 졸린 상태 / 사용자가 먹이를 가까이 옮김 / 먹기를 마침.

표의 추가 종류와 필드는 **제안**이다. 현재 수집하는 최소 사건은 D-048·D-049와 ADR-001을 따르며, 수집 항목을 늘리기 전에는 범위를 정해야 한다. 또한 성격 반영 공식과 보존 기간을 임의 확정하지 않는다. 경험 기록이 필수라는 이유로 전체 대화나 매 순간의 마우스 좌표를 저장하지 않는다. 부재 중 실제로 없었던 식사·사용자 놀이를 경험으로 만들어 넣지 않는다. 보존 정책을 정하기 전 조용히 과거 경험을 자동 삭제하지 않는다.

### 3.3 비서 기능과 임시 기억

| 데이터 | 항목 후보 | 보존 구분 |
|---|---|---|
| 예약 알림 | 식별자, 종류, 내용, 날짜·현지 시각·시간대, 전달 예정 시각, 타이머 원래 길이, 예약·취소 상태 | 재시작 뒤 복원 필요 |
| 전달 기록 | 예약 식별자, 예정 회차 식별, 전달 시도·실패 시각, 사용자 확인 여부 | 중복과 누락 복구에 필요한 최소 기록 |
| 대화 중 임시 정보 | 진행 중 요청, 빠진 정보, 확인한 시간·내용 | 처리·취소 후 정리 |
| 사용자 명시 기억 | 기억을 요청한 내용과 출처 | 장기 기억 원칙만 유지, 일반 기억 기능의 범위는 후속 결정 |

모든 테이블을 처음부터 각각 만들 필요는 없다. 펫 상태는 하나의 묶음으로 저장하고 경험·예약·전달 기록은 별도 항목으로 두는 작은 구조부터 검토한다. 큰 대화 저장소나 검색 엔진은 지금 만들지 않는다.

### 3.4 로컬 영속화와 복구

**영속화는 앱을 꺼도 데이터가 남도록 저장하는 것**이다. 사용자 선택에 따른 SQLite는 별도 서버 없이 펫의 상태와 경험을 같은 파일 기반 저장소에 보관한다. 알부터 아기 경험까지의 형식과 앱 전용 위치·변환 한계는 [ADR-001](ADR-001-local-pet-storage.md)을 따른다. 경험 보존 기간과 이후 성격 반영 규칙은 미정이다.

**트랜잭션은 관련 변경을 전부 저장하거나 전부 취소하는 한 묶음**이다. 식사 완료 때 배고픔 변화·식사 경험·계산 시각을 함께 저장하면 중간 종료로 기록 일부만 남는 문제를 줄인다. 이것을 원자적 저장이라고도 한다. [SQLite 원자적 저장 설명](https://www.sqlite.org/atomiccommit.html)

**Repository는 저장소에 접근하는 전용 창구**다. 여기서는 Git 저장소를 뜻하지 않는다. Pet Brain은 SQLite 명령 대신 “펫 저장”, “경험 추가”를 요청한다. 저장 도구를 바꾸더라도 펫 규칙에 미치는 영향을 줄인다.

추천 저장·복구 순서는 다음과 같다.

1. 앱 전용 사용자 데이터 폴더에 저장한다. 프로젝트 코드 폴더와 분리한다.
2. 저장을 수정하는 담당을 한 곳으로 두고 중복 앱 실행이 같은 펫을 동시에 갱신하지 않게 한다.
3. 이름·경험·예약·부화 지점 등 중요한 변경은 해당 처리에서 저장한다. 종료 시 저장에만 의존하지 않는다.
4. 생활 상태는 마지막 계산 시각과 함께 주기적으로 보존한다. 장기 부재는 제한된 변화와 자연스러운 복귀로 해석한다.
5. 앱 시작 시 저장 형식 버전을 확인한다. **마이그레이션은 기존 데이터를 새 저장 형식으로 옮기는 작업**이며, 변경 전 복구용 사본과 실패 시 원본 보존을 준비한다.
6. 디스크 부족·쓰기 권한 오류·손상 때 성공으로 표시하지 않는다. 저장 실패 상태를 알리고 중요한 변경을 조용히 버리지 않는다.
7. 손상된 저장소를 삭제해 새 알을 만들지 않는다. 원본을 보존하고 복구 가능한 사본 여부를 확인한다.

상태와 경험을 모두 매번 재생해 현재 상태를 만드는 복잡한 기록 체계는 도입하지 않는다. 현재 상태와 최소 경험 사건을 함께 관리한다. 자동 백업 주기, 사본 수, 내보내기·삭제 화면, 암호화는 미정이다. 로컬 저장 자체가 암호화를 의미하지 않는다. 내보내기 가능성은 고려하지만 클라우드 동기화는 v0.1 밖이다.

## 4. v0.1 구현 단계

아래 단계 번호는 초기 구현 순서와 다른 문서의 참조를 유지한다. 알·부화·아기 생활·기본 비서의 연결 구조와 검사 기록이 존재하며, 단계 1만 구현된 상태로 읽지 않는다. 각 단계의 목표·완료 조건·테스트 방법은 검증 기준이지 완료 선언이 아니다. 현재 구조와 결과 출처를 구분하고, 남은 범위는 개발 기록의 후속 결과와 함께 판단한다.

### 단계 0. 첫 구현에 필요한 결정 정리

- **목표:** Electron + TypeScript / macOS 첫 검증 선택을 기록하고, 임시 외형·검증 범위를 정한다. 당시 미정이던 SQLite는 이후 D-039에서 선택했다. React 등 미도입 후보와 구분한다.
- **주요 파일:** 현재 기술 설계서, 기존 `docs/Jarvis_Pet_Decision_Log.md`.
- **완료 조건:** 선택한 검증 방향, 추천 기술, 미정 항목이 구분되고 코드 구현을 시작할 범위가 명확하다.
- **테스트 방법:** PRD 17~18장과 문서 내용 대조. 이 단계는 문서 검수이며 앱 테스트가 아니다.
- **다음 연결:** 실제 창 검증에 필요한 최소 코드만 만든다.

### 단계 1. 투명한 알 하나로 창 기능 검증

**현재 구현 구조:** 투명한 임시 알 창은 Electron·TypeScript와 HTML/CSS로 만들고, 제한된 `preload` 통로로 클릭·드래그·메뉴 조작을 연결한다. 초기 외형은 최종 그래픽이 아니다. 날짜별 실행·검사 결과는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

- **목표:** 임시 알 표시, 클릭 반응, 드래그 이동, 트레이 종료를 확인한다. 트레이는 운영체제 메뉴 영역의 작은 앱 아이콘이다.
- **창 설계 보완:** macOS에서는 앱이 다른 입력창을 활성화하지 않도록 `focusable: false`와 `type: 'panel'`을 함께 사용한다. 화면 재로딩·모니터 작업 영역 변경 때는 오래된 드래그를 취소하고 창을 사용 가능한 영역 안에 둔다. 실제 문제와 검증 범위는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

- **주요 파일:** `package.json`, `tsconfig.json`, `src/main/index.ts`, `src/main/windows.ts`, `src/renderer/index.html`, `styles.css`, `pet.ts`. 이번 임시 화면은 React 없이 구현했다.
- **완료 조건:** 실제 macOS에서 펫 표시·조작이 가능하고 빈 영역은 뒤 앱 클릭을 막지 않으며 키보드 입력을 빼앗지 않는다. 개발 실행과 실행 앱으로 묶은 결과를 확인한다.
- **테스트 방법:** 다른 앱 입력, 화면 가장자리, 배율 변경, 가능한 다중 모니터 환경과 모니터 분리 검사. 기기가 없으면 미검증으로 기록한다.
- **다음 연결:** 통과 결과로 Electron 최종 채택 여부를 판단한다. 실패하면 창 구성이나 후보를 재검토한다.

**한 번의 후속 실기기 확인:** 후속 통합본을 실행한 뒤 텍스트 편집기에 글을 쓰다가 알을 클릭·드래그하고 입력칸을 다시 누르지 않은 채 이어 쓰기 → 알 주변 및 둥근 네 모서리의 빈 공간을 통해 뒤 앱의 버튼 클릭 → 알을 화면 네 가장자리까지 옮겼다가 다시 안쪽으로 끌기. 보조 화면이 있다면 화면 간 이동·배율 변경·보조 화면 분리 뒤에도 알이 보이고 다시 잡히는지 이어서 확인한다. 보조 화면이 없으면 해당 항목은 미검증으로 유지한다. 이번 작업은 운영체제 화면 조작·접근 권한을 요청하지 않았다.

### 단계 4. AI 없는 알 생활

**알 생활 구조:** [D-042](Jarvis_Pet_Decision_Log.md#d-042-알의-쓰다듬기와-이동을-나누고-최소-돌봄-사건을-보존한다)의 조작·시간·수집 결정을 아래 모듈에 나눈다. 당시 개별 브랜치와 후속 통합 검사 결과는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

**D-054 반영 구조 — 2026-10-06 원본 코드 확인:** [D-054](Jarvis_Pet_Decision_Log.md#d-054-알-쓰다듬기는-대각선-왕복과-알-경계-밖-놓기를-인정한다)에 따라 첫 의도적인 이동 방향을 기준으로 평면상 왕복을 판정하고, 시작점에서 멀어졌다는 이유만으로 무효화하지 않는다. [화면 입력 처리](../src/renderer/pet.ts)는 같은 투명 창 전체에서 손 떼기를 받는다. 문서 보완 전 검토의 미커밋 상태·실제 손동작 확인 대기는 당시 상태다. 이후 2026-10-06 PR #39 병합 뒤 손동작 6개 확인은 개발 기록에 있으며 다른 장치·투명 창 바깥 조작·장기 사용으로 확대하지 않는다. 이전 수치와 검사 이력은 [개발 기록](Jarvis_Pet_Development_Log.md#stroke-adjustment-2026-09-27)에 보존한다.

- [알 조작 판정](../src/main/egg-gesture.ts): 누른 직후 6 DIP 이상 움직이면 창 이동으로 유지한다. 350ms 동안 이동을 시작하지 않고 누르면 쓰다듬기 모드가 되며, 첫 의도적인 이동 방향에 대한 되돌림 6 DIP 이상과 유효 이동 합계 18 DIP 이상을 요구한다. DIP은 화면 배율과 무관한 논리적 거리 단위다. 한 번의 관측 이동이 6 DIP 미만이면 작은 흔들림으로 제외하며, 시작점 기준 최대 이탈 거리는 두지 않는다. 취소·화면 재로딩·중복 종료는 사건을 남기지 않는다. 메인 영역이 OS 좌표와 단조 시계(뒤로 가지 않는 시간)를 읽고 화면의 임의 좌표는 받지 않는다.
- `src/pet/egg-life.ts`: 입력된 시각과 기존 값만으로 경과·사건을 반환한다. 저장·Electron·AI 의존은 없다. 벽시계 기준 양의 차이를 누적하고 시각 역행 때 마지막 최대 관측을 유지한다. 종료 중 시간도 포함하되 큰 시계 변경의 실제 의미는 구분할 수 없다. D-042 최초 단계에서는 경과를 기록만 했고, 이후 D-051에서 이 누적 경과와 돌봄 기록을 부화 준비 판단에 연결했다. 아기 이후 성장 계산은 v0.1 범위 밖이다.
- `src/storage/egg-life-repository.ts`: 형식 v1 사본 보존 후 v2로 표를 추가하고 같은 펫을 유지한다. `egg_life(elapsed_ms, observed_at_ms)`와 `egg_care(id, kind, occurred_at_ms, elapsed_ms)`가 최소 필드다. 단일 알 DB이며 관계·성격 수치를 만들지 않는다. 돌봄 사건과 경과는 한 트랜잭션으로 처리한다. 자세한 변환·복구 한계는 [ADR-001](ADR-001-local-pet-storage.md)을 따른다.
- `src/main/app.ts`가 시작·60초·정상 종료에 경과를 저장하고 창에 돌봄 저장 함수를 전달한다. 창은 저장 성공 후 Brain 반응을 요청하고, 실패 때 오류 안내를 보낸다. 화면 재로딩은 진행 중 동작을 버리고 Brain의 현재 반응만 다시 읽는다. 임시 반응·커서 경로·창 위치는 이 저장소에 넣지 않는다.

**반응 연결:** `src/pet/brain.ts`는 AI·화면·SQLite와 분리해 대기 → 짧은 클릭 반응 → 대기를 결정한다. 화면은 전달받은 상태만 표현하고 임시 반응은 SQLite에 기록하지 않는다. 저장과 반응의 결합 검사는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

- **목표:** 알의 대기·작은 반응·쓰다듬기·굴러가기와 부화 준비 판단을 구현한다.
- **주요 파일:** `src/pet/brain.ts`, `src/pet/egg-life.ts`, `src/main/egg-gesture.ts`. 초기 `egg.ts`·`clock.ts`는 현재 파일명이 아니다.
- **완료 조건:** LLM 없이 반응하고 시간·돌봄 정보가 재시작 후 유지된다. 준비 상태여도 부화 연출 구현 전에는 임의 부화하지 않는다.
- **테스트 방법:** 가짜 시계로 돌봄 유무·장기 부재·시각 역행을 검사하고 실기기에서 조작 충돌을 확인한다.

### 단계 5. 입력창과 짧은 대화 흐름

**입력창 구조:** `src/main/prompt-window.ts`의 별도 입력창을 메뉴 막대에서 열고, `src/preload/prompt.ts`의 제한된 요청 창구로 연결했다. React는 추가하지 않았으며 `src/renderer/prompt.html`·`prompt.ts`가 입력·앱 결과·예약 목록을 담당한다. 알은 말하지 않는다. 한글 조합 시작/끝, `isComposing`, 키 코드 229와 조합 종료 직후 Enter를 보호한다. Esc·닫기·창 닫기는 입력 초안을 버린다. 저장 성공 후 8초 자동 닫기를 사용하며 새 입력·키보드·포인터 상호작용은 자동 닫기를 취소한다. 모르는 요청·오류에는 자동 닫기를 걸지 않는다. 알 클릭 경로와 Pet Brain은 기존 상태를 유지한다.

메인 영역에서 발신 창·프레임·페이지·인자 개수를 검증하고, 타이머 안내 전용 창에는 등록·취소 권한을 주지 않는다. 화면에서 SQL·파일·일반 명령을 실행할 수 없다. Electron 합성 조합 이벤트 검사는 실제 macOS 한글 입력기 검증을 대신하지 않는다. 실제 별도 Electron 창에 입력 초점이 있을 때 만료 안내가 초점을 가져가지 않는 것은 확인했고, 타사 앱의 키보드 복귀는 미검증이다. 일반 짧은 대화·정보 부족 되묻기가 남아 있다는 설명은 초기 입력창 당시 상태다. 후속 아기 명령과 날짜 알림 해석은 단계 7·10 및 2.9절을 따른다. 일반 AI 자유 대화로 확대하지 않는다.

- **목표:** 입력·되묻기·취소·결과 표시·자동 닫기를 만든다. 일반 AI 연결은 넣지 않는다.
- **주요 파일:** `src/renderer/prompt.html`, `src/renderer/prompt.ts`, `src/main/prompt-window.ts`, `src/preload/prompt.ts`, `src/pet/baby-social.ts`, `src/assistant/time-parser.ts`. 초기 React 화면·대화 전용 폴더 후보와 구분한다.
- **완료 조건:** 모르는 요청을 실행하지 않고, 알은 말하지 않으며, 입력·되묻기 중 창이 사라지지 않는다.
- **테스트 방법:** 한글 조합 Enter, Esc 취소, 모호한 시간, 긴 입력, 클릭·드래그 구분, 다른 앱 입력 복귀 검사.
- **다음 연결:** 실제 알림 기능을 연결할 입력 통로가 생긴다.

### 단계 6. 타이머 하나를 끝까지 완성

**타이머 구조 — D-043:** `src/assistant/timer.ts`가 5분 타이머의 해석·경과 시간·등록/취소/복원을 맡고 `src/storage/timer-repository.ts`가 별도 `assistant/timers.sqlite3`에 저장한다. `src/main/notifications.ts`는 운영체제 알림 요청과 결과를 분리한다. 동시에 진행하는 타이머 하나, 같은 요청의 중복 방지, 미확인 완료 목록, 확인 후 목록에서 제외까지 구현했다. 입력 원문은 저장하지 않는다. 취소·확인 이력은 재전송 방지를 위해 보존하며 자동 삭제 정책은 아직 없다.

이번 승인 범위에서는 완전 종료·절전 중 정시 전달을 보장하지 않는다. 재시작 때 아직 남은 타이머는 저장된 예정 시각으로 이어가고, 지난 예약은 “지난 타이머 · 재시작 후 복원”으로 남긴다. 지난 예약의 OS 알림 재전송은 없으며 앱 내 미확인 목록은 사용자가 확인할 때까지 남는다. 앱 시작 시에도 알림용 비활성 창으로 안내하며 입력창을 자동으로 열거나 초점을 잡지 않는다. 실행 중 시스템 시각 변경은 경과 시간 판단을 바꾸지 않는다. 절전 이벤트를 받았을 때 정지된 경과 시간을 보완하되, 절전 중 시각 수정·재시작 사이 시각 수정은 실제 경과 시간과 구분할 수 없는 한계가 있다.

예약 만료를 DB에 먼저 남기고 운영체제 알림을 시도한다. 시스템 상태는 미요청/요청/표시 신호/실패/미지원/결과 미확인이며 앱 표시·사용자 확인 상태와 다르다. 화면을 숨긴 상태를 앱 표시 성공으로 기록하지 않는다. 표시 요청 도중 종료되면 미확인 목록으로 복원하며 시스템의 정확히 한 번 전달을 주장하지 않는다. 타이머 저장소를 열 수 없으면 입력 기능을 끄고 기존 알과 파일을 보존한다.

- **목표:** “5분 타이머”를 저장·시간 판단·알림까지 연결한다. 2.6절의 실행 상태별 지원 정책을 먼저 정한다.
- **주요 파일:** `src/assistant/timer.ts`, `src/main/notifications.ts`, `src/storage/timer-repository.ts`. 초기 `scheduler.ts`·`reminder-repository.ts`는 현재 파일명이 아니다.
- **완료 조건:** 저장 성공 후 등록됨을 표시하고 창을 닫아도 앱 실행 중에는 동작한다. 종료·절전·권한 거부 시 한계와 복구를 확인한다.
- **테스트 방법:** 짧은 타이머, 취소, 재시작, 시스템 시각 변경, 절전 복귀, 전달 중 종료·중복 요청 검사.
- **다음 연결:** 알람·리마인더도 같은 시간·전달 구조를 사용한다.

### 단계 7. 일회성 알람과 단순 리마인더

**알람·리마인더 구조:** 명확한 날짜·시각·내용을 확인한 뒤 별도 `assistant/schedules.sqlite3`에 저장한다. 목록·취소·미확인 항목 복원과 운영체제 알림 요청 결과를 펫·타이머 자료와 분리한다. 입력 당시 절대 시각을 유지하는 시간대 해석은 구현 가정이며 장기 제품 결정이 아니다. 당시 검사와 한계는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

**단일 입력창 구조 — D-055:** `prompt.html/ts/css`는 타이머·아기 명령·날짜 알림 요청을 한 입력에서 받는다. 날짜 알림은 입력 아래 확인 카드의 명시적 등록 전에는 저장하지 않는다. 수정·닫기 때 초안을 버리고, 처리 중 중복 전송과 닫힌 창에 늦게 도착한 결과를 막는다. 실제 화면 검사는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

- **목표:** 날짜·시각·내용을 가진 알림과 최소 목록·취소를 지원한다.
- **주요 파일:** `src/assistant/reminders.ts`, `src/assistant/time-parser.ts`, `src/storage/schedule-repository.ts`, 기존 `src/renderer/prompt.ts`.
- **완료 조건:** 해석한 시각과 내용을 명확히 보여주고 모호함을 되묻는다. 예약과 지난 미확인 항목이 재시작 후 복원된다.

### 단계 8. 부화와 첫 교감·이름 짓기

**부화 저장 구조:** 기존 `pet.sqlite3`의 단계·이름·장면 완료 지점을 같은 `petId`와 함께 저장한다. 이전 형식의 원본 사본을 보존하고 각 단계의 저장 성공 뒤 다음 장면으로 진행한다. 형식·복구는 [ADR-001](ADR-001-local-pet-storage.md), 단계별 검사 결과는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

**부화 화면 연결:** 첫 장면은 사용자가 메뉴에서 시작하고 저장된 지점부터 이어간다. 잠금·절전·숨김 중 낡은 요청을 버리고 저장하지 않는 표시 세션과 제한된 화면 통로를 사용한다. 현재 장면은 2.9절과 같이 기존 펫 창에 겹치며 별도 부화 팝업을 뜻하지 않는다. 첫 이름은 앞뒤 공백 정리 후 1~20자로 저장하며 같은 펫의 아기 생활로 잇는다.

**부화 준비 구조:** 누적 경과 시간과 저장된 돌봄으로 준비 여부를 계산하고 준비 상태와 경과를 한 묶음에 저장한다. 준비돼도 알 생활을 유지하고 사용자 메뉴 선택 전에는 첫 장면을 열지 않는다. 인정되지 않은 돌봄도 경험 기록에는 남긴다. 정책 수치는 [D-051](Jarvis_Pet_Decision_Log.md)을 따른다.

**기본 정책 연결:** 일반 실행은 돌봄 없이 24시간, 인정된 클릭·쓰다듬기마다 30분 단축, 1시간 인정 간격·총 6시간 상한을 사용한다. 시작·돌봄·60초 확인·절전 복귀에서 준비 상태를 판단한다. PR #17의 비활성 기록과 PR #19의 후속 연결·검사는 [개발 기록](Jarvis_Pet_Development_Log.md)을 따른다.

- **목표:** 정해진 순서의 부화와 이어하기를 구현한다. 시간·돌봄 영향과 연출 시작 기준을 먼저 결정한다.
- **주요 파일:** `src/pet/lifecycle.ts`, `src/storage/lifecycle-repository.ts`, `src/renderer/HatchSequence.ts`, `src/renderer/NamePrompt.ts`.
- **완료 조건:** 사용자가 구슬 등장·아기 등장·첫 교감·이름 짓기를 순서대로 겪고 같은 `petId`로 이어진다.
- **테스트 방법:** 모든 진행 지점에서 종료·재시작, 잠금·절전, 중복 시작, 이름 저장 실패 검사.

## 5. 테스트 전략

테스트는 **정해진 조건에서 실제 결과가 요구와 일치하는지 확인하는 작업**이다. 코드가 존재하거나 실행 창이 떴다는 사실만으로 기능 완료를 판단하지 않는다.

| 검사 수준 | 쉬운 뜻 | 핵심 확인 |
|---|---|---|
| 단위 검사 | 작은 규칙 하나씩 확인 | 배고픔 변화, 감정 진정, 부화 순서, 시간 해석 |
| 통합 검사 | 연결된 부분을 함께 확인 | 상태·경험 동시 저장, 예약과 복구, 요청 검증 |
| 앱 흐름 검사 | 사용자가 하는 일을 순서대로 수행 | 알 → 부화 → 이름 → 돌봄 → 재실행 |
| 실기기 검사 | 실제 운영체제에서 확인 | 투명 창, 클릭 통과, 입력 초점, 알림 권한, 절전 |
| 장시간 사용 검사 | 며칠 함께 생활 | 상태 연속성, 기억 유지, 방해 정도, 자원 사용 증가 |

**가짜 시계는 검사 중 프로그램에 전달하는 시간을 직접 바꾸는 장치**다. 하루 기다리지 않고 “하루 뒤 재실행”을 검사한다. 실제 운영체제 절전은 이것으로 대체할 수 없으므로 별도로 확인한다. 무작위 반응도 검사에서는 기준값을 고정해 같은 문제를 재현할 수 있게 한다.

### 5.1 반드시 지킬 규칙

- 인터넷과 외부 AI 없이 펫 생활·짧은 반응·기본 비서 기능이 동작한다.
- 부화 전후 식별자가 같고, 없는 동안 부화를 완료하지 않으며, 아기 이후로 넘어가지 않는다.
- 감정·관계·성격은 숫자·게이지·등급으로 표시하지 않는다.
- 감정·몸 상태·관계를 분리하고 구슬은 감정 표현에만 사용한다.
- 부재로 죽음·영구 이별·성장 실패를 만들지 않는다.
- 이름·기질·기본 상태·관계·경험·예약은 재시작 후 유지된다.
- 상태 변경과 경험 기록 중 일부만 저장되는 일을 막는다.
- 저장 전에 등록 성공을 표시하지 않는다. 모호한 요청은 되묻고 취소 시 실행하지 않는다.
- 펫의 감정·관계·수면이 정확한 알림 전달을 방해하지 않는다.
- 허용되지 않은 파일·프로그램 실행 경로가 없다.

### 5.2 PRD 완료 조건과 검증 연결

### 5.8 실제 Mac 검증 계획과 후속 결과의 구분

**2026-10-01에는 문서 반영만 승인된 계획이었다.** 후속 실행 승인과 실제 결과는 개발 기록의 10월 1일·6일 항목을 따른다. 아래 표는 반복 사용 가능한 검사 순서와 판단 기준이며 전부 미실행이거나 전부 통과했다는 뜻이 아니다. 자동 검사, 실제 앱 화면, macOS 알림 표시, 자연스러운 시간 경과·며칠 사용을 각각 판정한다. 현재 문서 정리 승인은 새 검사 실행·데이터 준비·설정 변경을 포함하지 않는다. 제품 완료 기준은 기존 PRD를 유지한다.

**후속 기록의 위치:** 개발 기록에는 2026-10-06 격리 Mac 시험 앱의 세 종류 알림 배너·소리, 종료 중 만료 후 복원·각 확인 처리와 재실행 유지, 잠금 중 타이머 관찰 등의 결과가 있다. 잠금 알람·리마인더는 배너·소리·해제 후 목록을 나눠 읽으며 물리 절전·자연 부화·며칠 생활과 구분한다. 기존 미커밋 개발 기록의 후속 내용을 통합 정리본에 보존하고 관련 상태를 대조했다. 이번 문서 작업에서 앱을 재검사한 것은 아니다.

**검사 데이터와 환경 준비**

- Codex가 검사할 코드의 브랜치·커밋·미커밋 변경, macOS·앱 버전, 앱 실행 방식, 데이터 경로와 실행 중인 앱을 확인한다. 본래 펫 자료와 기존 Preview 자료를 초기화하거나 덮어쓰지 않는다.
- [Mac 앱 묶기 스크립트](../scripts/package-mac.mjs)의 Preview 앱은 별도 `Jarvis Pet Preview` 저장 폴더를 계속 사용한다. 새 앱 묶음을 만들어도 새 임시 펫이 보장되지 않는다. 기존 자료의 존재 여부를 먼저 확인하고, 재실행·며칠 관찰 동안 유지할 전용 검사 폴더와 종료 후 보존 방법을 실행 승인 전에 확정한다. 새 실행 장치가 필요하면 파일·변경안을 별도로 승인받는다.
- [숨김 패키지 검사](../scripts/mac-validation-entry.cjs)는 임시 폴더를 만들고 종료 때 지우므로 며칠 체험 경로로 사용하지 않는다. [앱 검사 실행기](../tests/fixtures/app-runner.ts) 역시 제한된 자동 검사 도구이며, 현재 일반 실행에 임의 데이터 경로를 지정하는 옵션이 있다고 안내하지 않는다.
- 사용자가 실제 잠금·절전·복귀와 알림 표시를 확인한다. 알림 권한·집중 모드 등 시스템 설정은 관찰한 상태를 기록하고, 변경이 필요하면 이유를 설명한 뒤 별도 승인받는다. 실제 펫의 종료·재시작·자료 복사를 검사 편의로 수행하지 않는다.

### 5.10 개인용 v1 후보판 최소 CI

CI는 PR(변경 검토 요청)이 올라올 때 실행하는 자동 점검이다. [워크플로](../.github/workflows/ci.yml)는 `main` 대상 PR에서 Ubuntu 24.04·Node.js 24 한 환경으로 `npm ci` → `npm run typecheck` → `npm run test:ci`를 실행한다. 작업 제한은 10분이며 같은 PR의 새 실행이 이전 실행을 취소한다. 저장소 내용 읽기 권한만 사용하고 인증정보를 checkout 뒤 남기지 않는다. 외부 실행 도구는 확인한 커밋에 고정한다. 캐시·산출물 업로드·별도 비밀 인증값은 사용하지 않는다. 실행 시간이 10분이라는 뜻이 아니라 중단 상한이다.

[`test:ci`](../scripts/test-ci.mjs)는 빌드 뒤 `brain`, `egg-life`, `lifecycle`, `baby-social`, `timer`, `reminders`, `storage`의 7개 `.test.ts`에 대응하는 파일만 일반 Node.js 24로 순차 실행한다. 개별 검사 제한 60초·선택 묶음 전체 제한 120초를 두며 오류·강제 종료를 성공으로 처리하지 않는다. 기존 검사 코드가 만드는 새 임시 자료만 사용한다. CI 설치에서는 Electron 실행 파일 다운로드를 생략한다.

**선택 이유와 한계:** 기존 `npm test`는 Electron 내장 Node와 앱을 사용한다. `baby-life`·재시작·부화 제품·시작 검사는 `.test.ts`라도 자식 프로세스에서 Electron을 실행하므로 최소 CI에서 제외한다. 화면 없는 규칙·저장을 먼저 검사하면 창·초점·운영체제 권한에 의존하지 않는 작은 점검을 유지할 수 있다. 일반 Node.js와 Electron의 실행 환경은 다르므로 SQLite·Electron 연결 호환성을 이 CI 하나로 보장하지 않는다. 기존 전체 검사는 그대로 유지하고 Escape 검사와 함께 Mac에서 별도 조율 후 실행한다. 실제 배너·소리·잠금·절전·며칠 생활 및 인터넷 단절 실기기 검사를 대체하지 않는다.

**비용·운영:** 비공개 저장소는 계정의 포함 시간을 사용하며 초과 사용에 비용이 생길 수 있다. 잔여 시간·결제 설정은 이번 작업에서 확인하거나 변경하지 않는다. Linux 한 작업으로 시작하며 macOS 작업·다중 환경·정기 실행은 추가하지 않는다. [GitHub 권한·시간 제한](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [요금 기준](https://docs.github.com/en/billing/concepts/product-billing/github-actions)을 따른다. GitHub 전송·PR 실행 전에는 실제 Ubuntu CI 통과로 표시하지 않는다.

**검증 기록 경계:** 이번 실행의 명령·종료 코드·실패·재실행은 워크트리의 Git 제외 `.local/readiness-validation/`에 각각 보존해 인계한다. Development Log에는 직접 기록하지 않는다. 이 폴더에는 새 자동 검사 출력만 두며 사용자 펫·관찰 원본은 넣지 않는다. 2026-10-06 후속 요청으로 승인된 6개 파일의 원본 반영·커밋·푸시·PR 생성까지 진행하며, 병합은 이번 범위에 포함하지 않는다. 실제 실행 상태는 PR과 인계 결과에서 구분한다.

### 6.2 문서와의 충돌·해석 주의점

검수 범위에서 핵심 제품 원칙의 직접 충돌은 발견하지 못했다. 다음은 잘못 확대·확정하기 쉬운 지점이다.

- PRD 27장의 `energy`는 초기 예시다. 현재 아기 생활 구조는 배고픔·졸림을 구분한다. 초기 후보 필드를 실제 저장 형식으로 읽지 않는다.
- 외형 자연어 생성, 이름 변경권, 집중 모드, 알림 중요도·재알림을 v0.1 필수 완료 기준으로 올리지 않는다.
- 드래그·고정 시간대·터치 부위 같은 캐릭터 세부 표현을 PRD와 별개의 새 필수 조건 묶음으로 늘리지 않는다.
- 아기 경험 기록은 필수다. 반대로 모든 경험 종류·성격 반영 공식을 이미 확정한 것으로 쓰지 않는다.
- 완전 종료 중 알람·리마인더의 정시 전달은 v0.1에서 약속하지 않고 재실행 때 미확인 항목으로 보여주기로 결정했다. 실제 절전·잠금 중 운영체제 표시 여부까지 결정·검증한 것으로 확대하지 않는다.
- D-004는 상세 Pet Brain 구조 확정 시 ADR 기록을 후속 조치로 둔다. **ADR은 중요한 기술 선택의 이유·대안·영향을 남기는 짧은 기록**이다. D-006의 SQLite 선택 후속 조치는 이름·이유·내용을 먼저 안내한 [ADR-001](ADR-001-local-pet-storage.md)로 이행했다. 기존 Decision Log만으로 대체하지 않았으며 Pet Brain 상세 구조 확정은 이번 저장 작업 범위 밖이다.

### 6.4 실사용 피드백의 설계 반영과 검증 경계

2026-09-28부터 수집한 14개 항목의 관찰·수정·사용자 확인 기록은 [개발 기록의 실사용 목록](Jarvis_Pet_Development_Log.md#field-feedback-2026-09-28)에 보존한다. 각 행의 당시 상태와 후속 결과를 함께 읽으며, 현재 구조는 아래 기준을 따른다.

- **쓰다듬기:** D-054와 단계 4의 평면상 왕복·같은 창 안의 손 떼기 처리를 따른다. 규칙·화면 연결 검사와 실제 손동작 확인을 나눈다.
- **수면 중 접촉:** [D-057](Jarvis_Pet_Decision_Log.md#d-057-실사용-수정-14번은-원본-반영-전에-함께-검사한다)에 따라 수면 중 반복 접촉의 거리두기는 예정 기상 시각 뒤에도 유한한 시간 동안 표현되도록 연결했다. [관계 규칙](../src/pet/baby-social.ts)과 [재시작·기상 검사](../tests/baby-social.test.ts)를 근거로 삼으며 실제 펫의 자연 수면·기상 확인은 별도다.
- **입력·알림·생활 표현:** 단일 입력은 D-055, 자연어 알림·닫힘 초읽기·수면 기호·먹이 이동·이름표는 D-058, 기상·외형·같은 창 부화는 D-059~D-061과 해당 설계 절을 따른다. 10월 1일·6일 시험용 앱의 알림 실기기 확인을 모든 문법·생활 표현의 확인으로 확대하지 않는다.
- **종료·복구:** 화면 처리 오류의 제한된 재로딩과 앱 주 실행 프로세스의 종료 원인 조사는 구분한다. 재부팅 자동 실행 정책, 물리 절전·잠금 뒤 갑작스러운 종료의 원인과 재발 여부, 며칠간 생활은 미확정·미검증 상태를 유지한다.

### 6.5 앱 흐름 조립 함수의 작은 분리 제안 — 코드 수정 승인 전

[app.ts](../src/main/app.ts)의 `startJarvis`는 저장소 준비, 펫 창·부화 연결, 비서 기능, 메뉴와 종료 순서를 조립한다. 세부 기능은 이미 별도 모듈에 있지만 비서 연결 구간에는 타이머·예약 저장소와 서비스, 입력창, 주기적 검사, 절전·복귀 연결과 정리가 함께 있다. 부화 후 단계 변경과 아기 상호작용도 같은 함수의 상태를 참조하므로 변경 영향 확인이 필요하다.

**다음 관련 기능 연결 때 검토할 첫 범위:** 비서 연결 구간을 `createAssistantRuntime` 함수로 추출하는 안이다. 새 파일 후보는 `src/main/assistant-runtime.ts`이며 아직 생성하지 않았다. `app.ts`와 이 후보 파일을 중심으로 작은 변경안을 먼저 승인받는다. 앱 전체 시작·부화 구조의 전면 개편은 이 제안에 포함하지 않는다.

- 조립 함수는 필요한 저장 경로·표시 여부·검사용 알림 연결·아기 반응 콜백을 명시적으로 받고, 입력창 열기·사용 가능 여부·종료 정리 기능을 반환하는 안을 검토한다. 종료 정리는 만든 서비스·반복 실행·이벤트 연결을 해제하는 책임이다.
- 기존 `startJarvis` 옵션과 검사 연결 방식을 유지한다. 알람 저장 실패 시 타이머·펫을 보존하고, 타이머 실패 시 펫을 보존하는 경계를 바꾸지 않는다. 숨김 검사에서 실제 알림을 요청하지 않는 처리도 유지한다.
- 생성 도중 오류와 정상 종료 모두에서 정리가 이루어져야 한다. 앱의 `before-quit`과 `will-quit` 순서, 부화 저장 후 같은 개체·아기 화면 연결, 입력창에서 최신 아기 상태를 읽는 방식이 달라지지 않는지 검토한다.
- 코드 승인 후 `npm run typecheck`와 기존 [통합 검사 실행 목록](../scripts/test.mjs)을 유지해 확인한다. 특히 시작·저장·타이머/예약 재시작·알림·입력창·부화·아기 연결을 확인하고, 추출로 생기는 생성 실패·종료 정리 위험에 기존 검사 공백이 있으면 그 부분만 보강한다. 앱 묶음의 파일 포함 경로에 영향이 있으면 `npm run test:mac-package`도 수행한다. 자동 검사와 별개인 실제 OS 알림·절전 확인은 5.8절을 따른다.

지금은 구조 개선 제안만 문서에 남긴 상태다. 코드 수정·검사 실행·성공 결과를 뜻하지 않는다.

</details>

## 7. 구현·실사용 검증에서 유지할 위험 점검

| 위험 | 왜 중요한가 | 확인·대응 방향 |
|---|---|---|
| 투명 창과 클릭 통과 | 보이지 않는 영역이 다른 앱 조작을 막을 수 있다. | 단계 1에서 펫·빈 영역·드래그·입력 초점을 실제 검사 |
| 완전 종료·절전 중 알림 | 일반 앱 코드가 동작하지 않는 시간을 정시 보장할 수 없다. | 지원 범위를 먼저 결정하고 실행·숨김·잠금·절전·종료를 구분 |
| 알림 전달 중 종료 | DB 기록과 운영체제 표시를 한 번의 작업으로 묶기 어렵다. | 전달 기록·미확인 목록·예약 식별자로 복구, 정확히 한 번 보장 주장 금지 |
| 시각·시간대 변경 | 일정 시각과 경과 시간은 다르게 영향을 받는다. | 타이머와 날짜 알림 분리, 재시작·절전·시각 역행 검사 |
| 부화 중단 | 개체 중복·연출 누락·이름 초기화가 관계 연속성을 해친다. | 완료 지점 저장, 같은 식별자 유지, 모든 지점에서 재시작 검사 |
| 저장 실패·손상 | 펫의 기억이 사라지면 제품 핵심이 무너진다. | 관련 상태 묶음 저장, 사본·원본 보존, 실패를 성공으로 표시하지 않음 |
| SQLite 실행 앱 호환성 | 개발 중 되더라도 실제 앱에 라이브러리가 포함되지 않을 수 있다. | 선택한 Electron·운영체제·CPU 환경에서 실행 앱 검사 |
| 상시 자원 사용 | 항상 켜 둔 앱이 업무를 방해할 수 있다. | 대기·수면 중 갱신 최소화, 처리량·메모리 실측 후 판단 |
| 그래픽 제작량 | 필요한 동작 그림이 구현보다 오래 걸릴 수 있다. | 최소 동작 목록과 임시 그림으로 검증, 최종 제작 방식 별도 결정 |
| 경험 과수집·무한 증가 | 미래 활용을 이유로 불필요한 개인 정보와 기록이 쌓일 수 있다. | 실제 사건 최소 수집, 크기 측정, 보존 정책 결정 전 임의 삭제 금지 |
| Windows 검증 누락 | macOS에서 되는 창·알림이 다른 운영체제에서 다를 수 있다. | 환경별 결과 구분, 검증 전 지원 완료 주장 금지 |
| 범위 확대 | AI·성격 엔진·미래 성장 선구현이 첫 완성을 늦춘다. | PRD 필수 범위에 없는 아이디어는 `추후 제안`으로 분리 |

이 설계의 완료 조건은 PRD를 따른다. 실제 구현·통합·사용자 화면 확인은 [개발 기록](Jarvis_Pet_Development_Log.md)에서 날짜와 범위를 구분한다. 설계상의 추천·미정 항목을 승인·검증된 결정으로 오해하지 않는다.
