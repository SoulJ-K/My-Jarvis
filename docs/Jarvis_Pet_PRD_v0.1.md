# Jarvis Pet PRD v0.1

> 상태: v0.1 기획 범위 확정 / 구현 완료 여부 미확인  
> 문서 목적: 제품 방향, v0.1 요구사항·완료 기준, 이후 범위를 정의한다. 캐릭터의 세부 동작은 [Character & Growth Design](Jarvis_Pet_Character_and_Growth_Design_v0.1.md), 결정 이유와 변경 이력은 [Decision Log](Jarvis_Pet_Decision_Log_v0.1.md)를 따른다.

**상태 표시 원칙:** 아래의 `현재 반드시 구현`은 계획된 범위이며 **구현 완료**를 뜻하지 않는다. 현재 프로젝트 폴더에서 실행 가능한 앱이나 검증 결과를 확인하지 못했으므로 이 문서에는 완료된 기능을 표시하지 않는다. `구조만 고려`는 후속 구현을 막지 않기 위한 설계 고려, `미래 확장`은 v0.1 밖의 비전이다.

---

# 1. 프로젝트 한 줄 정의

**화면 속에서 태어난 한 펫과 관계를 계속 유지하며, 함께 성장해 점점 유능한 개인 AI 비서가 되는 독립형 데스크톱 펫.**

쉽게 표현하면:

> **다마고치화된 자비스**

단, 본 프로젝트의 정체성은 게임이 아니다.

**AI 비서 + 데스크톱 펫 + 감정 + 관계 + 성장**이 핵심이며, 경험치·미션·수집·미니게임 등의 게임 요소는 추후 선택적으로 추가할 수 있는 확장 기능이다.

---

# 2. Product Vision

사용자가 특정 AI 서비스의 앱을 찾아다니는 대신, 자신의 컴퓨터 안에 항상 존재하는 하나의 개인 AI 동반자를 갖게 한다.

이 절은 제품의 장기 방향이며 구현 완료 목록이 아니다. 현재 작업 범위는 17~18장의 `현재 반드시 구현 / 구조만 고려 / 미래 확장` 분류를 따른다.

펫은 단순한 챗봇 UI가 아니다.

펫은:

- 화면 안에서 실제로 움직인다.
- 감정 상태를 가진다.
- 사용자와의 관계가 변화한다.
- 사용자의 기억과 펫의 상태를 유지한다.
- 알람, 리마인더 등 실제 생활 보조 기능을 수행한다.
- AI와 직접 대화할 수 있는 인터페이스가 된다.
- 특정 AI 모델이나 서비스에 종속되지 않는다.
- 시간이 지날수록 기능적으로도 성장한다.

장기적으로는 여러 AI와 도구를 연결하여 사용자의 일을 실제로 수행하는 **개인 AI 에이전트**를 목표로 한다.

---

# 3. 핵심 제품 철학

## 3.1 큰 비전은 크게, MVP는 작게 완성한다

이 프로젝트의 장기 비전은 크지만, 처음부터 모든 기능을 구현하지 않는다.

기능의 작업 범위는 항상 다음 세 가지로 명확히 구분한다.

### 현재 반드시 구현
개인용 첫 완성품을 위해 지금 만들기로 한 범위. 이 분류는 구현 완료를 뜻하지 않으며, 실제 동작 여부는 별도로 확인해 표시한다.

### 구조만 고려
지금 기능으로 제공하지는 않지만 향후 확장을 막지 않도록 데이터 구조나 연결 경계에만 고려할 사항.

### 미래 확장
현재 개발 범위에서 제외한 기능과 장기 제품 방향.

**구현하지 않은 기능을 구현한 것처럼 표현하지 않는다.**

현재 범위는 **개인용 완성품 우선**이다. 다중 사용자 서비스, 대규모 배포, 서버 운영, 과금 체계, 고객지원은 현재 MVP에서 제외한다. 향후 확장 가능성은 구조에서만 필요한 만큼 고려한다. 포트폴리오에도 실제 구현 상태와 이 범위를 그대로 표시한다.

## 3.2 기본은 자동, 사용자 선택은 열어둔다

기본 경험은 기술 설정을 많이 요구하지 않는 자동화와 단순화다. 사용자가 체감하는 선택권은 펫의 외형·탄생·키우는 방식·관계처럼 정서적 영역에 집중한다. 다만 고급 기술 설정과 명시적 요청을 통해 AI 제공자(Provider), 모델, 사용 시점, 허용·금지 조건을 제어할 수 있어야 한다.

AI 선택의 우선순위는 **사용자 명시 제약 > 고급 설정 > 작업별 선호 > 자동 Router 판단**이다. 명시적으로 금지한 제공자나 사용 시점을 자동 선택이 뒤집어서는 안 된다. 자동 Router는 미래 확장 기능이며, 이 우선순위는 지금부터 설계 원칙으로 적용한다.

---

# 4. 제품 정체성

Jarvis Pet은 다음 중 어느 하나로 정의하지 않는다.

- 단순 데스크톱 펫
- 움직이는 ChatGPT
- AI가 붙은 다마고치
- 육성 게임

보다 정확한 정의는:

> **감정과 관계를 가진 데스크톱 AI 동반자이자, 점차 사용자를 이해하고 일을 수행할 수 있게 성장하는 개인 비서.**

태어난 펫은 성장해도 같은 개체다. 다른 캐릭터로 교체하는 방식보다 **관계의 지속성**을 우선한다. 외형이 취향에 완전히 맞지 않아도 “못생기고 못나도 내가 키운 내 펫”이라는 애착이 쌓이는 경험을 지향한다. 액세서리와 꾸미기는 이 정체성을 바꾸지 않는 범위에서만 고려한다.

# 5. 핵심 사용자 경험

아래 경험은 초기 방향과 성장 가능성을 설명한다. 실제 v0.1 범위와 완료 기준은 17~18장에서 구분하며, 펫의 세부 표현은 Character & Growth Design에 둔다.

## 초기

처음에는 펫의 비중이 높다.

예:

- 알 상태
- 부화
- 화면에서 움직임
- 잠자기
- 돌아다니기
- 클릭 반응
- 감정 표현
- 간단한 대화

사용자는 먼저 펫과 친숙해진다.

## 성장 과정 (v0.2 이후 비전 포함)

사용자와 함께 지내면서 점차 비서 기능이 늘어난다.

예:

- 간단한 대화
- 알람
- 리마인더
- 사용자 기억
- 일정 보조
- 할 일 관리
- 파일/앱 작업
- 자동화

성장은 단순한 레벨업이나 외형 변화가 아니라:

> **관계의 성장 + 개체 고유성의 발현 + 사용자 이해의 성장 + 비서 능력과 업무 수행 주도성(Agency)의 성장**

을 의미한다.

---

# 6. 성장 시스템의 기본 방향

성장 단계의 큰 흐름은 **알 → 아기 → 어린이 → 청소년 → 성체**로 확정한다. **v0.1에서 구현할 전환은 알 → 아기 한 번뿐**이다. 아기 이후의 실제 성장은 v0.2 이후로 둔다. 단계별 성격·행동·비서 능력과 성장 경험의 상세 정의는 Character & Growth Design에 둔다.

초기 버전에서는 게임처럼 보이지 않도록 한다.

따라서 기본적으로:

- XP 숫자
- 레벨 게이지
- 퀘스트
- 일일 미션
- 보상 상자

등을 전면에 노출하지 않는다.

초기에는 사용자가 다음과 같은 변화로 성장을 느끼도록 한다.

- 행동 변화
- 말투 변화
- 관계 변화
- 새로운 기능 해금
- 외형 변화
- 사용자에 대한 이해 증가
- 함께 지내며 드러나는 개체 고유의 행동과 성격
- 더 복잡한 일을 믿고 맡길 수 있는 업무 수행 능력

게임적 요소는 향후 사용자가 원할 경우 추가할 수 있다.

예:

- 경험치
- 미션
- 업적
- 꾸미기
- 수집
- 미니게임

하지만 이것들은 **Core Product가 아니라 Optional Gamification Layer**이다.

# 7. 핵심 아키텍처 개념

현재 개념 구조:

```text
Pet
 │
 ▼
Pet Brain
 ├─ State / Relationship
 ├─ Emotion System
 ├─ Memory System
 ├─ Behavior System
 ├─ Growth System
 └─ Decision (기본 반응은 로컬에서 결정)
        │ 필요할 때만
        ▼
    AIService
     ├─ 자연어 생성·복잡한 추론용 AIProvider (후보)
     └─ 작업 수행 Agent / Tool (Codex 조건부 후보)
```

이는 책임 구분을 보여주는 개념도이며 구현 완료를 뜻하지 않는다. Claude·Gemini 연결과 일반 대화용 Local LLM은 현재 구현 대상으로 확정하지 않았다.

---

# 8. Pet Brain

Pet Brain은 펫의 정체성·상태·감정·행동·관계·기억·성장과 기본 반응을 담당한다.

외부 언어 모델(LLM)이 없어도 기본 생명성과 행동을 유지해야 한다. 외부 AI는 자연어 생성, 복잡한 추론, 고난도 작업에 필요할 때만 쓴다. AI 모델이나 Codex가 펫의 두뇌 전체가 되어서는 안 된다. 일반 대화용 Local LLM 채택은 아직 후보/검토 상태다.

Pet Brain의 주요 구성:

## Emotion System

펫의 현재 감정을 관리한다. **v0.1의 최소 감정 표현은 기쁨·불편함·호기심 중심**이며, 아래는 후속 확장까지 포함한 예시다. 배고픔·졸림은 감정이 아닌 생활 상태로 별도 관리한다.

예:

- 평온
- 행복
- 심심함
- 외로움
- 놀람
- 삐짐
- 화남
- 반가움

감정은 표정뿐 아니라 행동에도 영향을 준다.

예:

```text
심심함
→ 화면을 돌아다님

외로움
→ 사용자 가까이 이동하거나 구석에 앉음

반가움
→ 사용자가 상호작용하면 가까이 다가옴
```

---

## Behavior System

실제 화면에서 나타나는 행동을 관리한다.

예:

- 걷기
- 멈추기
- 앉기
- 눕기
- 자기
- 점프
- 사용자에게 다가가기
- 화면 구석으로 이동
- 커서 바라보기
- 알람 전달 행동

AI 연결이 없어도 기본 행동은 동작해야 한다.

---

## Memory System

펫과 사용자에 관한 기억을 관리한다.

예:

- 펫 이름
- 펫 성격
- 펫의 현재 감정
- 성장 상태
- 사용자 설정
- 사용자와의 관계 상태
- 리마인더
- 대화 요약
- 장기 기억

중요 원칙:

**Memory는 AI Provider가 소유하지 않는다.**

GPT → Claude → Gemini 등 Provider가 변경돼도 펫의 기억은 유지되어야 한다.

---

## Growth System

펫의 성장 상태를 관리한다.

확정한 단계 순서:

```text
Egg
 ↓
Baby
 ↓
Child
 ↓
Teen
 ↓
Adult
```

이는 단계의 큰 방향이다. **v0.1은 Egg → Baby만 구현 대상으로 삼는다.** 이후 단계의 실제 전환 조건과 세부 표현은 아직 확정하지 않는다.

성장하면서:

- 외형
- 행동
- 말하기 능력
- 사용자 이해
- 비서 기능
- 관계와 개체 고유성
- 업무를 스스로 계획하고 수행하는 능력

등이 변화할 수 있다.

성장 과정에서 미리 정하지 않은 개체 고유성이 드러날 수 있다. 외형이 변하더라도 태어난 펫의 정체성과 쌓인 관계는 이어진다.

---

# 9. AIService

AIService는 Pet Brain이 필요할 때 호출하는 AI 관련 중간 계층이다. Pet Brain의 상태와 기본 행동은 AIService의 응답 없이도 유지된다.

개념적으로 다음 역할을 담당할 수 있다.

- 사용자 메시지 처리
- 필요한 기억 조회
- AI 요청 구성
- Prompt 구성
- 사용자 제약과 설정을 적용한 AIProvider 선택
- 작업 수행 Agent / Tool 호출 연결
- AI 응답을 Pet Brain에 전달

예:

```text
사용자
 ↓
Pet
 ↓
Pet Brain
 ↓
AIService
 ├─ AIProvider → 자연어 생성·복잡한 추론 (연결 후보)
 └─ 작업 수행 Agent / Tool → Codex 등 (조건부 후보)
```

Codex는 사용자가 시작한 로컬 코드·파일 작업을 돕는 작업 수행 Agent/도구 후보이며, 일반 대화 모델이나 Pet Brain 전체와 동일시하지 않는다. 자동 선택 기능은 장기 구상이고, 사용자의 명시적 허용·금지 조건을 항상 우선한다.

AIService는 특정 Java/Spring 문법을 의미하지 않는다.

Java/Spring으로 구현할 경우 Service Layer가 될 수도 있고, TypeScript 등 다른 기술을 사용하면 동일 역할을 하는 Class/Module로 구현할 수 있다.

---

# 10. AIProvider

AIProvider는 필요한 외부 AI 서비스 또는 로컬 모델과 통신하는 연결 경계(Adapter)다. 작업 실행을 맡는 Codex 같은 Agent/도구 연결은 AIService에서 역할을 구분한다.

목표 인터페이스 예시:

```text
AIService
 ├─ AIProvider (일반 AI 기능: 채택 방식 미정)
 └─ 작업 수행 Agent / Tool (Codex: 조건부 후속 후보)
```

필요한 경우에만 사용자가 명시적으로 선택하는 API Key 연결 Adapter를 추가한다. 구체적인 Provider와 인증 방식은 각 서비스의 공식 지원 범위를 확인한 뒤 결정한다.

초기 MVP에서 여러 Provider를 모두 구현하지 않는다. 일반 대화용 Local LLM도 확정된 구현 대상이 아니다.

원칙:

> **아키텍처는 Multi-Provider Ready, 실제 연결은 좁은 범위에서 시작한다.**

즉:

```text
후속 연결 후보 (v0.1 필수 구현 범위 밖)

작업 수행 Agent / Tool
 └─ Codex (사용자가 시작하는 로컬 코드·파일 작업에 한정)
```

처럼 좁은 범위에서 출발할 수 있다. 일반 대화의 연결 방식과 첫 AIProvider는 아직 미정이다.

추후 Provider 구현체를 추가하더라도 Pet이나 Pet Brain의 핵심 코드를 크게 변경하지 않는 구조를 목표로 한다.

---

# 11. 특정 AI 서비스 비종속성

Jarvis Pet은 ChatGPT, Codex, Claude, Gemini 등의 특정 앱 안에서만 실행되는 기능이 아니다.

**독립 실행형 데스크톱 애플리케이션**을 목표로 한다.

따라서 ChatGPT나 Codex가 종료되어도:

- 펫 이동
- 감정
- 성장 상태
- 알람
- 로컬 기억
- 기본 행동

등은 계속 동작할 수 있어야 한다.

외부 AI가 필요한 순간에만 AIService를 통해 해당 AIProvider나 작업 수행 Agent를 사용한다.

# 12. AI 계정 연결 원칙

**MVP의 중요한 제품·아키텍처 제약조건:** 기존 AI 구독을 추가 API 과금 없이 활용할 수 있다면 공식적으로 허용된 범위에서만 사용한다. 초기 사용자에게 별도의 Jarvis Pet AI 사용료를 청구하는 구조를 목표로 하지 않는다.

기본 연결 우선순위:

1. 공식 계정 로그인과 공식 로컬 클라이언트·CLI를 통한 연동
2. 공식적으로 제공되는 무료 계정 사용 범위
3. 사용자 기기에서 실행하는 로컬 모델
4. 사용자가 추가 API 비용 가능성을 알고 명시적으로 원하는 경우에만 API Key 연결

각 경로는 해당 서비스가 Jarvis Pet의 연동 방식과 사용 목적을 공식적으로 허용하고 실제로 제공하는 경우에만 사용한다. 현재 조사 결과, 기존 유료 구독의 추가 API 과금 없는 재사용에서 **조건부 후속 후보는 OpenAI의 Codex 작업 경로뿐**이다. 이것도 사용자가 시작하는 로컬 코드·파일 작업 보조에 한정하며 **v0.1 필수 구현 범위에는 넣지 않는다.** 실제 제품 연동·운영체제별 동작은 아직 검증하지 않았다.

일반 ChatGPT 대화를 Jarvis Pet에 그대로 넣어 기존 ChatGPT 구독으로 사용하는 공식 경로는 확인되지 않았다. Claude·Gemini 기존 구독을 제3자 앱이 재사용하는 방식은 현재 MVP에서 제외한다. 공식 허용 방식이 생기면 다시 검토할 수 있도록 여러 제공자에 대응 가능한 연결 경계만 유지한다. 이 판단은 `research/`의 제공자별 구독 재사용 타당성 조사에 근거하며, 출시 전 공식 조건을 재확인한다.

ChatGPT Plus/Pro, Claude Pro/Max 등 기존 구독이 제3자 앱의 API 사용권을 제공한다고 가정하지 않는다. 구독 사용량과 API 사용량·과금은 구분하며, 공식 계정·클라이언트·CLI에서 지원하는 범위만 활용한다.

공식 클라이언트의 인증 토큰을 추출하거나 내부 API를 호출·우회하는 방식은 사용하지 않는다.

# 13. Local-first & User-owned Memory

이 프로젝트의 핵심 설계 원칙 중 하나다.

## Local-first

펫의 핵심 데이터는 기본적으로 사용자의 기기에 저장한다.

예:

```text
Jarvis Pet
 └─ Local DB
      ├─ Pet
      ├─ Emotion
      ├─ Growth
      ├─ Memory
      ├─ Reminder
      ├─ Conversation Summary
      └─ Settings
```

초기 후보:

**SQLite**

정확한 저장 기술은 기술 스택 결정 후 확정한다.

---

## User-owned Memory

펫의 기억은 특정 AI 기업이나 Jarvis Pet 중앙 서버가 기본 소유자가 되어서는 안 된다.

기본 철학:

> **펫의 기억은 사용자에게 속한다.**

장점:

- Provider 교체 가능
- 서버 비용 최소화
- 개인정보 보호
- 오프라인 상태에서도 일부 기능 유지
- 사용자가 자신의 데이터를 보관 가능

---

# 14. Free-first Architecture

첫 완성품의 사용자는 개발자 본인이다. 주변 지인 사용과 배포는 이후 별도로 검토한다.

여기서 **무료**는 추가 AI API 과금을 기본값으로 요구하지 않는다는 뜻이다. 기존 유료 구독 자체가 무료라는 뜻은 아니다. 현재 구독 재사용 후보는 12장의 제한된 Codex 작업 경로뿐이다. 무료 공식 계정 범위나 로컬 모델은 검토 대상이며, 일반 대화용 Local LLM 채택은 미정이다.

이 원칙은 MVP의 중요한 제품·아키텍처 제약조건이며, AI 연결에는 12장의 우선순위를 적용한다. 공식적으로 허용되는 연결 수단이 없으면 해당 구독을 임의로 API처럼 사용하지 않는다.

특히 다음 구조를 피한다.

```text
사용자 증가
→ 중앙 서버 사용량 증가
→ 저장 비용 증가
→ AI API 비용 증가
→ 개발자 비용 증가
```

가능한 한:

```text
사용자 PC
 ├─ Pet App
 ├─ Local DB
 ├─ Pet State
 ├─ Memory
 └─ Reminder
```

형태로 해결한다.

Jarvis Pet이 사용자별 AI API 호출 비용을 자체적으로 대신 부담하는 구조는 기본 설계에서 제외한다. API Key 방식은 사용자가 명시적으로 선택할 때만 제공하며, 발생 가능한 API 비용은 연결 전에 분명히 안내한다.

향후 사용자가 여러 기기에서 펫을 사용해야 할 경우 다음 단계로 확장할 수 있다.

```text
Local Storage
 ↓
Export / Import
 ↓
Optional Backup
 ↓
Cloud Sync
```

Cloud Sync는 초기 MVP 범위가 아니다.

# 17. 개인용 v0.1 범위와 완료 기준

v0.1의 사용자 경험은 **알을 받아 키우고 → 부화를 직접 목격하고 → 태어난 아기와 며칠 함께 생활하며 기본적인 비서 기능을 쓰는 것**이다. 아래 항목은 모두 **구현 목표**이며 구현 완료로 검증된 항목은 현재 없다.

## 현재 반드시 구현

### 알부터 부화까지

- 독립 실행형 데스크톱 펫으로 평범한 타원형 알 상태에서 시작한다. 투명 배경의 화면 위 표시, 기본 움직임·대기 행동, 클릭 반응을 제공한다.
- 사용자가 알과 기본 상호작용을 할 수 있다. 부화 직전의 변화를 보여주고, 감정구슬이 먼저 나타난 뒤 부화하는 장면을 사용자가 직접 목격한다.
- 첫 교감 후 이름을 짓고, **같은 개체**가 아기 상태로 이어진다.
- 알 상태에서도 알람·타이머·리마인더의 최소 기능을 사용할 수 있다.

### 아기와 함께 생활

- 아기는 화면에서 짧게 이동하고, 커서 쫓기와 감정구슬 놀이를 한다. 배고픔·졸림에 따라 종에 관계없이 쓰는 기본 먹이 1종과 수면에 반응한다. 먹이는 드래그해서 주며, 아기는 기본 먹이를 먹는다.
- 최소한의 감정 표현과 감정구슬, 관계에 따른 행동 차이를 보여준다. 감정구슬은 감정만 표현하고 배고픔·졸림은 별도 행동으로 알린다. 감정·관계를 수치나 막대로 직접 노출하지 않는다.
- 클릭하면 짧게 대화할 수 있다. 기본 반응은 외부 AI 서비스가 없어도 작동한다. 일반 대화용 AI 제공자와 로컬 언어 모델의 채택 여부는 미정이다.
- 아기는 짧고 단순한 요청을 이해하며 필요한 정보가 빠지면 되묻는다. 알람·타이머·리마인더처럼 범위가 좁고 실행 결과를 확인할 수 있는 기본 비서 기능을 제공한다. 중요한 알림을 놓치는 식의 실수는 허용하지 않는다.
- 앱을 껐다 켜도 이름, 성장 단계, 기본 상태·관계·기억 및 등록한 알림을 복원한다. **아기 때의 상호작용·돌봄 경험을 내부적으로 기록하고 앱 재시작 뒤에도 유지하는 것은 v0.1 필수 구현**이다. 이후 성장에 활용할 준비를 하되, 구체적인 기록 항목·보존 기간·성격 반영 규칙은 후속 설계에서 정한다.
- 돌봄은 업무를 방해하거나 큰 시간·노력을 요구하지 않는다. 방치로 죽거나 사용자를 떠나지 않는다.

### v0.1 완료 판단

1. 새 사용자가 알을 받아 상호작용하고 부화 전조, 감정구슬, 부화, 첫 교감·이름 짓기를 순서대로 경험할 수 있다.
2. 아기가 기본 돌봄과 감정·관계 반응을 보이며, 며칠 사용하는 동안 상태가 이어진다. 아기 때의 상호작용·돌봄 경험이 내부에 기록되고 앱 재시작 뒤에도 유지되는지 확인한다.
3. 사용자가 짧은 대화와 알람·타이머·리마인더를 사용하고, 앱 재시작 뒤 펫과 등록한 알림을 다시 만날 수 있다.
4. 인터넷 또는 외부 AI가 없어도 기본 펫 행동과 로컬 비서 기능이 유지된다.

완료 여부는 실제 앱에서 검증한 뒤 항목별로 기록한다. 현 문서는 설계 기준이며 테스트 통과 기록이 아니다.

# 19. 장기 AI Router Vision

초기 AIProvider 선택은 단순할 수 있다.

향후에는 AIService 내부에서 AI Router로 발전할 수 있다.

예:

```text
사용자 요청
 ↓
Intent 분석
 ↓
대화 / 코딩 / 검색 / 파일 / 일정
 ↓
적합한 Provider 또는 Tool 선택
 ↓
실행
```

예:

```text
"코드 고쳐줘"
→ Coding AI

"이 문서 요약해줘"
→ Document AI

"내일 약속 알려줘"
→ Local Reminder Tool
```

모든 요청을 LLM으로 보낼 필요는 없다.

로컬에서 처리 가능한 요청은 로컬 기능으로 처리하는 것을 우선 고려한다.

자동 Router가 도입되더라도 **사용자 명시 제약 > 고급 설정 > 작업별 선호 > 자동 Router 판단** 순서를 적용한다. AI 사용 금지·제공자 제한·모델 지정·사용 시점에 대한 사용자의 명시적 조건은 자동 판단으로 바꾸지 않는다.

# 22. 차별화 방향

현재 핵심 차별점은 아직 확정하지 않았다.

이 부분은 반드시 추가 조사 및 검증한다.

검토할 후보:

### Agent Experience

대답만 하는 펫이 아니라 사용자의 실제 일을 끝내는 펫.

### Growth UX

단순 캐릭터 성장 대신:

> 사용자를 이해하는 능력 + 실제 비서 능력

이 성장하는 경험.

### Persistent Presence

사용자가 AI 앱을 찾아가는 것이 아니라 항상 데스크톱에 존재하는 인터페이스.

### Unified Identity

여러 AI를 사용하더라도 사용자는 각각의 AI와 대화한다기보다 하나의 펫과 관계를 유지한다.

### Persistent Relationship

태어난 펫을 다른 캐릭터로 교체하지 않고, 외형 취향보다 함께 살아온 관계와 애착을 우선한다.

단, 위 요소 역시 기존 프로젝트와 충분히 비교한 뒤 차별점으로 확정해야 한다.

# 29. 현재 확정 사항

다음 사항은 현재 프로젝트의 핵심 결정으로 취급한다.

### 제품

- 게임이 아니다.
- 성장하는 AI Desktop Pet이다.
- v0.1의 실제 성장 범위는 알 → 아기이며, 아기 이후 실제 성장 전환은 v0.2 이후다.
- 현재 범위는 개인용 완성품 우선이며, 다중 사용자 서비스·대규모 배포·서버 운영·과금·고객지원은 MVP에서 제외한다.
- 기본 경험은 자동화·단순화하되, 펫과 관계에 관한 선택권을 중심에 두고 고급 AI 설정도 열어둔다.
- 태어난 펫의 정체성은 교체하지 않고, 관계의 지속성을 외형 선택권보다 우선한다.
- 성장은 외형뿐 아니라 관계·개체성·사용자 이해·비서 능력과 업무 수행 주도성의 성숙이다.
- 성장으로 넓어지는 것은 이해·제안·수행 능력이다. 실제 작업 실행 권한은 성장 단계와 별개로 사용자가 허용한 범위에서만 주어진다.
- 전체 성장 단계의 큰 흐름은 알 → 아기 → 어린이 → 청소년 → 성체다. 성장 장면은 사용자가 직접 볼 때 진행한다.
- 최종 방향은 개인 AI Agent / Jarvis다.

### Architecture

- Pet Brain과 AI Provider를 분리한다.
- 펫의 정체성·상태·감정·행동·관계·기억·성장·기본 반응은 외부 LLM 없이 유지한다.
- Codex는 Pet Brain 전체가 아니라 작업 수행 Agent/도구 후보다.
- 혼합형 구조를 지향하되 일반 대화용 Local LLM은 미정이다.
- AIProvider 교체 가능성을 고려한다.
- Multi AI는 처음부터 전부 구현하지 않는다.
- AI 선택은 사용자 명시 제약 > 고급 설정 > 작업별 선호 > 자동 Router 판단 순서다.
- 공식적으로 허용된 연결만 사용하며, 기존 구독 재사용은 제한된 Codex 작업 경로만 조건부 후속 후보로 둔다. v0.1 필수 구현은 아니다.

### Data

- Local-first.
- User-owned Memory.
- 초기에는 자체 Cloud 서버를 사용하지 않는 방향.
- 데이터는 특정 AI Provider에 종속시키지 않는다.

### Cost

- 첫 완성품은 개인용이다. 지인 사용이나 배포는 미래에 별도로 검토한다.
- 무료 원칙은 추가 AI API 과금을 기본값으로 요구하지 않는다는 뜻이다.
- 연결 우선순위는 공식 계정/클라이언트·CLI → 무료 공식 계정 범위 → 로컬 모델 → 사용자가 명시적으로 선택한 API Key다.
- 일반 ChatGPT 구독 대화의 임베드 경로는 확인되지 않았고, Claude·Gemini 구독 재사용은 MVP에서 보류한다.
- 기존 구독을 제3자 API 사용권으로 간주하거나 인증 토큰 추출·내부 API 우회를 하지 않는다.
- Jarvis Pet이 사용자별 AI API 비용을 대신 부담하거나 사용자 수에 따라 지속적인 API/Storage 비용을 부담하는 구조는 피한다.

### Development

- MVP는 개인용 완성품으로 작게 완성한다.
- 모든 기능·비전은 `현재 반드시 구현 / 구조만 고려 / 미래 확장`으로 구분하고, 실제 구현 여부는 따로 표시한다.
- 포트폴리오는 완성 → 실제 사용·검증 → 다음 확장 순서로 작성한다.
- 멀티펫 가능성을 고려해 `petId` 사용 가능성을 염두에 둔다.

# 33. 다른 ChatGPT/Codex 세션에 전달할 지침

이 문서를 받은 새로운 세션은 다음 원칙을 유지한다.

1. 프로젝트를 게임으로 해석하지 않는다.
2. 사용자가 명시하지 않은 기능을 MVP에 임의로 추가하지 않는다.
3. `현재 반드시 구현 / 구조만 고려 / 미래 확장`과 실제 구현 완료 여부를 구분한다.
4. Local-first 및 User-owned Memory 원칙을 유지한다.
5. 특정 AI Provider에 종속되는 설계를 기본값으로 선택하지 않는다.
6. Multi AI 전체 구현을 초기 목표로 삼지 않는다.
7. 공식적으로 허용된 연결만 구현하고, Provider 교체 가능한 구조를 유지한다.
8. 펫의 감정/행동/기억을 LLM 자체에 전적으로 맡기지 않는다.
9. 기존 구독 재사용은 사용자 시작 로컬 코드·파일 작업용 Codex만 조건부 후보로 두고, 일반 ChatGPT 대화나 Claude·Gemini 구독 재사용을 MVP에 약속하지 않는다.
10. 태어난 펫의 정체성을 교체하지 않고, 관계의 지속성과 개체 고유성을 유지한다. v0.1의 성장 전환은 알 → 아기까지만 구현한다.
11. 사용자가 아이디어를 제시하면 `현재 반드시 구현 / 구조만 고려 / 미래 확장`으로 분류해서 검토한다.
12. 기존 오픈소스에 이미 존재하는 기능을 무조건 차별점이라고 주장하지 않는다.
13. 아직 결정되지 않은 사항은 임의로 확정하기보다 PRD의 Open Questions로 관리한다.
14. 기본은 자동화하되 사용자 명시 제약을 최우선으로 적용하고, 고급 설정을 열어둔다.
15. 포트폴리오는 실제 완성 → 사용·검증 → 다음 확장 순서로 제시한다.

# 34. 현재 프로젝트의 핵심 문장

> **Jarvis Pet은 AI가 붙은 캐릭터가 아니라, 감정과 기억을 가진 하나의 독립적인 존재가 여러 AI와 도구를 활용해 사용자의 곁에서 점점 유능한 개인 비서로 성장하는 데스크톱 AI 동반자다.**

그리고 개발 전략은:

> **큰 비전은 크게 잡고, MVP는 작게 완성한다.**
