# ADR-001. 같은 알을 유지하는 SQLite 저장

- 날짜: 2026-09-26
- 상태: 사용자 선택 확정(D-039). 아래 v1·v2 당시 검사 기록과 후속 v3 구성요소 검사를 구분한다. 배포용 설치 앱·실제 사용자 DB 변환은 미검증.
- 관련 기준: [Decision Log D-006·D-039](Jarvis_Pet_Decision_Log_v0.1.md), [기술 설계 단계 2·3](Jarvis_Pet_Technical_Design_v0.1.md)

ADR은 기술 선택의 이유·대안·제약을 남기는 기록이다. D-006이 SQLite 선택 시 별도 ADR을 요구하므로 이 문서를 만들었다. Decision Log에는 선택과 결과의 요약을 두고, 여기에는 저장 형식·실패 처리·호환성 근거를 둔다. 기존 Decision Log만으로 대체하지 않았다. 문서 이름·목적·내용은 구현 전에 사용자에게 안내했다.

## 결정과 대안

SQLite와 Electron에 포함된 `node:sqlite`의 `DatabaseSync`를 사용한다. SQLite는 별도 서버 없이 기기 안의 파일에 표 형태로 정보를 저장하는 도구다. JSON은 이번 알 정보만 저장하기에는 충분하지만, 이후 상태와 경험을 한 묶음으로 기록할 때 직접 구현해야 할 부분이 늘어난다. SQLite의 트랜잭션은 여러 변경을 전부 저장하거나 전부 취소하는 방식으로, 일부 기록만 남는 일을 줄인다.

외부 SQLite 연결 패키지는 추가하지 않았다. 현재 Electron 바이너리에서 내장 모듈이 실제로 동작하므로 별도 네이티브 모듈 설치·재빌드 부담을 늘릴 이유가 없다. 동기 방식은 한 알의 시작 시점에만 작은 읽기·쓰기를 한다. 이후 기록량이 늘면 처리 시간을 측정한 뒤 별도 실행 영역을 판단한다.

## 최초 저장 형식과 실행 순서 — v1 당시 기록

- 위치: `app.getPath('userData')/pet/pet.sqlite3`. 프로젝트, GitHub, 화면의 브라우저 저장소와 분리한다. 테스트는 매번 운영체제 임시 폴더를 만든다.
- 형식: `application_id = 0x4a505431`, `user_version = 1`. `pet` 표에 `singleton = 1`, UUID v4 `pet_id`, UTC ISO 문자열 `created_at`, `stage = egg` 한 행만 둔다. 알 생성 시각은 부화 시각이 아니다.
- 아직 없는 이름·성격·아기 경험·예약·임시 반응·화면 위치는 저장하지 않는다. 실제 아기 경험 수집은 이후 필수 단계로 남아 있다.
- 앱은 중복 실행 잠금을 먼저 확보하고, 저장 성공 후에만 알 창을 만든다. 추가 실행은 저장 코드에 들어가기 전에 종료한다.
- 새 파일만 배타적으로 생성한다. POSIX 환경에서는 파일 권한 `0600`, 새 데이터 폴더 `0700`을 사용한다. 암호화는 아니다.
- SQLite `DELETE` 저널과 `synchronous = FULL` 설정에서 표·형식 번호·알 한 행을 같은 트랜잭션으로 만든다. 저장 성공 전에 알을 표시하지 않는다.
- 재실행은 읽기 전용으로 열어 `quick_check`, 앱 식별값, 형식 번호, 행 개수와 값 형태를 검사한다. 현재 단계에는 이후 상태 변경·저장 작업이 없으므로 실행 중 DB 연결을 유지하지 않는다.
- 화면에는 검증된 `egg:snapshot` 읽기 요청만 추가한다. 발신 창·최상위 프레임·로컬 페이지 주소·인자 개수를 확인한다. 저장 경로·SQL·쓰기·일반 IPC 호출은 화면에 노출하지 않는다.

## 실패와 복구 범위

손상, 빈 기존 파일, 다른 형식, 알 행 누락, 권한 문제, 저장 실패는 새 알 생성으로 숨기지 않는다. 기존 파일과 SQLite 부속 파일을 삭제하지 않고 실행을 중단한다. 정상 앱에서는 오류 코드와 보존 안내를 운영체제 대화상자로 보여준다. 원문 데이터·SQLite 내부 오류를 로그에 출력하지 않는다.

최초 저장 중 중단되어 빈 파일이나 불완전한 파일이 남은 경우도 자동 초기화하지 않는다. 이 경우 사람이 파일·권한·사본을 확인하는 복구가 필요하다. 자동 복구·주기 백업·이전 형식 변환은 이번에 구현하지 않았다. 이후 D-042에서 아래 v1→v2 변환에 원본 사본 보존과 검사를 추가했다. 그 외 형식 변환은 별도 절차와 검사가 필요하다. 기존 형식의 자료를 조용히 새 형식으로 덮어쓰지 않는다.

## 검증과 한계

macOS 26.6.2 / arm64, Electron 44.4.5, 내장 Node.js 24.21.0, SQLite 3.53.4에서 검사했다. 내장 모듈 조회뿐 아니라 실제 Electron 메인 영역에서 저장·복원하고 숨긴 화면이 동일 식별자를 받는 것까지 확인했다.

- `npm run typecheck`, `npm test` 통과. 저장 검사 8개, 실제 앱 시작 검사 5개와 화면·요청 경계 검사를 포함한다.
- 새 저장소, 별도 프로세스 재실행, 단일 알 제약, 중복 앱 실행, 손상·빈 파일·미지원 형식·행 누락·잘못된 값 보존을 검사했다.
- 실제 파일 권한 거부와 경로 충돌, 삽입 실패 주입에 따른 취소, 최초 저장 중 프로세스 강제 종료, 실행 중 강제 종료 후 복원을 확인했다.
- 검사 자료는 임시 데이터이며 사용자의 실제 알과 원본 실행 앱은 조작하지 않았다. 잘못된 요청 거절 시 Electron이 기록하는 예상 오류 로그와 검사 실패는 구분한다.
- 실제 디스크 전체 소진·정전, 정상 화면의 오류 대화상자 사용자 확인, 설치용 `.app`, Windows, 다중 모니터, 장시간 보존은 미검증이다. 아기 상태·경험의 동시 저장도 아직 구현·검사하지 않았다.

## 공식 근거

- [Node.js SQLite API](https://nodejs.org/api/sqlite.html): `DatabaseSync`, 읽기 전용 옵션, 확장 기능 차단, 동기 실행. 현재 공식 페이지의 버전과 앱의 내장 버전은 다르므로 채택한 API만 실제 앱에서도 검사했다.
- [Electron 앱 데이터 위치](https://www.electronjs.org/docs/latest/api/app#appgetpathname): 앱 전용 자료는 `userData`의 별도 하위 폴더 사용.
- [Electron 중복 실행 잠금](https://www.electronjs.org/docs/latest/api/app#apprequestsingleinstancelockadditionaldata): 저장 접근 전 단일 실행 확보.
- [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security): 제한된 연결과 요청 발신자 검증.
- [SQLite 원자적 저장](https://www.sqlite.org/atomiccommit.html): 트랜잭션과 저널의 역할. 문서의 보장 전체를 현재 테스트에서 확인한 것은 아니다.


## D-042 후속: 알 돌봄·경과 시간 — v2 작업 브랜치

최초 v1의 식별 표는 그대로 두고 `egg_life`, `egg_care`를 추가한다. [D-042](Jarvis_Pet_Decision_Log_v0.1.md)에 최소 필드·시간 해석·미구현 범위를 기록했다. 일단 v2로 변환한 저장소는 v1 전용 이전 앱으로 열지 않는다. 실제 사용자 데이터 변환은 이번 검사에 포함하지 않았다.

`loadOrCreateEgg`는 v1/v2의 식별자를 읽기 전용으로 검증한다. `openEggLife`는 단일 실행 잠금 아래 쓰기 연결을 열고, v1이면 변경 전 `pet.sqlite3.v1-backup`을 배타적으로 복사한다. 기존 사본이 원본 v1과 일치하면 재시도를 허용하며, 다른 파일·심볼릭 링크면 보존하고 중단한다. 표 추가·초기 경과·형식 번호 2를 한 묶음으로 저장한다. 사본은 자동 삭제하지 않으며 프로젝트·GitHub 업로드 대상도 아니다. 실패 시 v1 원본과 사본을 보존한다. 사본을 자동 복원하는 기능은 없다.

실행 중에는 작은 동기 쓰기 연결을 유지한다. 돌봄 사건과 해당 경과는 함께 저장하며 커밋(저장 확정) 뒤에만 성공 반응을 보인다. 주기 경과 저장 실패는 오류 코드로 알리고, 돌봄 저장 실패는 화면에서 재시도를 안내한다. 강제 종료 직전 아직 저장하지 않은 경과는 다음 시작 시 벽시계 차이로 반영한다. 저장된 사건은 재시작 뒤 남고 반응 애니메이션은 대기에서 시작한다.

기존 v1 검사에 더해 원본 사본 동일성, 변환 취소, 기존 사본 충돌 보존, 가짜 시계 복원, 사건 삽입 실패 시 상태 동시 취소, 실제 앱 쓰다듬기·실패 안내·재시작·강제 종료를 검사했다. 실제 디스크 소진·정전·타 프로세스의 비협조적인 DB 수정·장기 저장량·백업 복원 UX는 미검증이다. 검사 수와 환경은 기술 설계 단계 4의 최신 결과를 따른다.

## 부화 진행을 위한 v3 확장 — 2026-09-26

부화 구성요소는 기존 `pet.sqlite3`의 펫 식별자와 돌봄 기록을 그대로 유지하고, `pet.stage`가 알·아기를 표현하도록 제약을 넓힌다. 이름과 연출 완료 지점은 같은 파일에 저장한다. 별도 부화 파일을 기준으로 삼으면 같은 펫의 단계가 두 파일에서 달라질 수 있어 채택하지 않았다. `pet` 표의 단계·이름과 `lifecycle` 표의 완료 지점을 한 트랜잭션으로 변경하고 읽을 때 서로 일치하는지 검사한다.

v1 자료는 검증된 v1→v2 변환을 먼저 통과한다. v2→v3 전에 원본을 `pet.sqlite3.v2-backup`으로 배타적으로 복사하고, 다른 내용의 기존 사본이 있으면 덮어쓰지 않고 멈춘다. 표 재구성·연출 초기 상태·형식 번호 3을 한 트랜잭션으로 반영한다. 실패하면 v2 본문과 사본을 보존한다. **v3 파일은 이전 v2 앱에서 열 수 없다.** 자동 이전 버전 복귀나 사본 복원 화면은 아직 없다.

임시 저장소에서 v1→v2→v3의 동일 `petId`·돌봄 사건 유지, 모든 연출 지점의 별도 프로세스 재시작, 이름·단계 쓰기 실패 시 동시 취소, 백업 충돌·손상 파일 보존을 검사했다. 실제 사용자의 펫 DB는 변환하지 않았다. 이 형식은 아기의 실제 생활·경험 기록을 아직 포함하지 않으며, 제품의 부화 자동 발동·실기기 잠금·절전도 검증하지 않았다.
