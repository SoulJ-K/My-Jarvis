> 사용자 선택: **Electron + TypeScript로 macOS에서 첫 기술 검증을 진행한다.** 프레임워크 최종 채택은 투명 창·클릭 통과·입력 방해 여부를 실제 기기에서 확인한 뒤 판단한다.  
> 문서 목적: v0.1을 어떻게 작게 구현하고 검증할지 설명한다. 이 문서 작성과 작업 폴더 준비는 앱 구현 완료를 뜻하지 않는다.

## 문서 기준과 상태 읽는 법

기준 문서는 [README](../README.md), [PRD](Jarvis_Pet_PRD_v0.1.md), [Decision Log](Jarvis_Pet_Decision_Log_v0.1.md), [Character & Growth Design](Jarvis_Pet_Character_and_Growth_Design_v0.1.md)이다. 기능 범위와 완료 판단은 PRD 17~18장, 행동 표현은 Character & Growth Design, 결정 이유와 변경 이력은 Decision Log를 따른다. 이 설계안이 기존 요구사항을 바꾸지는 않는다.

| 상태 | 이 문서에서의 뜻 |
|---|---|
| 실제 구현 완료 | 코드를 작성하고 명시한 범위에서 동작까지 검증한 상태. **임시 알 표시·클릭 반응·드래그 이동을 사용자 실기기에서 확인했다. 단계 1 전체나 v0.1 완료는 아님.** |
| 설계만 완료 | 설명이나 계획을 문서로 정리한 상태. 사용자 승인이나 실제 동작 검증을 뜻하지 않는다. 본 문서는 검토용 초안이다. |
| 구조만 고려 | 나중의 연결을 막지 않도록 책임과 데이터 경계만 정리한 상태. 동작 코드·화면을 미리 만들 필요는 없다. |
| 미래 확장 | v0.1에서 구현하지 않는 범위. 별도 결정 후 검토한다. |
| 추천·미정 | 아직 사용자와 결정하거나 실기기에서 검증해야 하는 기술 선택 또는 세부값. |

v0.1은 **알 → 부화 → 아기 생활**까지다. 어린이·청소년·성체 전환, 복잡한 작업 수행, 여러 AI 연결은 현재 구현하지 않는다. 아기 경험 기록은 필수이고, 이를 성격과 이후 성장에 반영하는 구체 규칙은 후속 설계다. LLM은 문장을 생성·해석하는 언어 모델을 뜻하며, **Pet Brain의 기본 생활에는 외부·로컬 LLM 모두 필요하지 않아야 한다.**

이후 중요한 기술 선택·범위 변경·구조 변경·구현 단계 완료를 이 문서와 관련 기준 문서에 반영한다. 작은 코드 변경마다 문서를 늘리거나 `final`, `new`, 새 버전 파일을 만들지 않는다. 새 문서가 필요하면 이름·이유·담을 내용을 먼저 제안한다.

병렬로 진행할 수 있는 작업은 역할과 변경 대상 파일을 먼저 제안하고 사용자 확인 후 에이전트에 나눠 맡긴다. 담당 파일을 분리하고 최종 결과는 통합 검수한다.

## 1. 추천 기술 스택

기술 스택은 **앱을 만들 때 함께 사용하는 도구들의 조합**이다. Jarvis Pet에는 데스크톱 창, 화면 표현, 펫 규칙, 저장, 검사를 맡을 도구가 필요하다.

### 1.1 데스크톱 앱 후보 비교

| 후보 | 무엇인가 | Jarvis Pet에 맞는 점 | 부담·차이 | 현재 판단 |
|---|---|---|---|---|
| Electron | 웹 화면 기술을 데스크톱 창 안에서 실행하는 도구 | 창·트레이·알림을 연결하고 화면과 핵심 로직을 TypeScript로 작성할 수 있다. | 브라우저 실행 환경을 포함하므로 앱 크기와 상시 메모리 사용을 측정해야 한다. | **사용자가 첫 검증 경로로 선택. 최종 채택은 검증 후.** |
| Tauri | 운영체제의 웹 화면 엔진과 Rust 기반 앱 관리 부분을 결합하는 도구 | 설치 크기와 자원 사용을 줄일 대안으로 검토할 가치가 있다. | Rust와 화면 기술을 함께 다루며, 운영체제별 창 제약을 확인해야 한다. | Electron 검증 결과에 따라 재검토 가능한 후보 |
| Electron + Java/Spring Boot | 화면과 별도로 Java 프로그램을 실행해 핵심 처리를 맡기는 구성 | 사용자의 기존 Java/Spring 경험을 활용하기 좋다. | 두 프로그램의 실행·종료·통신·묶음을 관리해야 한다. | v0.1에서는 추가하지 않는 안 추천 |

Electron은 앱 관리 영역과 화면 영역을 나누고 창·메뉴·트레이 같은 데스크톱 기능을 제공한다. 이 프로젝트에서는 먼저 창 조작 가능성을 확인하고, 통과하면 한 언어로 작은 제품을 완성하는 방향을 추천한다. [Electron 실행 구조](https://www.electronjs.org/docs/latest/tutorial/process-model)

Tauri의 macOS 투명 창은 공식 문서상 `macOSPrivateApi` 설정이 필요한 제약이 있다. 비공개 운영체제 기능 사용으로 Mac App Store 등록에 제한이 생길 수 있으므로, 경량성만 보고 선택하지 않는다. 현재 개인용 v0.1에 앱스토어 배포를 추가한다는 뜻은 아니다. [Tauri 창 설정](https://v2.tauri.app/reference/config/#transparent)

첫 검증 환경은 macOS로 정했다. **Windows 지원 목표는 유지하지만, macOS 검증 성공을 Windows 검증 성공으로 표현하지 않는다.** 선택 이유와 제한은 Decision Log D-035를 따른다.

### 1.2 함께 사용할 도구 제안

첫 검증용 Electron 44.4.5와 TypeScript 7.0.2는 프로젝트에 설치했다. 아래의 다른 도구와 버전은 아직 미확정이다. 추천안이 곧 설치·구현 승인은 아니다.

| 영역 | 추천 도구 | 쉬운 설명과 필요한 이유 | 다른 선택과의 차이 |
|---|---|---|---|
| 개발 언어 | TypeScript | 데이터 모양을 검사하는 JavaScript다. 예를 들어 알림 시간 자리에 잘못된 값이 들어가는 실수를 개발 중 줄인다. | 화면과 핵심 로직에 같은 언어를 사용한다. 단, 실행 중 입력 검증도 따로 필요하다. |
| 입력창·말풍선·알림 카드 | React | 화면을 작은 부품으로 나누는 도구다. 입력창 상태와 알림 결과를 따로 관리하기 좋다. | 순수 JavaScript도 가능하지만 화면 상태가 늘 때 분리를 유지하기 쉽다는 판단이다. |
| 개발·화면 코드 묶기 | Vite | 개발 중 화면을 실행하고 앱에 넣을 파일로 묶는 도구다. | 직접 묶는 설정을 만드는 일을 줄인다. Electron 구성 도구와의 조합은 확인해야 한다. |
| 로컬 저장 | SQLite | 별도 서버 없이 기기 안 파일에 표 형태의 데이터를 저장하는 데이터베이스다. | 설정 파일만 쓰는 것보다 상태·경험·예약의 연결과 일관성을 다루기 좋다. |
| 펫 표현 | 2D 이미지 애니메이션 + CSS | 여러 그림을 순서대로 보여주고 위치·크기를 바꾼다. | 게임 엔진·3D보다 한 마리의 아기와 소수 동작을 작게 시작하기 적합하다. |
| 규칙 자동 검사 | Vitest | 정해진 입력에 예상한 결과가 나오는지 반복 검사하는 도구다. | 시간·상태 규칙을 실제로 오래 기다리지 않고 확인한다. |
| 앱 조작 자동 검사 | Playwright 후보 | 입력·클릭·화면 흐름을 자동으로 따라 하는 도구다. | 운영체제 투명 창·알림은 실기기 확인을 함께 해야 한다. |
| 실행 앱 만들기 | Electron Forge 후보 | 개발 파일들을 실제 실행 가능한 앱으로 묶는 도구다. | 개발 모드에서만 되는 기능을 놓치지 않도록 초기부터 포장 결과도 확인한다. |

현재는 Java 서버, 게임 엔진, 일반 대화용 로컬 모델을 기본 구성에 추가하지 않는다. 필요한 모듈을 TypeScript 파일로 나누는 것으로 시작한다. **모듈은 관련 기능을 묶은 코드 단위**이며, 별도 서버나 프로그램을 뜻하지 않는다.

### 1.3 첫 검증용 개발 도구 설치 — 2026-09-26

**프로젝트별 설치는 해당 프로젝트가 사용할 도구와 버전을 폴더별로 따로 정하는 방식**이다. 다른 프로젝트가 새 버전으로 바뀌어도 Jarvis Pet의 도구가 함께 바뀌지 않도록 전역 설치 대신 이 방식을 사용한다. Node.js와 npm은 기존 설치를 사용하며 시스템 설정은 변경하지 않았다.

- Electron **44.4.5**, TypeScript **7.0.2**를 `package.json`의 `devDependencies`에 정확한 버전으로 지정했다. 공개 npm registry의 `latest` 안정판과 Node.js 요구 조건을 조회한 뒤 선택했다.
- Electron의 Node.js 요구 조건은 `>=22.12.0`, TypeScript는 `>=16.20.0`으로 현재 Node.js **24.21.0**이 둘 다 충족한다. 설치 도구는 npm **11.19.0**이다.
- `package-lock.json`은 연관 패키지까지 버전을 기록하는 잠금 파일이다. 두 파일을 함께 Git 기록 대상으로 삼고, 내려받은 `node_modules/`는 기존 제외 규칙을 유지한다.
- macOS **26.6.2 / arm64**에서 설치 목록, TypeScript 버전 명령, Electron 실제 바이너리 버전 명령을 확인했다. 설치 시 npm 취약점 조회 결과는 **0개**였다. 버전 출력 성공이 앱 화면·기능의 호환성이나 안전성 전체를 검증한 것은 아니다.
- 도구 설치 직후에는 앱 코드가 없었으며, 같은 날 사용자의 후속 승인으로 단계 1의 임시 알 앱과 실행·검사 명령을 추가했다. React·Vite·SQLite·Forge 등의 추가 설치와 채택은 미정이다. Electron 최종 채택 판단은 단계 1의 남은 창 검증 후에 한다.

선택 이유와 범위는 Decision Log **D-037**에 남긴다. 패키지 조회 출처: [Electron 44.4.5](https://registry.npmjs.org/electron/44.4.5), [TypeScript 7.0.2](https://registry.npmjs.org/typescript/7.0.2).

## 2. 전체 아키텍처

아키텍처는 **각 부분이 무엇을 책임지고 서로 어떻게 연결되는지 정한 설계**다. 화면이나 AI가 바뀌어도 같은 펫의 기억과 생활을 유지하기 위해 필요하다.

### 2.1 전체 흐름과 실행 위치

```text
사용자
  ↓ 클릭·드래그·짧은 문장
화면: 펫 / 입력창 / 알림 표시
  ↓ 제한된 요청 창구
앱 진행 관리자: 입력 검증 / 처리 순서 / 저장 조율
  ├─ Pet Brain: 생애·생활·감정·관계·행동·경험 정책
  ├─ 기본 비서: 요청 해석·알람·타이머·리마인더
  ├─ 저장 담당 → SQLite 후보
  ├─ 운영체제 창·알림 담당
  └─ [구조만 고려] AIService
         ├─ AIProvider: 대화·추론 연결
         └─ 작업 도구 연결: Codex 등, 권한 확인 후 사용
```

**프로세스는 프로그램이 분리되어 실행되는 단위**다. Electron에서는 앱을 관리하는 메인 프로세스와 화면을 그리는 렌더러 프로세스를 구분한다.

| 영역 | 담당 | 맡기지 않는 일 |
|---|---|---|
| 메인 프로세스 | Pet Brain, 시간 관리, 저장, 창 관리, 요청 검증 | 매 장면의 그림 계산 |
| 렌더러 | 펫·구슬·먹이 그리기, 입력창과 알림 표시 | 데이터베이스 직접 수정, 임의 파일·프로그램 실행 |
| Preload | 화면에 필요한 요청만 제공하는 연결 창구 | 운영체제 기능 전체를 화면에 공개 |

**IPC는 분리된 실행 영역끼리 메시지를 전달하는 방식**이다. 접수창구에 신청서를 전달하는 것과 비슷하다. 화면이 “타이머 등록”을 요청하면 메인 영역이 검사하고 저장한 결과를 반환한다. 화면이 직접 저장 파일을 고치지 않는다.

Pet Brain의 현재 원본은 메인 영역에서 관리하고 중요한 변경을 저장한다. 화면은 사용자에게 표현할 정보만 받는다. 화면이 닫히거나 다시 만들어져도 펫과 예약을 복원할 수 있게 하기 위해서다. 요청에는 식별자를 붙여 같은 등록 버튼이 중복 처리되는 일을 막는 안을 추천한다. 제한된 연결 구조는 [Electron 실행 구조](https://www.electronjs.org/docs/latest/tutorial/process-model)를 참고한다.

초기에는 가벼운 규칙과 작은 저장을 한 앱 안에서 처리한다. 느린 연산이나 대량 저장이 실제로 발견되면 별도 작업 영역을 검토하되, 지금부터 분산 서버나 복잡한 메시지 시스템을 만들지 않는다.

### 2.2 Pet Brain의 책임과 내부 모듈

Pet Brain은 **현재 상태와 발생한 일을 받아 다음 상태와 반응을 결정하는 로컬 규칙**이다.

예: 졸린 아기에게 먹이를 준다 → 배고픔을 완화한다 → 짧게 만족한다 → 식사 경험을 기록한다 → 원래 졸렸으므로 쉬거나 잠든다.

| 모듈 | 책임 | v0.1 범위 |
|---|---|---|
| 생애 흐름 | 알·부화·첫 교감·이름 짓기 진행 | 알 → 아기 한 번 |
| 생활 상태 | 배고픔·졸림·수면과 시간 경과 | 두 가지 필요와 자연스러운 복귀 |
| 감정 | 기쁨·불편함·호기심의 발생과 진정 | 최소 감정 표현 |
| 관계 | 익숙함·신뢰·잠시 거리두기와 회복 | 수치 비노출, 행동 차이 |
| 행동 선택 | 현재 가능한 행동 중 하나 선택 | 쉬기·짧은 이동·커서 쫓기·구슬 놀이 |
| 기억·경험 정책 | 무엇을 기억으로 남길지 판단 | 이름·기질·상태·관계, 아기 돌봄 경험 |

Pet Brain은 파일에 직접 쓰거나 그림을 재생하거나 외부 AI를 기다리지 않는다. 다음 상태, 남길 경험, 표현할 행동을 반환하고 앱 진행 관리자가 저장과 화면 전달을 조율한다. 처리는 순서대로 하여 먹이 주기와 타이머 갱신처럼 동시에 들어온 요청이 상태를 덮어쓰지 않게 한다.

행동 선택은 현재 상태와 사건의 우선순위 규칙으로 시작한다. 복잡한 계획 시스템이나 성격 학습 엔진은 만들지 않는다. **펫이 졸리거나 잠시 거리를 두더라도 기본 알림의 정확성을 낮추지 않는다.** 알림 전달은 별도 비서 담당이 책임진다.

### 2.3 알 / 부화 / 아기 상태 흐름

**상태 머신은 현재 단계와 다음 단계로 넘어갈 조건을 적은 규칙표**다. 신호등처럼 허용된 순서로 진행한다. 구슬보다 아기가 먼저 나오거나 재시작 때문에 이름 짓기를 건너뛰지 않도록 사용한다.

```text
알 생활
  ↓ 시간 기본 조건 + 돌봄의 제한적 영향
부화 준비 완료, 사용자 기다림
  ↓ 사용자가 볼 수 있는 상황에서 시작
부화 전조 → 알에 금 → 감정구슬 등장 → 껍질 갈라짐
  ↓
아기 등장·주변 살피기 → 첫 교감 → 이름 짓기
  ↓
아기 생활: 쉬기 / 짧은 이동 / 식사 / 수면 / 두 가지 놀이
```

성장 단계와 연출 진행 지점을 따로 저장한다. 알부터 사용한 `petId`라는 식별자는 부화 후에도 같다. 구슬 역시 새로 뽑는 장식이 아니라 같은 아기의 물건으로 유지한다.

- 부화는 시간에 돌봄을 제한적으로 반영한다. 돌봄 횟수를 필수 통과 조건으로 만들지 않는다. 시간·영향량은 미정이다.
- 사용자가 없을 때 조건이 충족되면 준비 상태로 기다린다. 잠금 해제·최근 입력은 사용자가 실제로 보는지의 보조 신호일 뿐이다.
- 전조 뒤 클릭 등 명시적 상호작용을 받고 연출을 시작하는 안을 추천한다. 정확한 시작 방식은 결정이 필요하다.
- 완료한 연출 지점을 저장한다. 중간 종료 시 마지막 완료 지점 이후를 다시 보여주며 아기·이름·구슬을 중복 생성하지 않는다.
- 절전·잠금·화면 사라짐 때 중요한 연출을 보류하는 안을 추천한다. 사용자가 못 본 구간을 완료 처리하지 않도록 재개 규칙을 검증한다.
- 이름을 저장하기 전에는 이름 짓기 단계가 끝난 것으로 처리하지 않는다. 이름 길이·공백 처리 등의 기준은 구현 전에 정한다.
- 아기 이후 성장 조건이나 어린이 연출은 v0.1에 만들지 않는다.

### 2.4 펫 렌더링과 애니메이션

**렌더링은 상태와 그림 자료를 실제 화면으로 그리는 작업**이다. Pet Brain이 “기쁨 표현”을 결정하면 화면이 가능한 몸짓으로 보여준다. 규칙과 그림을 나누면 같은 펫의 표현을 바꿔도 관계 계산을 고치지 않아도 된다.

**스프라이트 시트는 여러 동작 그림을 한 이미지에 모은 것**이다. 작은 만화책을 넘기듯 순서대로 보여준다. 이미지와 함께 동작별 위치·속도·반복 여부를 적은 설명 파일을 두는 안을 추천한다.

- 펫 본체·감정구슬·먹이를 나눠 그린다. 손이나 꼬리가 없는 외형에 해당 동작을 강요하지 않는다.
- 구슬은 놀이·감정 표현에 필요한 때 나타난다. 배고픔·졸림 표시기로 사용하지 않는다. 전체 색상표는 미정이다.
- 그림을 자주 바꾸는 주기와 생활 상태 계산·저장 주기를 분리한다. 화면 한 장을 그릴 때마다 저장하지 않는다.
- 작은 투명 펫 창과 입력 시 열리는 대화 창을 나누는 안을 추천한다. 평소 다른 앱의 키보드 입력을 빼앗지 않게 한다.
- 화면에서 클릭을 받을 부분을 펫·먹이 등 필요한 영역으로 제한한다. 빈 공간을 클릭하면 뒤의 앱으로 전달되어야 한다.
- 모니터 분리·화면 배율 변경 시 펫이 화면 밖에 남지 않도록 현재 화면의 안전한 영역으로 되돌린다.

투명 창의 빈 공간이 자동으로 클릭을 통과하는 것은 아니다. 펫 클릭·먹이 드래그·뒤 앱 클릭이 함께 성립하는지를 첫 시제품에서 확인해야 한다. [Electron 투명 창 제약](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles#limitations)

### 2.5 입력창과 간단한 대화 UX

**UX는 사용자가 기능을 찾고 사용하고 결과를 이해하는 전체 경험**이다. 아기는 짧게 말하되 비서 기능의 결과는 정확히 알 수 있어야 한다.

자연어 처리는 **문장에서 사용자가 원하는 일을 해석하는 과정**이다. v0.1은 짧은 한국어 표현을 정해진 규칙으로 해석하는 안을 추천한다. 모든 문장을 알아듣는 챗봇을 만들지 않는다.

```text
입력창 열기 → 입력 → 요청 해석
  ├─ 정보 부족: 한 가지를 되묻고 기다림
  ├─ 지원 요청: 검증 → 처리·저장 → 결과 표시
  └─ 모르는 요청: 실행하지 않고 가능한 요청 안내
결과 읽을 시간 제공 → 자동 닫기
```

| 예시 | 제안하는 반응 |
|---|---|
| “안녕”, “잘했어” | 현재 상태와 관계에 맞는 짧은 몸짓·말풍선 |
| “5분 타이머” | 로컬 등록 후 종료 예정 시각을 정확히 표시 |
| “알람 맞춰줘” | 아기 말풍선 “몇 시?”와 입력 안내로 필요한 정보를 요청 |
| “3시에 알려줘” | 날짜·오전/오후가 불명확하면 추측 실행하지 않고 확인 |
| “이따 알려줘” | 구체 시간을 되묻기 |
| 지원하지 않는 복잡한 요청 | 이해한 척 실행하지 않고 지원 범위 안내 |

알은 말하지 않는다. 알 상태의 입력 안내·등록 결과는 앱 안내로 표현하고 알은 움직임만 보인다. 아기도 “응!”이라는 말풍선과 “오늘 오후 3시 · 물 마시기 알림 등록”이라는 업무 결과를 분리한다.

입력 중·한글 조합 중·되묻기 중·오류 확인 중에는 자동으로 닫지 않는다. Enter 전송과 Esc 닫기를 제공하는 안을 추천하되, 한글 글자를 완성하는 Enter가 전송으로 처리되지 않게 한다. 화면을 열 때만 입력 초점을 받고 평소 다른 앱의 입력을 방해하지 않는다. 되묻기를 취소하면 예약을 만들지 않는다.

아기 클릭은 입력창 열기다. 알의 작은 클릭 반응과 입력창 접근을 어떻게 함께 제공할지, 쓰다듬기와 이동 드래그를 어떻게 구분할지는 미정이다. 정확한 좌표 클릭을 요구하지 않고 먹이를 넉넉한 범위에 놓도록 한다. UI 구현 세부값을 별도 제품 완료 조건으로 늘리지 않는다.

### 2.6 알람 / 타이머 / 리마인더 구조

**스케줄러는 언제 어떤 일을 해야 하는지 확인하는 시간 담당**이다. 펫의 감정이나 화면 갱신과 분리해 알림 시각을 관리한다.

| 종류 | 시간의 의미 | 예 |
|---|---|---|
| 타이머 | 시작부터 일정 시간이 지남 | 5분 뒤 |
| 알람 | 특정 날짜·시각 | 내일 오전 7시 |
| 리마인더 | 특정 날짜·시각과 할 일 내용 | 내일 오후 3시 서류 확인 |

예약을 먼저 저장하고 성공했을 때만 “등록됨”을 표시한다. 가까운 예약을 기다리면서 주기적인 재확인과 재시작·절전 복귀 시 확인을 함께 사용한다. 정해진 시간에 예약 식별자로 전달 기록을 남기고 운영체제 알림과 앱 내부 표시를 요청한다. 등록 목록 확인과 취소도 최소한으로 제공한다.

화면에서 초를 하나씩 빼는 방식만 쓰지 않는다. 원래 길이, 시작 시각, 예정 시각을 저장한다. 실행 중의 타이머는 **단조 시계**, 즉 사용자가 시스템 시각을 바꿔도 뒤로 가지 않는 경과 시간 기준을 활용하는 안을 추천한다. 재시작 이후에는 저장된 실제 날짜·시각이 필요하며, 절전 포함 방식도 운영체제에서 검증해야 한다.

| 앱·기기 상태 | 설계상 동작 제안 | 지원 상태 |
|---|---|---|
| 앱 실행, 컴퓨터 깨어 있음 | 예정 시각 판단과 알림 요청 | 구현·실기기 검증 필요 |
| 펫·입력창만 숨김, 앱 계속 실행 | 메인 영역에서 시간 관리 유지 | 숨김과 종료를 명확히 구분할 필요 |
| 화면 잠금 | 앱 실행 여부와 운영체제 알림 설정에 따름 | 표시·확인 가능한 범위 실기기 검증 필요 |
| 컴퓨터 절전 | 절전 중 일반 앱 코드의 정시 실행을 가정하지 않음. 복귀 후 지난 항목 확인 | 절전 중 전달 보장 없음 |
| 앱 완전 종료·컴퓨터 꺼짐 | 재실행 시 지난 항목 복구 | 종료 중 정시 전달은 별도 결정·운영체제 연동 없이는 보장 불가 |

**종료 중 정시 전달까지 v0.1이 보장할지는 아직 미정이다.** 위 표는 제품 요구사항을 낮춰 확정한 것이 아니라 기술적 경계를 드러낸 제안이다. 알림 구현 전에 사용자가 기대하는 지원 범위를 정해야 한다. 늦은 알림을 정상 시각 전달로 기록하거나 아기의 서툼으로 정당화하지 않는다.

시스템 시각 변경, 시간대 이동, 일광절약시간으로 같은 현지 시각이 두 번 오거나 사라지는 경우를 구분한다. 정확한 재해석 정책은 미정이다. 사용자가 등록한 날짜·현지 시각·시간대와 계산된 전달 시각을 함께 보관하고 모호함은 확인하는 안을 추천한다.

데이터베이스 기록과 운영체제 알림 표시는 하나의 저장 묶음으로 처리할 수 없다. 표시 요청 후 기록 전에 종료되면 중복 가능성, 기록 후 표시 요청 전에 종료되면 누락 가능성이 생긴다. 따라서 운영체제 알림이 **정확히 한 번** 보였다고 보장하지 않는다. 앱 안에서는 예약 식별자로 하나의 알림 항목을 유지하고 전달 시도·실패·사용자 확인을 나누며, 재시작 때 미확인 항목을 복구하는 안을 추천한다. 운영체제에 요청을 보낸 것과 사용자가 읽은 것은 다르다.

알림 권한 거부·집중 설정으로 표시가 억제된 경우를 숨기지 않고 앱 내 미확인 항목으로 남긴다. 한꺼번에 밀린 알림을 과도하게 쏟지 않는 표현 방식도 정해야 한다. 반복 예약, 중요도 등급, 10분 뒤 재알림은 이 최소 구현안에 넣지 않는다. 후자의 두 항목은 기준 문서에서도 필수 완료 범위가 아니다.

### 2.7 AIService / AIProvider와 Codex 확장 지점

**추상화는 특정 제품의 구현 대신 공통 역할을 정하는 것**이다. 기기가 바뀌어도 같은 콘센트를 쓰는 것과 비슷하다. AI 연결이 바뀌어도 펫의 기억과 규칙을 그대로 유지하기 위해 필요하다.

| 경계 | 역할 | v0.1 상태 |
|---|---|---|
| AIService | 사용자 제약, 필요한 기억, 보낼 정보 최소화, 요청·결과 조율 | 구조만 고려 |
| AIProvider | 특정 AI의 대화·추론 기능을 공통 요청·응답으로 연결 | 첫 제공자·인증·모델 미정 |
| 작업 도구 연결 | 작업 시작·진행·취소·승인·결과를 연결 | Codex 조건부 후속 후보 |

기본 대화와 비서 요청은 로컬 규칙으로 처리한다. AI 미연결은 정상 상태다. AIService가 펫의 생활을 시작시키는 전제 조건이 되어서는 안 된다. v0.1에서 실제 연결이 없다면 빈 제공자 관리 화면이나 여러 제공자의 형식뿐인 코드를 만들 필요도 없다.

후속 연결에서는 사용자 요청 → 허용 조건 확인 → 필요한 기억만 구성 → AI 응답 또는 작업 결과 → 검증 → 필요한 로컬 반응 순서로 처리한다. 외부 AI의 응답이 펫 상태·관계·권한을 직접 덮어쓰거나 임의 명령으로 실행되어서는 안 된다.

Codex는 일반 대화 모델과 구분한다. 사용자가 시작한 코드·파일 작업의 도구로 검토하며, 공식 연결 방식과 운영체제별 동작·구독 범위는 도입 시 다시 확인한다. 기존 조사 결론은 Decision Log D-019를 따른다. **일반 ChatGPT 구독을 앱의 대화 API 사용권으로 가정하지 않는다.** 여러 AI 자동 선택은 미래 범위다.

선택 순서는 사용자 명시 제약 > 고급 설정 > 작업별 선호 > 자동 판단이다. 사용자가 금지한 AI·시점·정보 전송을 자동 판단이 뒤집지 못한다. 인증값을 공식 클라이언트에서 추출하거나 비공식 내부 경로를 사용하지 않는다. 비용이 드는 연결은 사용자가 선택할 때 별도로 안내한다.

### 2.8 안전한 권한 구조

**권한은 특정 대상에 특정 행동을 해도 되는 허용 범위**다. 펫의 이해·제안·수행 능력이 성장해도 권한은 자동으로 넓어지지 않는다.

| 작업 | v0.1 제안 |
|---|---|
| 앱 전용 저장소에 상태·경험 저장 | 기본 앱 기능으로 제한 |
| 사용자가 요청한 로컬 알림 등록·취소 | 입력을 검증한 뒤 처리 |
| 운영체제 알림 표시 | 운영체제의 허용 상태 확인 |
| 임의 파일 읽기·수정·삭제, 프로그램 실행 | 실행 경로 자체를 제공하지 않음 |
| 외부 AI 정보 전송 | 후속 연결 도입 시 별도 사용자 선택 |
| 성장에 따라 실행 허용 확대 | 허용하지 않음 |

화면에는 필요한 요청만 노출하고 메인 영역에서 요청 종류·발신 창·값을 다시 검사한다. 외부 페이지나 임의 스크립트를 앱 화면에서 실행하지 않고, 입력 문장을 HTML 코드로 해석하지 않는다. 화면에 운영체제 접근 권한 전체를 주지 않는 것이 기본이다. 구현 시 공식 [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security)을 확인한다.

향후 파일 작업은 대상 폴더·허용 행동·해당 작업·유효 기간을 묶어서 허용하고 실행 직전에 다시 확인하는 방향이다. 요청 취소나 권한 철회도 반영해야 한다. 이 전체 권한 관리 기능은 후속 범위이며 v0.1에 선구현하지 않는다. 향후 비밀 인증값을 보관할 때에는 일반 데이터베이스 평문 대신 운영체제의 인증정보 보관 기능을 검토한다.

## 3. 핵심 데이터 모델

데이터 모델은 **무엇을 어떤 항목으로 기억할지 정한 설계**다. 아래 이름과 필드는 후보이며, 확정된 저장 형식이나 이미 만든 코드가 아니다. 관계·감정·성격의 내부 수치·임곗값과 경험 보존 기간은 미정이다.

### 3.1 펫의 현재 상태

| 모델 후보 | 주요 항목 제안 | 필요한 이유 |
|---|---|---|
| 개체 정보 | `petId`, 생성·탄생 시각, 이름, 외형 식별자, 기질 생성 기준값 | 알과 아기가 같은 개체임을 유지 |
| 생애 진행 | 성장 단계, 부화 준비 상태, 연출 완료 지점, 첫 교감·이름 짓기 완료 여부 | 중간 종료 후 이어가기 |
| 생활 상태 | 배고픔, 졸림, 수면 여부, 마지막 계산 시각 | 몸의 필요를 감정과 별도로 관리 |
| 감정 | 종류, 내부 강도, 발생 원인·시각, 진정 기준 | 순간 반응과 자연스러운 복귀 |
| 관계 | 내부 익숙함·신뢰, 일시적 거리두기, 최근 상호작용 시각 | 장기적인 행동 차이와 회복 |
| 선천 기질 | 약한 반응 경향, 생성 규칙 버전 | 재실행할 때 기질이 다시 바뀌지 않게 함 |
| 화면 정보 | 화면 식별자, 펫 위치·방향 | 모니터 변경 후 안전한 위치 복원 |

“배고프고 졸리지만 칭찬에는 기쁘고 사용자와 친숙함”이 동시에 가능해야 한다. 하나의 행복도에 모든 의미를 넣지 않는다. 내부 계산값을 쓰더라도 화면에 숫자·게이지·관계 등급으로 노출하지 않는다. 화면으로 보낼 정보는 몸짓·표정·구슬 표현 중심으로 제한한다.

후천 성격 전체를 계산하거나 성장 결과를 미리 확정하지 않는다. v0.1은 약한 선천 기질, 최소 관계 반응, 이후 해석할 수 있는 경험 기록을 우선한다.

### 3.2 아기 경험 기록 — v0.1 필수

경험 기록은 **현재 상태와 별도로 보존하는 실제 사건**이다. 배고픔이 해소되었다는 상태만 있으면 어떤 돌봄을 받았는지 나중에 알 수 없다.

| 항목 후보 | 의미·예시 |
|---|---|
| 경험 식별자 | 같은 식사를 중복 기록하지 않기 위한 값 |
| 펫 식별자 | 경험의 주인 |
| 발생 시각·당시 성장 단계 | 아기 때 발생했는지 판단 |
| 경험 종류 | 식사·놀이·칭찬·터치 등 후보 |
| 필요한 상황 | 수면 중이었는지, 졸렸는지 등 최소 정보 |
| 실제 결과 | 먹기 완료, 잠시 피함, 구슬 보여주기 등 |
| 기록 형식 버전 | 나중에도 옛 기록의 의미를 해석하기 위한 번호 |

예: 아기 / 식사 / 졸린 상태 / 사용자가 먹이를 가까이 옮김 / 먹기를 마침.

구체 종류와 필드는 **제안**이다. 경험 수집을 구현하기 전에 최소 목록을 정해야 하며, 성격 반영 공식과 보존 기간을 임의 확정하지 않는다. 경험 기록이 필수라는 이유로 전체 대화나 매 순간의 마우스 좌표를 저장하지 않는다. 부재 중 실제로 없었던 식사·사용자 놀이를 경험으로 만들어 넣지 않는다. 보존 정책을 정하기 전 조용히 과거 경험을 자동 삭제하지 않는다.

### 3.3 비서 기능과 임시 기억

| 데이터 | 항목 후보 | 보존 구분 |
|---|---|---|
| 예약 알림 | 식별자, 종류, 내용, 날짜·현지 시각·시간대, 전달 예정 시각, 타이머 원래 길이, 예약·취소 상태 | 재시작 뒤 복원 필요 |
| 전달 기록 | 예약 식별자, 예정 회차 식별, 전달 시도·실패 시각, 사용자 확인 여부 | 중복과 누락 복구에 필요한 최소 기록 |
| 대화 중 임시 정보 | 진행 중 요청, 빠진 정보, 확인한 시간·내용 | 처리·취소 후 정리 |
| 사용자 명시 기억 | 기억을 요청한 내용과 출처 | 장기 기억 원칙만 유지, 일반 기억 기능의 범위는 후속 결정 |

모든 테이블을 처음부터 각각 만들 필요는 없다. 펫 상태는 하나의 묶음으로 저장하고 경험·예약·전달 기록은 별도 항목으로 두는 작은 구조부터 검토한다. 큰 대화 저장소나 검색 엔진은 지금 만들지 않는다.

### 3.4 로컬 영속화와 복구

**영속화는 앱을 꺼도 데이터가 남도록 저장하는 것**이다. SQLite 후보를 사용하면 별도 서버 없이 관련 데이터를 한 파일 기반 저장소에 보관할 수 있다. 저장 파일 형식과 운영체제별 위치는 기술 검증 후 확정한다.

**트랜잭션은 관련 변경을 전부 저장하거나 전부 취소하는 한 묶음**이다. 식사 완료 때 배고픔 변화·식사 경험·계산 시각을 함께 저장하면 중간 종료로 기록 일부만 남는 문제를 줄인다. 이것을 원자적 저장이라고도 한다. [SQLite 원자적 저장 설명](https://www.sqlite.org/atomiccommit.html)

**Repository는 저장소에 접근하는 전용 창구**다. 여기서는 Git 저장소를 뜻하지 않는다. Pet Brain은 SQLite 명령 대신 “펫 저장”, “경험 추가”를 요청한다. 저장 도구를 바꾸더라도 펫 규칙에 미치는 영향을 줄인다.

추천 저장·복구 순서는 다음과 같다.

1. 앱 전용 사용자 데이터 폴더에 저장한다. 프로젝트 코드 폴더와 분리한다.
2. 저장을 수정하는 담당을 한 곳으로 두고 중복 앱 실행이 같은 펫을 동시에 갱신하지 않게 한다.
3. 이름·경험·예약·부화 지점 등 중요한 변경은 해당 처리에서 저장한다. 종료 시 저장에만 의존하지 않는다.
4. 생활 상태는 마지막 계산 시각과 함께 주기적으로 보존한다. 장기 부재는 제한된 변화와 자연스러운 복귀로 해석한다.
5. 앱 시작 시 저장 형식 버전을 확인한다. **마이그레이션은 기존 데이터를 새 저장 형식으로 옮기는 작업**이며, 변경 전 복구용 사본과 실패 시 원본 보존을 준비한다.
6. 디스크 부족·쓰기 권한 오류·손상 때 성공으로 표시하지 않는다. 저장 실패 상태를 알리고 중요한 변경을 조용히 버리지 않는다.
7. 손상된 저장소를 삭제해 새 알을 만들지 않는다. 원본을 보존하고 복구 가능한 사본 여부를 확인한다.

상태와 경험을 모두 매번 재생해 현재 상태를 만드는 복잡한 기록 체계는 도입하지 않는다. 현재 상태와 최소 경험 사건을 함께 관리한다. 자동 백업 주기, 사본 수, 내보내기·삭제 화면, 암호화는 미정이다. 로컬 저장 자체가 암호화를 의미하지 않는다. 내보내기 가능성은 고려하지만 클라우드 동기화는 v0.1 밖이다.

## 4. v0.1 구현 단계

아래 파일 경로는 프로젝트 기준 **생성·수정 후보**다. 단계 1의 임시 알 앱과 최소한의 화면 요청 연결만 구현했다. 나머지 후보 파일·기능이 이미 존재한다는 뜻은 아니다. 한 단계의 완료 조건을 실제로 확인한 다음 이어간다.

### 단계 0. 첫 구현에 필요한 결정 정리

- **테스트 방법:** PRD 17~18장과 문서 내용 대조. 이 단계는 문서 검수이며 앱 테스트가 아니다.
- **다음 연결:** 실제 창 검증에 필요한 최소 코드만 만든다.

### 단계 1. 투명한 알 하나로 창 기능 검증

**현재 결과 — 2026-09-26:** 원본 프로젝트에 `src/main/index.ts`, `src/main/windows.ts`, `src/preload/index.ts`, `src/shared/window-api.d.ts`, `src/renderer/index.html`, `styles.css`, `pet.ts`, `tsconfig.json`, `scripts/copy-assets.mjs`, `tests/egg-smoke.ts`를 추가하고 `package.json`의 실행·검사 명령을 연결했다. 화면 하나에는 HTML/CSS와 TypeScript만 사용하며 React·Vite 채택은 미뤘다. 외부 이미지 없이 CSS로 그린 임시 알은 클릭 시 흔들리고 드래그로 이동한다. 메뉴 막대에 종료·초기 위치 복원 기능을 넣었다.

**남음:** 다른 앱 클릭 통과·키보드 입력 유지, 메뉴 종료·위치 복원, 화면 가장자리·다중 모니터·배율·장시간 동작, 설치용 앱 묶기, Windows 검증. 화면 조작 도구 권한이 없어 운영체제 조작은 Codex가 직접 검증하지 못했다. 따라서 **단계 1 전체 완료와 Electron 최종 채택은 보류**한다. Pet Brain·저장·부화·아기·비서 기능은 구현하지 않았다. 클릭과 드래그를 구분하는 6px 임계값은 이번 검증용 값이며 쓰다듬기·굴러가기 같은 최종 제스처 정책이 아니다. D-038 참조.

## 5. 테스트 전략

테스트는 **정해진 조건에서 실제 결과가 요구와 일치하는지 확인하는 작업**이다. 코드가 존재하거나 실행 창이 떴다는 사실만으로 기능 완료를 판단하지 않는다.

| 검사 수준 | 쉬운 뜻 | 핵심 확인 |
|---|---|---|
| 단위 검사 | 작은 규칙 하나씩 확인 | 배고픔 변화, 감정 진정, 부화 순서, 시간 해석 |
| 통합 검사 | 연결된 부분을 함께 확인 | 상태·경험 동시 저장, 예약과 복구, 요청 검증 |
| 앱 흐름 검사 | 사용자가 하는 일을 순서대로 수행 | 알 → 부화 → 이름 → 돌봄 → 재실행 |
| 실기기 검사 | 실제 운영체제에서 확인 | 투명 창, 클릭 통과, 입력 초점, 알림 권한, 절전 |
| 장시간 사용 검사 | 며칠 함께 생활 | 상태 연속성, 기억 유지, 방해 정도, 자원 사용 증가 |

**가짜 시계는 검사 중 프로그램에 전달하는 시간을 직접 바꾸는 장치**다. 하루 기다리지 않고 “하루 뒤 재실행”을 검사한다. 실제 운영체제 절전은 이것으로 대체할 수 없으므로 별도로 확인한다. 무작위 반응도 검사에서는 기준값을 고정해 같은 문제를 재현할 수 있게 한다.

### 5.1 반드시 지킬 규칙

- 인터넷과 외부 AI 없이 펫 생활·짧은 반응·기본 비서 기능이 동작한다.
- 부화 전후 식별자가 같고, 없는 동안 부화를 완료하지 않으며, 아기 이후로 넘어가지 않는다.
- 감정·관계·성격은 숫자·게이지·등급으로 표시하지 않는다.
- 감정·몸 상태·관계를 분리하고 구슬은 감정 표현에만 사용한다.
- 부재로 죽음·영구 이별·성장 실패를 만들지 않는다.
- 이름·기질·기본 상태·관계·경험·예약은 재시작 후 유지된다.
- 상태 변경과 경험 기록 중 일부만 저장되는 일을 막는다.
- 저장 전에 등록 성공을 표시하지 않는다. 모호한 요청은 되묻고 취소 시 실행하지 않는다.
- 펫의 감정·관계·수면이 정확한 알림 전달을 방해하지 않는다.
- 허용되지 않은 파일·프로그램 실행 경로가 없다.

### 5.2 PRD 완료 조건과 검증 연결

| PRD 17장 완료 조건 | 구현 단계 | 실제 확인할 증거 |
|---|---|---|
| 알 상호작용·전조·구슬·부화·첫 교감·이름 | 1, 4, 8 | 순서대로 경험하고 중단 후 이어가기 |
| 아기 돌봄·감정·관계·며칠 연속성·경험 보존 | 3, 9, 10, 11 | 실제 사용 및 재시작 전후 기록 대조 |
| 짧은 대화·알람·타이머·리마인더·복원 | 5, 6, 7, 11 | 등록·취소·전달·재실행 사례 |
| 인터넷·외부 AI 없는 기본 동작 | 전 단계, 특히 11 | 네트워크 차단·외부 AI 종료 상태에서 흐름 재검사 |

검증 기록에는 날짜, 운영체제·앱 버전, 조건, 예상·실제 결과, 실패·미검증 항목을 적는다. 민감한 대화 원문이나 인증값을 검사 로그에 남기지 않는다. 자동 검사 도구의 Electron 지원 범위는 도입 시 공식 문서로 재확인하고 운영체제 동작은 직접 확인한다. [Playwright Electron 문서](https://playwright.dev/docs/api/class-electron)

**현재 결과:** 기준 문서 검수와 도구 설치 확인에 이어 단계 1의 임시 알 창을 구현했다. TypeScript·빌드·앱 내부 자동 검사와 사용자 확인에 의한 표시·클릭·드래그 검증까지 수행했다. 검증 방법과 남은 운영체제 동작은 단계 1의 현재 결과에 기록한다. Pet Brain·알림·성능·장기간 보존 검증은 수행하지 않았다.

| 종료·절전 중 알림 정책 | 정시 전달 보장 범위 미정 | 단계 6 전에 사용자 기대와 일치 확인 |
| 시간·시간대 변경 해석 | 제안만 있음 | 단계 6~7 전 |
| 자연어 지원 표현 | 짧은 한국어 규칙 추천 | 단계 5~7 전 |
| 부화 시작 확인·시간·돌봄 영향 | 미정 | 단계 8 전 |
| 알 클릭·쓰다듬기·드래그 구분 | 미정 | 단계 1·4·5에서 검증 |
| 생활 시간표·먹이·수면 수치 | 미정 | 단계 9 전 |
| 관계 영향·회복 속도·기질 차이 | 미정 | 단계 10 전 |
| 경험 최소 필드·보존 기간 | 후보 제안, 미정 | 수집 구현 전 최소 항목 결정; 이후 확장 별도 검토 |
| 그래픽·외형·제작 권리 | 미정 | 임시 자료와 최종 자료를 구분해 결정 |
| 저장 사본·복구·암호화 | 원본 보존 방향 추천, 세부 미정 | 단계 3부터 필요한 최소 복구 우선 |

캐릭터 문서의 “고정 시간대”는 사용자 생활 패턴을 학습하지 않는 낮·밤 기본 반응으로 해석한 제안이다. 특정 지역의 시간대를 영구 고정한다는 뜻으로 확정하지 않았다. 구현 전에 뜻을 확인해야 한다.

### 6.2 문서와의 충돌·해석 주의점

검수 범위에서 핵심 제품 원칙의 직접 충돌은 발견하지 못했다. 다음은 잘못 확대·확정하기 쉬운 지점이다.

- PRD 27장의 `energy`는 초기 예시다. 실제 모델은 상세 설계에 맞춰 배고픔·졸림을 구분하는 안을 추천한다.
- 외형 자연어 생성, 이름 변경권, 집중 모드, 알림 중요도·재알림을 v0.1 필수 완료 기준으로 올리지 않는다.
- 드래그·고정 시간대·터치 부위 같은 캐릭터 세부 표현을 PRD와 별개의 새 필수 조건 묶음으로 늘리지 않는다.
- 아기 경험 기록은 필수다. 반대로 모든 경험 종류·성격 반영 공식을 이미 확정한 것으로 쓰지 않는다.
- 알림의 기술적 한계는 제품 정확성 요구와 조율해야 할 미결정 사항이다. “완전 종료 중은 무조건 지원하지 않음”을 승인 없이 확정하지 않는다.
- D-004는 상세 구조 확정 시, D-006은 SQLite 선택 시 ADR 기록을 후속 조치로 둔다. **ADR은 중요한 기술 선택의 이유·대안·영향을 남기는 짧은 기록**이다. 현재는 검토용 초안이므로 별도 ADR을 만들지 않았다. 최종 채택 때 기존 Decision Log로 충분한지, 기존 후속 조치를 유지해 별도 기록할지 먼저 제안해야 한다.

### 6.3 후속으로 미룰 사항

첫 일반 대화 AI·인증, 로컬 언어 모델, Codex 실제 연동, 어린이 이후 성장, 자동 AI 선택, 멀티펫, 클라우드 동기화, 집중 모드, 이름 변경권, 다양한 먹이·취향은 현재 단계에서 구현하지 않는다. 연결 경계나 최소 식별자만 고려하며 빈 기능·설정 화면을 미리 만들지 않는다.

## 7. 구현 시작 전 확인해야 할 위험 요소

| 위험 | 왜 중요한가 | 확인·대응 방향 |
|---|---|---|
| 투명 창과 클릭 통과 | 보이지 않는 영역이 다른 앱 조작을 막을 수 있다. | 단계 1에서 펫·빈 영역·드래그·입력 초점을 실제 검사 |
| 완전 종료·절전 중 알림 | 일반 앱 코드가 동작하지 않는 시간을 정시 보장할 수 없다. | 지원 범위를 먼저 결정하고 실행·숨김·잠금·절전·종료를 구분 |
| 알림 전달 중 종료 | DB 기록과 운영체제 표시를 한 번의 작업으로 묶기 어렵다. | 전달 기록·미확인 목록·예약 식별자로 복구, 정확히 한 번 보장 주장 금지 |
| 시각·시간대 변경 | 일정 시각과 경과 시간은 다르게 영향을 받는다. | 타이머와 날짜 알림 분리, 재시작·절전·시각 역행 검사 |
| 부화 중단 | 개체 중복·연출 누락·이름 초기화가 관계 연속성을 해친다. | 완료 지점 저장, 같은 식별자 유지, 모든 지점에서 재시작 검사 |
| 저장 실패·손상 | 펫의 기억이 사라지면 제품 핵심이 무너진다. | 관련 상태 묶음 저장, 사본·원본 보존, 실패를 성공으로 표시하지 않음 |
| SQLite 실행 앱 호환성 | 개발 중 되더라도 실제 앱에 라이브러리가 포함되지 않을 수 있다. | 선택한 Electron·운영체제·CPU 환경에서 실행 앱 검사 |
| 상시 자원 사용 | 항상 켜 둔 앱이 업무를 방해할 수 있다. | 대기·수면 중 갱신 최소화, 처리량·메모리 실측 후 판단 |
| 그래픽 제작량 | 필요한 동작 그림이 구현보다 오래 걸릴 수 있다. | 최소 동작 목록과 임시 그림으로 검증, 최종 제작 방식 별도 결정 |
| 경험 과수집·무한 증가 | 미래 활용을 이유로 불필요한 개인 정보와 기록이 쌓일 수 있다. | 실제 사건 최소 수집, 크기 측정, 보존 정책 결정 전 임의 삭제 금지 |
| Windows 검증 누락 | macOS에서 되는 창·알림이 다른 운영체제에서 다를 수 있다. | 환경별 결과 구분, 검증 전 지원 완료 주장 금지 |
| 범위 확대 | AI·성격 엔진·미래 성장 선구현이 첫 완성을 늦춘다. | PRD 필수 범위에 없는 아이디어는 `추후 제안`으로 분리 |

첫 코드 단계는 **투명한 임시 알 하나를 다른 앱 작업을 방해하지 않고 조작할 수 있는지 확인하는 것**이다. 이 문서에는 그 이후 설계도 담았지만 모든 기능을 한 번에 만드는 계획은 아니다. 문서에서 제안한 항목을 승인·검증된 기술 결정으로 오해하지 않고, 작은 단계의 실제 결과를 기준으로 갱신한다.
