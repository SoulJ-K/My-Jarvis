## 1. 이 문서의 읽는 법

이 문서는 기능 수를 세기보다 **각 제품이 사용자에게 주는 중심 경험**을 비교한다. `확인`은 공개 자료에 명시된 내용, `미확인`은 해당 자료만으로 판단할 수 없는 내용, `해석`은 공개 정보를 바탕으로 한 제품 관점의 판단이다. `미확인`은 기능이 없다는 뜻이 아니다. 각 프로젝트가 설명하는 기능도 직접 실행해 확인한 결과는 아니다.

- **AI 의존도**: 언어 모델을 연결하지 않아도 핵심 경험이 유지되는 정도. 언어 모델은 문장을 이해하고 생성하는 AI를 뜻한다.
- **펫 생명성**: 사용자가 말을 걸지 않아도 움직임, 욕구, 휴식 같은 상태가 이어져 살아 있는 듯 느껴지는 정도.
- **선제성**: 사용자가 먼저 요청하지 않았을 때 펫이 상황을 보고 말을 걸거나 행동하는 정도.
- **Tool 실행**: 알람 설정, 파일 처리, 앱 실행처럼 컴퓨터의 기능을 실제로 사용하는 것.
- **Agency(자율 실행 범위)**: 요청을 해석해 도구를 고르고 여러 단계를 이어 수행하는 정도. 도구 하나가 있다는 사실만으로 높은 Agency를 뜻하지는 않는다.
- **데이터 소유**: 기억과 상태를 사용자가 어디에서 확인·보관·내보낼 수 있는지. 로컬 저장은 사용자 기기에 저장한다는 뜻이며, 쉬운 내보내기와 같은 의미는 아니다.
- **무료 운영 가능성**: 소프트웨어 값뿐 아니라 모델 사용료, 개인 기기 성능, 서버 비용을 함께 본다.

## 2. 한눈에 보는 제품 중심

|---|---|---|---|
| **NekoAI** | 화면 속 캐릭터와 AI 대화를 함께 원하는 데스크톱 사용자 | 움직이는 펫에 대화·기억·상황별 감정과 알림을 결합 | 움직임, 감정, 기억, 여러 AI 제공자 선택, 먼저 건네는 알림 |
| **Miru** | 자신을 오래 기억하고 작업 흐름을 살펴주는 동반자를 원하는 사용자 | 화면 맥락, 검토 가능한 장기 기억, 적절한 때의 대화 | 로컬 기억, 지속적 관계, 상황 이해, 선제적 개입 |

| **desktop-pet** | 대화창에서 PC 작업을 맡기고 싶은 Windows 사용자 | 캐릭터를 통해 알람·파일·명령 등 일을 수행하는 비서 | 장기 비전의 도구 실행과 실제 업무 수행 |

위의 `핵심 사용자`는 제작자가 공개한 정량적 고객 조사 결과가 아니라 제품 설명에서 도출한 **가설적 사용자상**이다. 제품 중심과 현재 기능의 근거는 각 프로젝트의 [NekoAI README](https://github.com/nucket/NekoAI), [Miru README](https://github.com/kiyotakali/Miru), [Pet Mochi README](https://github.com/cskwork/pet-mochi), [desktop-pet README](https://github.com/valerieliang/desktop-pet)이다.

## 4. 프로젝트별 제품 판단

### NekoAI — 겹치는 기본 기능의 기준선

**강점(공개 정보 기준):** 화면을 돌아다니는 펫, 기분에 따른 행동·답변, 지속 기억, 여러 모델 제공자, 장시간 작업 알림이 한 경험에 들어 있다. Jarvis Pet이 이 기능들을 각각 제공하는 것만으로는 차별화라고 말하기 어렵다. [근거](https://github.com/nucket/NekoAI)

**약점 또는 아직 확인할 부분:** 공개 README에서 성장에 따른 역할 확대와 PC 작업 수행은 확인되지 않는다. 이는 실제로 없다는 판정이 아니라, 현재 설명만으로 제품의 중심 가치라고 보기 어렵다는 뜻이다.

**Jarvis Pet과 겹침:** 이동·감정·기억·선제 알림·여러 AI 제공자 연결. **파고들 빈자리(가설):** 펫과 사용자 관계가 쌓이면서 실제 업무 위임 범위가 커지는 경험. 이 가설은 NekoAI의 실제 사용 흐름 확인 전까지 확정하지 않는다.

### Miru — 지속적 관계와 상황 이해의 기준선

**강점(공개 정보 기준):** 화면 상황을 살피고 말을 걸 시점을 판단하며, 사용자가 읽을 수 있는 Markdown 기억을 남긴다. 로컬 단일 기기와 개인 서버 방식도 제시한다. 따라서 `로컬 기억 + 선제적 동반자`만으로 차별화를 주장할 수 없다. [근거](https://github.com/kiyotakali/Miru)

**약점 또는 아직 확인할 부분:** 공개 README에서 알람·파일·앱을 단계적으로 맡기는 폭넓은 비서 도구와 AI 없이 이어지는 펫의 생활 주기는 확인되지 않는다. 화면을 살피는 경험의 배터리·비용·방해 정도는 실사용 검증이 필요하다.

**Jarvis Pet과 겹침:** 장기 기억, 사용자 상황 이해, 먼저 말 걸기, 로컬 데이터, 하나의 지속적 캐릭터. **파고들 빈자리(가설):** 상황 이해에서 끝나지 않고, 사용자가 허락한 구체적 일을 끝내는 데까지 이어지는 관계형 비서. 이 역시 Miru의 실제 기능 확인이 선행되어야 한다.

### Pet Mochi — AI 없는 펫 경험의 기준선

**강점(공개 정보 기준):** AI가 꺼져도 기분·욕구·이동·수면이 계속 갱신된다. 돌봄 행동, 작은 습관, 복귀 인사 등으로 펫의 존재감을 만든다. 기억 검토·삭제·내보내기도 제공한다. Jarvis Pet의 `AI 없이 살아 있는 아기 펫`은 이미 강한 선행 사례가 있다. [근거](https://github.com/cskwork/pet-mochi)

**약점 또는 아직 확인할 부분:** 공개 범위에서 PC 비서 업무는 동의받은 파일 요약 등으로 제한되고, 셸 실행은 의도적으로 제외한다. 성장 단계는 현재 기능이 아니라 향후 계획으로 적혀 있다. [근거](https://github.com/cskwork/pet-mochi)

**Jarvis Pet과 겹침:** 독립적인 펫 상태, 감정·기본 욕구, 로컬 저장, 선택적 AI. **파고들 빈자리(가설):** 펫을 돌보는 관계가 시간이 지나 실제 생활 보조와 업무 위임으로 연결되는 일관된 성장 경험.

### desktop-pet — 실제 업무 수행의 기준선

**강점(공개 정보 기준):** 알람과 반복 작업, 검색, 파일 작업, 앱 실행, 명령 실행까지 지원하며, 허용할 도구를 설정하고 실행 중인 일을 보여준다. Jarvis Pet이 `실제 일을 해주는 펫`이라는 문장만으로 새롭다고 주장하기 어렵다. [근거](https://github.com/valerieliang/desktop-pet)

**약점 또는 아직 확인할 부분:** 제품 설명의 중심은 대화와 작업 수행이다. 독립 욕구·돌봄·발달 단계는 확인되지 않는다. 파일 쓰기나 명령 실행처럼 영향이 큰 도구도 포함되므로, Jarvis Pet이 이런 기능을 다룰 때는 사용자의 허락과 결과 확인을 제품 경험의 핵심으로 설계해야 한다. 이 마지막 문장은 경쟁 제품의 결함 판정이 아니라 Jarvis Pet의 설계 과제다.

**Jarvis Pet과 겹침:** 알람, 기억, 도구 실행, 여러 단계의 일 처리. **파고들 빈자리(가설):** 어린 펫의 작은 도움에서 시작해 신뢰와 명시적 허락에 따라 작업 범위가 커지고, 무엇을 실행했는지 사용자가 쉽게 확인하는 경험.

## 5. Jarvis Pet에 주는 의미

네 제품은 Jarvis Pet의 구상 중 상당 부분을 이미 각각 보여준다. 특히 **NekoAI의 기능 조합**, **Miru의 지속적 기억·상황 이해**, **Pet Mochi의 AI 없는 생명성**, **desktop-pet의 도구 실행**은 단독 차별점으로 주장하기 어렵다. Jarvis Pet이 검증할 지점은 이 네 축을 한 펫의 시간 흐름 안에 묶었을 때 사용자가 **성장, 신뢰, 유용성**을 자연스럽게 느끼는지다.

이는 아직 제품 우위의 증거가 아니다. 공개 문서만으로 사용 만족도나 기능 완성도까지 비교할 수 없고, 네 요소를 더 많이 결합한다고 자동으로 좋은 경험이 되는 것도 아니다. Jarvis Pet의 PRD에 있는 `작은 MVP`, `로컬 기억`, `첫 AI 제공자 하나`, `AI 없는 기본 행동` 원칙을 유지하며 검증해야 한다.

## 현재 차별화 가설

1. **성장은 외형뿐 아니라 위임할 수 있는 일의 성장이다.** 처음에는 AI 없이 움직이고 쉬며 간단한 알람을 전한다. 이후 대화·기억·상황 이해를 더하고, 사용자의 명시적 허락에 따라 파일·앱 같은 실제 작업을 맡는다. 경쟁 프로젝트 각각에 유사 요소가 있으므로 **이 연결 경험 자체**를 검증 대상으로 둔다.
2. **하나의 펫 정체성이 AI 제공자가 바뀌어도 이어진다.** 기억·감정·관계는 펫에 남고, AI는 필요한 순간에 쓰는 도구가 된다. 다만 로컬 기억과 여러 제공자 지원은 이미 선행 사례가 있으므로 단독 차별점으로 내세우지 않는다.
3. **할 수 있는 일과 허락받은 일을 사용자가 이해한다.** 펫의 능력이 늘어날수록 사용자에게 현재 권한, 실행 결과, 실패 여부가 분명히 보여야 한다. 이것이 신뢰를 높이는지는 실제 사용자 검증이 필요하다.

## 추가 검증 필요 사항

1. **경쟁 제품 실제 사용:** 네 제품을 설치해 AI 연결을 끊었을 때 행동, 먼저 말 거는 빈도, 기억의 수정·삭제 경험, 작업 실행의 확인 절차를 같은 시나리오로 기록한다. README의 주장과 실제 동작을 분리한다.
2. **성장 경험의 가치:** 사용자가 `펫의 성장 = 비서 능력과 위임 범위의 성장`을 매력적으로 느끼는지, 단순한 기능 제한으로 느끼는지 확인한다.
3. **첫 사용자 정의:** AI 동반자를 원하는 사람과 PC 업무 비서를 원하는 사람 중 누구의 문제가 더 절실한지 인터뷰로 좁힌다. 현재 표의 핵심 사용자는 해석일 뿐이다.
4. **최소 가치 검증:** AI 없는 행동·감정·알람만으로도 계속 켜 두고 싶은지 확인한다. 그렇지 않다면 아기 단계의 체류 시간을 줄이거나 설계를 바꿔야 한다.
5. **선제적 개입의 기준:** 어떤 상황에 먼저 말을 거는 것이 도움이 되고, 언제 방해가 되는지 확인한다. 화면 접근 권한과 모델 사용 비용도 함께 측정한다.
6. **도구 권한과 책임:** 파일·앱·명령 등은 어떤 작업부터 맡길지, 실행 전 허락·실행 후 확인·실패 복구를 어떻게 보여줄지 정한다.
7. **무료 운영 범위:** 모델을 쓰지 않는 기본 기능, 로컬 모델을 쓰는 기능, 외부 API가 필요한 기능의 비용과 기기 성능 요구를 실제로 측정한다. `무료`를 모든 AI 기능의 무제한 사용으로 표현하지 않는다.
8. **비교 자료 갱신:** 공개 README는 바뀔 수 있다. 차별화 확정 전 각 저장소의 최신 기능·향후 계획을 다시 확인하고, 제품 관점 분석과 별개로 필요한 경우 코드·설치 상태를 검증한다.

**다음 문서 제안:** 차별화 가설 중 무엇을 채택하거나 보류했는지 기록하는 `Decision Log(결정 기록)`를 이 분석 이후에 만들면 좋다. 무엇을 왜 결정했는지 남기는 회의록과 비슷하지만, 선택 근거와 재검토 조건에 집중한다. 이 문서 작성 자체는 이번 범위에 포함하지 않는다.
