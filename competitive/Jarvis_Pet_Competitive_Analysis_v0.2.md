# Jarvis Pet 통합 경쟁 분석 v0.2

- **문서 목적:** NekoAI, Miru, Pet Mochi, desktop-pet을 동일한 축에서 직접 비교하고 Jarvis Pet의 차별화 가설과 후속 검증 순서를 정한다. 네 심층 분석의 세부 내용을 반복하기보다 서로의 기준선과 빈자리를 종합한다.
- **조사일:** 2026-09-25 (Asia/Seoul). 이 문서는 같은 날 작성된 네 심층 분석을 종합했다.
- **Jarvis Pet 기준:** [PRD](../docs/Jarvis_Pet_PRD.md), [결정 기록](../docs/Jarvis_Pet_Decision_Log.md). Jarvis Pet의 멀티 AI 조율과 폭넓은 업무 수행은 **장기 구상**이며 현재 구현 사실이 아니다. 첫 버전은 AI 제공자 하나와 작은 범위의 기능을 목표로 한다.
- **증거 범위:** 각 심층 분석은 공식 자료와 공개 코드 일부를 검토했으나 네 앱 모두 동일 조건으로 설치·장기 사용한 비교 시험은 아니다. NekoAI는 v0.3.8 코드, Miru는 `7d57a325` 커밋, Pet Mochi는 공개 `main`의 문서·일부 코드, desktop-pet은 공개 `main`의 README·기본 설정을 주로 기준으로 한다. `확인`은 해당 자료에서 확인했다는 뜻이며 실사용 품질의 입증은 아니다. `미확인`은 기능이 없다는 뜻이 아니다. [N1][M1][P1][D1]

## 1. 결론부터: 네 제품이 이미 만든 기준선

네 제품을 합치면 **움직이는 펫, AI 없이 유지되는 행동, 감정, 로컬 기억, 제공자 선택, 먼저 말 걸기, 알람, PC 도구 실행**은 이미 공개 사례가 있다. 그러므로 기능 이름 하나나 단순 합집합은 Jarvis Pet의 차별점이 아니다. 가장 강한 빈자리 가설은 **한 펫의 지속적 정체성 안에서 사용자에게 보이는 능력 성장, 별도로 승인받는 권한 확대, 실제 업무 결과, 그 이력을 한 흐름으로 연결하는 경험**이다. 다만 이는 네 공개 자료에서 뚜렷하게 확인되지 않은 조합이라는 뜻이지, 시장 전체의 공백이나 사용자 선호가 입증됐다는 뜻은 아니다. [N1][M1][P1][D1][J1][J2]

특히 두 번째 가설인 **여러 AI·도구의 오케스트레이션**은 더 좁게 정의해야 한다. Miru는 이미 화면 이해·대화·기억 정리에 역할별 모델을 배치하고, desktop-pet은 도구를 연속·병렬로 실행한다. Jarvis Pet이 추가로 증명할 것은 제공자 수가 아니라 **업무에 맞는 선택, 단계 간 결과 전달, 비용·실패 처리, 사용자에게 보이는 실행 근거**다. [M3][D2]

## 3. 핵심 사용자와 제품 포지셔닝

**펫에서 비서로 이어지는 축**으로 보면 Pet Mochi는 돌봄과 생명성, NekoAI는 화면에 상주하는 대화 동반자, Miru는 맥락과 기억에 기반한 관계, desktop-pet은 업무 수행에 각각 무게를 둔다. 이는 우열이 아니라 제품이 먼저 해결하는 문제의 차이다. Pet Mochi의 소스 실행 방식과 Miru의 모델·서버 설정, desktop-pet의 Python·모델 설정은 기술 사용자를 더 쉽게 떠올리게 하지만 실제 고객군을 증명하지는 않는다. [P1][M1][D1]

**Jarvis Pet의 사용자 가설은 아직 넓다.** ‘펫을 곁에 두고 싶은 사람’과 ‘PC 업무를 맡기고 싶은 사람’의 기대가 다를 수 있다. 동반 경험이 주목을 끌어도 업무 위임을 원하지 않을 수 있고, 업무 비서를 원하는 사용자는 돌봄 단계를 지연으로 느낄 수 있다. 첫 사용자군은 인터뷰와 사용 관찰로 좁혀야 한다. 이는 경쟁 분석에서 도출한 **추론**이다. [J1][J2]

NekoAI와 Pet Mochi는 **AI 연결 전에도 펫이 보이고 반응해야 한다**는 Jarvis Pet 원칙의 직접적인 선행 사례다. Pet Mochi의 규칙 기반 상태 루프는 행동의 일관성과 비용 통제에 참고가 된다. Miru는 같은 생명성보다 상황 해석과 관계의 흐름이 강하고, desktop-pet의 표정은 주로 대화의 표현이다. Jarvis Pet이 주장할 수 있는 것은 ‘생명성 자체’가 아니라 그 생명성이 **업무 상태와 성장에도 자연스럽게 반응하는지**다. 후자는 아직 제품 가설이다. [N2][P2][M2][D1][J2]

|---|---|---|
| **NekoAI** | 로컬 SQLite에 최근 대화와 이름·프로젝트·언어 같은 사실; 최근 문맥을 모델에 보냄 | 제한된 패턴으로 사실 추출. 검토·정정 UI는 이번 조사에서 미확인 [N3] |
| **Miru** | 개인 기기 또는 개인 서버의 Markdown 기억(프로젝트·사람·자기·주제), 일기·약속 및 JSON 상태 | 기억 열람·내보내기 경로 확인. 화면에서 잘못 읽은 사실의 출처·정정·완전 삭제 품질은 미검증 [M2][M4] |

| **desktop-pet** | 로컬 JSONL 사실을 추출·검색해 대화에 재주입 | 명령줄 조회·추가·삭제 가능. 일반 사용자용 내보내기·전체 대화 보관은 미확인 [D3] |

**판정:** ‘로컬 저장’과 ‘AI 제공자를 바꿔도 기억이 남음’은 이미 여러 사례와 겹친다. Jarvis Pet의 **사용자 소유 기억**은 저장 장소만으로 완성되지 않는다. 사실의 출처, 수정·삭제·내보내기, 어떤 AI에 어떤 기억을 보냈는지, 오래된 사실의 만료와 충돌 처리까지 사용자에게 설명 가능해야 차이가 난다. 이 세부 요건은 경쟁 제품의 미구현 판정이 아니라 Jarvis Pet의 검증 항목이다. 로컬 파일을 쓴다고 자동 암호화되거나 클라우드 전송이 사라지는 것도 아니다. [N3][M4][P3][D3][J1][J2]

## 6. 성장 개념: 관계의 축적과 업무 위임을 분리

| 프로젝트 | 공개 자료에서 확인된 성장의 의미 | 권한·비서 능력 성장과의 차이 |
|---|---|---|
| NekoAI | 펫 선택·기분·개인화. 단계적 역할·권한 성장은 미확인 | 현재 보이는 중심은 대화 동반 [N1] |
| Miru | 기억·일기가 쌓이는 관계의 연속성. 과거의 친밀도·신뢰도 계량기는 제거 | 업무 권한 해금·확대는 주요 공개 경로에서 미확인 [M1][M2] |
| Pet Mochi | 관계 수치·기념일·기념품. 명시적 성장 단계는 로드맵 | 동의한 파일 요약은 있으나 성장에 따른 업무 범위 확대는 미확인 [P1][P2] |
| desktop-pet | 사용자 사실 축적과 이미 열린 비서 도구 | 펫 발달·관계에 따른 위임 단계는 README·설정에서 미확인 [D1][D2] |

**Jarvis Pet의 가설:** 성장 단계가 외형이나 점수만 바꾸는 대신, 사용자가 이해하는 목표와 맡길 수 있는 업무를 늘린다. 단, **능력의 준비**(기능이 제공됨), **권한 부여**(사용자가 이번 작업 또는 정해진 범위를 허락함), **성공 이력**(실제 결과 확인)은 서로 다른 상태다. 오래 사용했다는 이유만으로 파일·앱 접근을 자동 허용해서는 안 된다. 단계가 단순 기능 잠금처럼 느껴진다면 가설은 약해진다. [J1][J2][D2]

## 7. 멀티 AI·제공자 구조와 오케스트레이션

| 프로젝트 | 실제 공개 범위 | ‘여러 AI를 뒤에서 조율’과의 거리 |
|---|---|---|
| NekoAI | Anthropic·OpenAI·Gemini·NVIDIA NIM·Ollama 중 설정한 제공자 하나로 답변 [N4] | 선택·교체이지 요청별 분업 증거는 아님 |
| Miru | 화면 이해, 대화, 기억 정리의 세 역할에 각기 호환 모델 설정 [M3] | **정적 역할 분담이 이미 존재**. 동적 선택·공동 문제 해결은 미확인 |
| Pet Mochi | 교체용 연결 규약, 공개 구현은 Ollama 하나 [P4] | 확장 지점이지 다중 제공자 운영의 증거는 아님 |
| desktop-pet | OpenAI 호환 대화 백엔드 교체, 기억 추출 모델 별도 지정 가능 [D3] | 모델 교체·부분 역할 분리 가능; 동적 AI 분업은 공개 자료에서 미확인 |

따라서 Jarvis Pet의 **멀티 AI**는 연결 가능한 모델의 개수가 아니라 다음의 실행 계약으로 정의해야 한다: 요청을 분해한다 → 로컬 기능·AI·도구를 목적과 비용에 맞게 고른다 → 단계별 결과를 넘긴다 → 실패 시 멈추거나 대안을 제시한다 → 사용자는 이유·비용·결과를 확인한다. 이는 **설계 제안**이다. Miru의 역할별 모델 배치와 desktop-pet의 도구 연속 실행이 이미 이 가설의 일부를 선점했으므로, 조율을 했다는 사실만으로 독창성을 주장하기 어렵다. [M3][D2][J1]

## 8. 선제적 개입: 무엇을 보고, 언제 침묵하는가

NekoAI는 오래 코딩한 뒤 쉬라는 알림을 공식 자료에서 소개하지만 실제 조건·빈도 제한·거절 학습의 연결은 조사에서 확인되지 않았다. Miru는 화면·활동·약속을 보고 발화 의도를 판단하며 최소 간격·중복 방지·대화 중 침묵을 코드에 둔다. Pet Mochi는 사용자 복귀·새 파일·조용한 시간 같은 사건에 중요도 문턱과 대기 제한을 둔다. desktop-pet은 예약 알람과 백그라운드 작업 완료를 확실한 사건으로 알리지만 화면 맥락에 따른 자발적 개입은 미확인이다. [N5][M4][P5][D4]

**종합 판단:** ‘먼저 말 거는 펫’도 단독 차별점이 아니다. Jarvis Pet이 시험할 기준은 도움이 된 개입뿐 아니라 **침묵을 지킨 비율**, 잘못 짚은 맥락, 끄기·조용한 시간·빈도 설정, 모델 호출 비용이다. 화면 접근 없이도 가치가 유지되는지도 확인해야 한다. 이 평가는 네 제품의 실제 개입 품질을 서로 측정한 결과가 아니라 비교 자료에서 도출한 제품 가설이다. [M4][P5][J1]

## 9. 도구·에이전트·실제 업무 수행

**도구**는 알람 예약·파일 읽기처럼 호출 가능한 한 기능이다. **에이전트**는 목표를 해석해 도구를 선택하고 결과에 따라 다음 단계를 정하는 실행 흐름이다. **권한**은 그중 사용자가 허락한 범위다. [D2][J2]

| Miru | 기억 검색, 최근 화면 보기, 약속 추가·완료 [M5] | 특정 내부 작업은 수행. 폭넓은 PC 작업이나 연결 파일의 실제 도구 등록은 미확인 |

desktop-pet 때문에 **‘일하는 펫’ 자체는 차별점이 아니다.** 반대로 Miru를 도구가 전혀 없는 제품으로, Pet Mochi를 파일을 전혀 못 읽는 제품으로 분류해서도 안 된다. Jarvis Pet의 가능한 차이는 **펫의 성장 서사와 작업별 위임·철회·결과 확인을 함께 설계하는 방식**이다. 도구가 성공했다고 모델이 말하는 것보다 실제 상태와 도구 결과를 우선해야 한다. [M5][P6][D2][J2]

## 13. 아직 비어 있거나 약한 영역 — 가설로만 취급

1. **성장과 권한의 연결:** 네 공개 자료에서 관계·기억·외형·도구는 각각 보이지만, 펫의 장기 성장과 사용자가 승인한 위임 범위·업무 능력이 한 여정으로 커지는 구조는 뚜렷이 확인되지 않았다. [N1][M1][P1][D1]
2. **권한의 설명과 회수:** Pet Mochi의 파일별 동의는 좋은 기준선이다. desktop-pet의 허용 목록과 실행 표시도 있다. 업무별 범위, 이번 실행 승인, 철회, 실패 후 복구를 한눈에 이해하는 경험은 이 조사만으로 검증되지 않았다. [P6][D2]
3. **기억의 신뢰성:** 열람·삭제·내보내기는 이미 존재한다. 출처, 충돌, 만료, 오인 저장의 정정, 제공자 전송 범위가 사용자에게 충분히 보이는지는 네 제품 모두 실사용 검증이 필요하다. [N3][M2][P3][D3]
4. **조율의 가시성과 경제성:** 역할별 모델 설정과 여러 도구 실행은 존재한다. 어떤 요청에서 왜 어떤 AI·도구를 골랐고, 비용·시간·실패·결과가 어땠는지를 한 펫의 업무 기록으로 보여주는 경험은 공개 범위에서 미확인이다. [M3][D2]
5. **동반자성과 업무 신뢰의 균형:** Pet Mochi가 보여주는 생명성과 desktop-pet의 업무 범위를 합친다고 자동으로 좋은 제품이 되지 않는다. 방해·돌봄 부담·설정 난도·권한 불안을 한 사용자가 감당할지는 별도로 시험해야 한다. [P1][D2]

위 다섯 항목은 **시장 공백 확정**이 아니라 네 제품의 조사 범위에서 얻은 후속 검증 질문이다.

## 14. Jarvis Pet 차별화 가설 판정

### 가설 A: ‘펫의 성장 = Agency·권한·비서 능력의 성장’

**판정: 네 제품 대비 탐색 가치가 높지만 사용자 가치 미검증.** NekoAI·Pet Mochi는 펫성과 관계를, Miru는 기억에 기반한 관계를, desktop-pet은 이미 유능한 업무 도구를 강하게 보여준다. 공개 범위에서는 **작은 펫이 신뢰를 쌓고, 사용자가 허락하는 일의 범위를 명확히 늘리고, 그 결과로 더 유능해지는 과정**이 이 네 제품의 중심 경험으로 확인되지 않는다. [N1][M1][P1][D1]

이를 검증할 최소 흐름은 `AI 없이 펫이 살아 있음 → 사용자가 요청한 알림을 정확히 수행 → 저장된 기억을 사용자가 확인·정정 → 다음 업무를 제안하되 실행 전 범위를 승인 → 성공·실패와 철회 가능성을 기록`이다. 이는 **제안**이며 MVP 범위를 자동으로 늘리는 결정이 아니다. PRD의 첫 버전 후보인 기본 행동·대화·알림과 결정 기록의 ‘작게 구현’ 원칙을 유지하면서 단계별 사용자 반응을 볼 수 있다. [J1][J2]

### 가설 B: ‘펫이 여러 AI와 도구를 뒤에서 오케스트레이션’

**판정: 표현 그대로는 약함; 실행 품질까지 좁히면 검증 가치가 있음.** Miru의 역할별 모델 배치와 desktop-pet의 도구 연쇄 실행 때문에 ‘여러 AI/도구를 쓴다’는 조합은 이미 일부 존재한다. Jarvis Pet은 한 작업을 **더 빠르고 정확하며 통제 가능하게 끝내는지**, 하나의 펫이 정체성과 기억을 유지한 채 **선택 이유·비용·실패를 설명하는지**를 증명해야 한다. 자동 전환 자체가 사용자에게 보이지 않는 복잡성과 비용만 늘린다면 이 가설은 기각하거나 축소해야 한다. [M3][D2][J1][J2]

### 약한 부분과 반증 조건

- **사용자 수요 미확인:** 펫 동반자 사용자가 권한 확대를 원하는지, 비서 사용자가 성장 과정을 원하는지 조사 자료가 없다.
- **성장의 역효과:** 초기의 제한이 귀여운 성장보다 인위적인 기능 잠금이나 번거로운 승인 절차로 느껴질 수 있다.
- **권한과 신뢰의 불일치:** 오래 함께했다는 사실은 파일·앱을 안전하게 다룰 능력의 증거가 아니다. 실제 허용은 명시적이고 철회 가능해야 한다.
- **다중 모델의 비용 대비 효용:** 한 모델과 소수 로컬 도구로 같은 일을 더 간단히 끝낼 수 있다면 복수 모델 조율은 차별화가 아니라 부담이다.
- **완료 검증:** 모델의 성공 선언과 실제 변경이 다를 수 있다. 업무 결과·부분 실패·되돌리기를 확인할 수 없다면 ‘유능해지는 펫’의 신뢰가 약해진다. [D2]
- **조사 범위의 한계:** 공개 자료에서 안 보인 기능이 실제 배포에 있을 수 있고, 네 프로젝트 외 경쟁 제품은 이번 문서에 포함되지 않는다.

## 15. Jarvis Pet이 참고할 요소와 피할 요소

| 참고할 요소 | 이유 | 피할 요소 또는 다른 설계 방향 |
|---|---|---|
| NekoAI의 즉시 보이는 펫·짧은 말풍선 [N1][N2] | AI 설정 전 첫 경험을 채움 | 제한적 사실 추출을 깊은 기억처럼 표현하거나 제공자 수를 차별점으로 주장하지 않기 |
| Miru의 읽을 수 있는 기억과 침묵 규칙 [M2][M4] | 관계의 연속성과 방해 제어를 체감하게 함 | 화면 상시 접근·감정 추정을 기본 전제로 두지 않고 사용자가 신호·전송을 선택하게 하기 |
| Pet Mochi의 로컬 상태 루프, 파일별 동의, 드문 AI 호출 [P2][P5][P6] | 생명성·비용·권한의 경계를 명확히 함 | 돌봄 수치와 기념품만을 성장의 전부로 두거나 조용한 기능을 과도한 알림으로 바꾸지 않기 |
| desktop-pet의 직접 명령, 알람 수명주기, 도구·작업 상태 표시 [D2][D4] | 실제 실행과 실패를 관찰 가능하게 함 | 넓은 파일·명령·클립보드 권한을 일괄 기본 허용하는 방식을 그대로 따르지 않기 |

마지막 열은 경쟁 제품의 결함을 확정한 판정이 아니라 Jarvis Pet을 위한 **설계 권고**다. 권한 확대는 캐릭터의 나이·호감도와 자동 결합하지 말고 `사용 가능한 능력 / 사용자가 허락한 범위 / 이번 실행 승인 / 실제 결과`를 구분해야 한다. [P6][D2][J2]

## 16. 다음 단계: Codex 코드 분석 우선순위

아래 순위는 **차별화 가설의 불확실성을 줄이는 가치**를 기준으로 정했다. 심층 분석에서 이미 읽은 부분을 반복하기보다 미확인된 실행 경로를 확인한다. 공개 저장소의 특정 시점과 현재 배포본이 다를 수 있으므로 분석 시작 시 버전·커밋을 고정한다.

| 순위 | 대상과 확인할 경로 | 이 순서인 이유 | 판정에 미치는 영향 |
|---|---|---|---|
| **1** | **desktop-pet:** `tools.allow`가 자연어·직접 명령·백그라운드 작업에 일관되게 적용되는지; 파일 쓰기·셸·클립보드의 실행 직전 승인, 결과 확인·취소·로그 | 이미 가장 넓은 PC 업무를 하는 직접 경쟁 기준선인데 현재 심층 분석은 README·설정 중심 | ‘업무 수행’과 ‘권한 성장’의 실제 남은 공간, Jarvis Pet의 안전한 위임 경계가 달라짐 [D2][D5] |
| **2** | **Miru:** 화면 센서 → 주의 판단 → 발화·약속 도구 → 기억 기록의 실제 데이터 흐름; 역할별 모델 설정의 호출 경로, `mcp_proxy.py`의 실제 등록 여부 | 관계·선제성·정적 AI 분업이 가장 앞선 사례라 오케스트레이션 가설의 기준을 높임 | 맥락 기반 개입과 역할 분담의 실제 범위, 개인정보·호출 비용을 판정 [M3][M4][M5] |
| **3** | **Pet Mochi:** 로컬 상태 저장·재시작, 사건 문턱에서 실제 AI 호출까지, 파일별 동의·경로 제한, 두 번째 공급자 추가 지점 | AI 없는 생명성과 좁은 권한의 구현 기준을 제공 | 초기 펫 루프와 안전한 작은 도구의 설계 기준을 구체화 [P2][P4][P5][P6] |
| **4** | **NekoAI:** 펫별 성격 프롬프트의 실제 적용, 90분 알림의 트리거·중복 제어, 사실 정정·제공자 실패 복구 | 기본 펫+대화+로컬 기억의 넓은 중복을 품질 수준에서 확인 | ‘기본 기능을 구현했다’ 이상의 첫 경험·기억 신뢰성 기준을 정함 [N3][N4][N5] |

코드 분석 뒤에도 네 앱을 **같은 사용자 시나리오로 설치·관찰**해야 한다. 우선 시나리오는 (1) 모델 연결 없이 첫 10분, (2) 잘못된 기억의 확인·수정·삭제, (3) 먼저 말 거는 빈도와 끄기, (4) 알람의 예약·재시작·취소, (5) 파일 작업의 승인·실행·실패·철회, (6) 제공자 변경 후 연속성이다. 이는 향후 검증 계획이며 이 문서에서 실행한 시험은 아니다.
