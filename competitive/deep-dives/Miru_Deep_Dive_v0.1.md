# Miru 제품 심층 분석 v0.1

- **조사일:** 2026-09-25
- **분석 대상:** [kiyotakali/Miru](https://github.com/kiyotakali/Miru) — 같은 이름의 다른 프로젝트와 구분
- **판단 기준:** 공식 사이트, 최신 공개 배포 안내, 공개 코드. 코드 확인 기준점은 2026-09-23의 커밋 [`7d57a325`](https://github.com/kiyotakali/Miru/commit/7d57a3256bc2af2d2ac289f7c73b24c68081b646)이다. 직접 설치해 사용하거나 실제 이용자를 조사하지는 않았다. 따라서 **공개 설명**, **코드에서 확인**, **제품적 추정**을 구분한다.
- **핵심 판단:** Miru는 ‘늘 곁에 있고, 보고, 기억하고, 적절할 때 먼저 말 거는’ 동반 경험에서 이미 높은 기준선을 제시한다. Jarvis Pet의 차별화는 단순한 로컬 기억이나 선제 대화가 아니라 **관계의 성숙이 사용자에게 보이는 업무 위임 범위와 수행 능력의 성숙으로 이어지는지**에서 검증해야 한다.

## 1) 제품 한 줄 정의

**Miru는 사용자가 허락한 화면 맥락과 대화를 개인 기기 또는 개인 서버에서 기억으로 정리하고, 데스크톱의 Live2D 캐릭터가 상황에 맞춰 먼저 다가오는 오픈소스 AI 동반자다.** 제작자는 ‘필요할 때 여는 챗봇’보다 일상에 함께 있는 캐릭터로 포지셔닝한다. [공식 사이트][S1] [README][S2]

## 2) 핵심 사용자

**제품적 추정:** 긴 작업을 하며 어제의 맥락을 오늘도 이어받고 싶고, 화면 속 캐릭터의 지속적 존재감에 가치를 느끼는 개인 사용자다. 공식 사이트의 하루 시나리오는 연구·코딩·휴식·대인 약속을 오가는 사람을 예로 든다. 로컬 또는 개인 서버 운영과 모델 API 키 설정을 감수하는 사용자에게 특히 맞을 가능성이 크다. 이는 실제 고객 분포를 뜻하지 않는다. [공식 사이트][S1] [배포 안내][S3]

## 3) 핵심 UX

경험의 흐름은 **함께 있음 → 관찰 → 의미 있는 사실 축적 → 적절한 순간에 개입 → 밤에 기억 정리 → 다음 날 이어받기**다. 캐릭터 자체가 진입점이고, 채팅창은 관계를 이어가는 한 방식이다. 사이트는 집중할 때 조용히 있고, 막혔을 때 대화하며, 약속을 기억하고, 자정에 일기·기억 카드로 정리하는 하루를 묘사한다. 이 예시는 제품이 의도한 경험을 보여주는 **홍보 시나리오**이며 모든 상황의 정확도를 입증하지 않는다. [공식 사이트][S1]

데스크톱 캐릭터의 시각적 존재감, 상황에 맞춘 발화, 사용자가 열어 검토할 수 있는 기억이 하나의 성격으로 묶이는 점이 중요하다. 여러 기기에서 같은 기억을 이어 쓰는 경로도 제시하지만, 직접 설치 품질은 이 조사에서 확인하지 않았다. [README][S2] [배포 안내][S3]

## 4) AI 없이 가능한 기능

**코드·구조상 확인:** 캐릭터 표시를 위한 데스크톱 셸, 설정 화면, 저장된 파일 열람 같은 앱의 기본 부분은 모델 호출과 구분된다. 화면 촬영의 변경 감지 역시 기기에서 수행한다. 다만 Miru의 핵심 가치인 화면 **이해**, 자연스러운 **대화**, 기억 **작성·정리**, 개입 **판단**은 각각 모델 호출에 의존한다. 공개 자료만으로 네트워크나 모델 API가 끊겼을 때 애니메이션·오프라인 상호작용이 어느 수준까지 유지되는지는 확정할 수 없다. [README][S2] [화면 센서 코드][S4] [모델 설정 코드][S5]

**Jarvis Pet 관점:** ‘AI가 없어도 살아 있는 펫’은 Miru와 다른 출발점이 될 수 있으나, Miru의 실제 장애·오프라인 동작을 시험하기 전까지 우월성으로 단정하지 않는다.

## 5) 감정/행동 시스템

**코드에서 확인:** `AttentionEngine`은 화면·대화·활동·약속 신호를 모아 사용자의 상태, Miru 자신의 감정, 말 걸 의도를 평가한다. 감정 기록은 현재 상태와 이력으로 저장된다. 동일한 감정 표현이 계속 기록되지 않도록 합치는 로직도 있다. 캐릭터 성격은 `soul.md`와 행동 지침을 통해 대화에 반영된다. 이는 정해진 표정 몇 개만 바꾸는 구조보다 ‘상황을 해석하는 인격’에 가깝게 설계되어 있다. [주의 시스템 코드][S6] [감정 코드][S7] [행동 지침][S8]

**제품적 해석:** 캐릭터가 조용히 기다리는 것까지 행동으로 해석하게 한다. 다만 감정은 모델과 프로그램이 만든 **상태 표현**이다. 실제 감정이나 사용자 감정 추론의 정확성을 입증하는 근거로 읽어서는 안 된다.

## 6) 기억 시스템

**공개 설명·코드에서 확인:** 장기 기억은 프로젝트·사람·사용자 자신·주제의 네 영역을 중심으로 Markdown 문서에 저장된다. 일기와 약속 목록이 따로 있고, 색인 파일을 통해 필요한 기억을 찾는다. 대화 역할은 기존 기억을 읽고, 백그라운드 정리 과정이 새 기억을 쓰도록 분리되어 있다. 화면에서 읽은 약속도 기록 후보가 될 수 있다. 앱에서 기억을 점검하고 내보내는 경험을 공식 사이트가 강조하며, 공개 코드에는 사용자 데이터의 JSON 묶음 내보내기 경로도 있다. [README][S2] [기억 코드][S9] [내보내기 코드][S10]

**제품적 해석:** ‘나를 기억한다’는 막연한 약속을 열어 볼 수 있는 기록으로 바꾼다. 반면 화면에서 잘못 읽은 사실이 기억으로 굳어질 수 있으므로, 출처·수정·삭제 경험과 실제 정확도는 별도 검증이 필요하다.

## 7) 성장 개념

**확인된 범위:** 기억과 일기가 쌓이며 관계의 연속성은 깊어진다. 그러나 공개 코드의 과거 친밀도·신뢰도 계량기는 2026-05-09 제거되었고, 현재는 처음 만난 날짜만 유지한다. 공개 자료와 확인한 주요 코드에서 펫의 단계별 진화, 능력 획득, 사용자 권한 확대가 제품 구조로 제시되지는 않는다. [감정 코드][S7] [README][S2]

**제품적 추정:** Miru의 성장은 ‘함께 겪은 시간이 기억에 남아 점점 더 나를 아는 느낌’에 가깝다. ‘일을 더 맡길 수 있게 되는 성장’과는 구별된다. 숨은 실험 기능이나 향후 계획의 부재까지 주장하는 것은 아니다.

## 8) AI Provider 구조

**코드에서 확인:** 화면 이해용 Vision, 대화용 Chat, 기억 정리용 Memory의 세 모델 역할을 별도로 설정한다. 각 역할은 OpenAI 호환 API 주소·모델·키를 받아 다른 제공자를 섞을 수 있다. 이는 여러 모델을 **작업별로 고정 배치**할 수 있다는 뜻이다. 한 사용자 요청을 놓고 모델들을 동적으로 비교·선택하거나 여러 AI를 협업시키는 범용 오케스트레이션이 확인됐다는 뜻은 아니다. [README][S2] [모델 설정 코드][S5]

**제품적 의미:** 사용자가 비용과 품질을 역할별로 조절할 수 있지만, 처음에 세 설정을 채워야 하는 부담이 있다. 개인 서버 모드의 설정은 서버 측 전역 구성이라는 코드 설명도 있어, 여러 사용자의 개별 모델 선택 경험과는 구분해야 한다. [모델 설정 코드][S5]

## 9) 선제적 개입

**확인:** 화면·대화·활동 신호를 받은 주의 시스템이 ‘말할지 조용히 있을지’를 판단하고, 발화 의도를 대화 에이전트가 자연스러운 문장으로 만든다. 코드에는 최소 간격, 중복 방지, 활발한 채팅 중 침묵 시간 등 제한도 있다. 그러므로 ‘타이머가 말을 시킨다’는 단순 구조는 아니지만, 백그라운드 점검 주기와 제한값은 존재한다. [주의 시스템 코드][S6] [공식 사이트][S1]

**제품적 해석:** 먼저 말 거는 기능보다 **말하지 않을 이유를 잘 판단하는 것**이 UX의 핵심이다. 화면 접근을 끄면 맥락의 질이 어떻게 바뀌는지, 잘못된 감정 추정으로 개입하는 비율이 어느 정도인지는 공개 자료로 확인되지 않는다.

## 10) Tool/Agent 기능

**코드에서 확인:** 대화 에이전트는 보관 기억 검색, 최근 화면 보기, 약속 추가·완료의 도구를 호출할 수 있다. 화면 이해 과정이 약속을 포착해 기록하는 경로도 있다. 따라서 Miru를 ‘도구가 전혀 없는 챗봇’으로 분류하면 부정확하다. [도구 목록 코드][S11] [행동 지침][S8] [대화 처리 코드][S12]

**한계:** 현재 자동 등록되는 도구 목록에서는 파일 편집, 임의 명령 실행, 다른 앱 조작, 일반 웹 작업 같은 폭넓은 PC 업무 대행을 확인하지 못했다. `mcp_proxy.py`라는 연결용 파일은 있지만, 현재 도구 등록 코드가 이를 제외하므로 **외부 도구 생태계가 사용자 기능으로 활성화됐다고 볼 근거는 없다.** 여기서 MCP는 외부 도구를 연결하는 규격을 뜻한다. 이 결론은 조사한 공개 코드 기준이며 실제 배포본의 모든 동작을 시험한 결론은 아니다. [도구 등록 코드][S11] [연결용 코드][S13]

## 11) 데이터 저장 방식

**공개 설명·코드에서 확인:** 로컬 단일 기기 또는 사용자의 개인 서버가 앱 데이터의 중심이다. 기억은 Markdown, 감정·주의 기록과 여러 설정·대화 데이터는 JSON 파일로 관리한다. 화면 이미지는 분석 뒤 계속 저장하지 않는다고 설명하며, 촬영 시각과 해석 결과는 기록될 수 있다. 화면 분석이 외부 모델 제공자에게 전달되므로 ‘데이터가 절대 기기 밖으로 나가지 않는다’고 표현하면 안 된다. 개인 서버 사용 시 기기와 서버 사이에도 데이터가 이동한다. [README][S2] [공식 사이트][S1] [저장 코드][S14] [화면 센서 코드][S4]

**주의할 차이:** ‘자기 데이터의 소유권’은 강한 제품 가치이나, 데이터 노출 범위는 선택한 모델 제공자, 서버 운영, 화면 촬영 설정에 달려 있다. 민감한 화면을 제외하는 기능이나 삭제 보장의 실제 효과는 사용 시험·코드 추적이 필요하다.

## 12) 비용/무료 사용 구조

**확인:** 앱 코드는 Apache 2.0으로 공개되고 소프트웨어 자체는 무료다. 사용자는 호환 모델 API 키를 준비하고, 모델 호출 비용을 부담한다. 개인 서버 동기화를 쓰면 서버 운영 비용도 생길 수 있다. 제작자는 추천 구성이 하루 2위안 미만이라고 소개하지만, 이는 **공식 추정치**다. 화면 확인 빈도, 모델 가격·사용량, 환율, 서버 비용을 포함한 보편적 총비용은 아니다. Live2D 구성 요소와 샘플 모델은 별도 이용 조건이 있다. [README][S2] [공식 사이트][S1] [배포 안내][S3]

**도입 장벽:** 세 모델 역할의 주소·키 설정, 개인 서버 방식 선택, 화면 권한 허용 여부가 초기 경험을 복잡하게 만들 수 있다. 최신 배포 안내상 macOS·Windows 설치 파일은 공식 서명이 없고 Android 파일은 디버그 서명이다. [배포 안내][S3]

## 13) 강점

1. **뚜렷한 관계 경험:** ‘기억한다’는 가치가 화면 맥락, 먼저 말 걸기, 밤의 정리, 다음 날 이어받기로 연결된다. [공식 사이트][S1]
2. **검증 가능한 기억:** 사용자가 기억을 읽고 내보낼 수 있어 캐릭터의 친밀감과 정보 통제감을 동시에 준다. [README][S2]
3. **침묵까지 설계한 선제성:** 개입 판단과 중복·빈도 제한을 분리해 성가신 알림이 되지 않으려 한다. [주의 시스템 코드][S6]
4. **기기·모델 선택권:** 개인 기기/서버, 세 모델 역할을 조합하는 구조가 특정 중앙 서비스 종속을 줄인다. [README][S2]

## 14) 약점/한계

1. **제품 설명의 최신성 차이:** 공식 사이트는 화면 확인 기본값을 60초, Android를 개인 서버가 필요한 방식으로 설명한다. 최신 README·코드는 기본 30초이고, 2026-08-30 배포 안내는 Android 로컬 단독 모드도 적는다. 여기서는 최신 코드·배포 안내를 우선하되, 설치 환경별 실제 동작은 **미검증**으로 둔다. [공식 사이트][S1] [README][S2] [배포 안내][S3] [설정 코드][S15]
2. **프라이버시와 비용의 긴장:** 화면 맥락이 핵심일수록 모델 전송과 호출량이 늘 수 있다. 실제 비용·보호 수준은 설정과 사용 행태에 따른다. [README][S2]
3. **업무 실행의 깊이:** 공개 도구는 기억·화면·약속 중심이다. 복수 앱을 넘나들며 사용자의 일을 끝내는 비서 능력은 확인되지 않는다. [도구 목록 코드][S11]
4. **정확도 검증의 빈자리:** 홍보 시나리오만으로 약속 추출, 감정 추정, 적절한 개입의 성공률을 판단할 수 없다. 이 항목은 성능 열등이라는 판정이 아니라 **공개 근거의 한계**다.

## 15) Jarvis Pet과 겹치는 부분

데스크톱 펫, 캐릭터의 감정 표현, 장기 기억, 사용자 상황 이해, 먼저 말 걸기, 개인 데이터 보관, AI 제공자 교체 가능성에서 겹친다. 따라서 이들 **개별 기능**을 Jarvis Pet만의 독창성으로 주장하기는 어렵다. Jarvis Pet의 현재 구상은 [PRD](../../docs/Jarvis_Pet_PRD.md)와 [결정 기록](../../docs/Jarvis_Pet_Decision_Log.md)을 기준으로 읽었다. [Miru README][S2]

## 16) Jarvis Pet이 참고할 부분

1. **기억의 증거를 보여주기:** 펫이 ‘알고 있다’고 말하는 내용마다 출처·수정 경로를 보여주면 신뢰를 높일 수 있다. Miru의 열어 볼 수 있는 문서가 좋은 기준선이다.
2. **개입의 품질을 침묵까지 포함해 평가하기:** 도움된 선제 발화뿐 아니라 불필요하게 말을 걸지 않은 순간도 제품 설계의 성과로 봐야 한다.
3. **역할별 모델 비용 제어:** 화면 이해, 대화, 기억 정리의 비용·품질 요구가 다름을 Miru의 세 역할 구성이 잘 드러낸다. Jarvis Pet은 장기 오케스트레이션을 목표로 하더라도 초기에는 작은 역할 분리로 학습할 수 있다.
4. **동반자 경험의 시간축:** 하루의 조각이 밤에 정리되고 다음 날 다시 등장하는 흐름이 기억의 가치를 체감하게 한다. [공식 사이트][S1] [README][S2]

## 17) Jarvis Pet이 피하거나 다르게 가져갈 부분

1. **화면 상시 접근을 기본 가치로 전제하지 않기:** 사용자가 무엇을 보여줄지 이해하고 선택하게 하며, 화면 접근이 꺼져도 펫의 기본 존재감과 유용성이 남는지 설계·검증한다.
2. **감정 추정을 사실처럼 말하지 않기:** ‘피곤해 보인다’ 같은 해석은 틀릴 수 있으므로, 개입 근거와 수정 가능성을 제공하는 방향이 적절하다.
3. **설정 복잡도를 성장 경험과 혼동하지 않기:** 세 모델 키·개인 서버를 설정할 줄 아는 능력은 펫의 성장과 다르다. 초기 경험은 작은 기능부터 명확히 보여주고, 기능 확대는 사용자에게 실제 가치로 느껴져야 한다.
4. **기억 축적과 실행 권한을 자동으로 연결하지 않기:** 오래 함께했다고 파일·앱 조작 권한을 자동 부여하면 신뢰가 손상될 수 있다. 권한은 작업 단위로 설명·허용·철회 가능해야 한다. 이는 Miru의 결함 판정이 아니라 Jarvis Pet 설계 원칙에 대한 제안이다.

## 18) 현재 Jarvis Pet 차별화 가설(펫의 성장=Agency/권한/비서능력 성장, 여러 AI/Tool 오케스트레이션)에 주는 영향

**가설은 살아 있지만 기준이 높아졌다.** Miru는 ‘관계가 지속되는 AI 펫’의 중요한 구성 요소인 기억·감정·선제 개입·제공자 선택을 이미 공개적으로 제시한다. 따라서 Jarvis Pet의 차이는 ‘더 많이 기억하는 펫’보다 **사용자가 신뢰를 쌓는 동안 펫에게 맡길 수 있는 일의 종류와 책임 범위가 명확하게 넓어지는 경험**에서 찾아야 한다. [Miru README][S2] [도구 목록 코드][S11]

여기서 **Agency(자율 실행 범위)**는 사용자의 목표를 받아 필요한 도구를 고르고 여러 단계를 이어 실제 결과를 만드는 능력이다. **권한**은 그중 무엇을 사용자가 허락했는지의 경계다. **오케스트레이션**은 서로 다른 AI와 도구에 일을 나눠 맡기고 결과를 합치는 조정이다. Miru의 세 모델 역할 배치는 이 목표의 일부와 닿지만, 동적 선택·연쇄 업무 수행·권한의 단계적 확대를 입증하지는 않는다.

**검증할 제품 가설:** 사용자는 ‘펫이 성장했다’를 새 표정이나 누적 기억보다, **지금 할 수 있는 일·허락받은 일·성공적으로 끝낸 일이 자연스럽게 달라지는 것**으로 느끼는가? 반대로 단계별 제한을 단순한 잠금으로 느끼는가? Jarvis Pet의 차별성은 구현 목록이 아니라 이 사용자 경험을 시험한 뒤에만 주장할 수 있다. [Jarvis Pet PRD](../../docs/Jarvis_Pet_PRD.md) [결정 기록](../../docs/Jarvis_Pet_Decision_Log.md)

## 19) 추가 코드 분석이 필요한 지점

1. **화면 데이터 흐름:** 기기 촬영 → 개인 서버 → Vision 제공자 사이에서 이미지·해석 문장이 어디에, 얼마나 오래 남는지. 민감 화면 제외·촬영 중지·삭제의 실제 동작.
2. **기억의 품질 관리:** 화면에서 포착한 약속의 근거 연결, 중복 제거, 잘못된 사실 정정, 기억 내보내기와 완전 삭제의 범위.
3. **선제 대화의 경계:** 화면 접근을 껐을 때의 판단, 빈도 제한·중복 방지, 사용자 피드백이 다음 판단에 반영되는지.
4. **도구 실행의 안전성·확장성:** 자동 등록 도구 외에 실제 배포에서 쓰는 도구가 있는지, `mcp_proxy.py`가 연결되는 경로가 있는지, 약속 자동 완료 시 확인 절차가 있는지.
5. **플랫폼별 동작:** 최신 배포본의 Android 로컬 모드, Windows 화면 센서, 설치 서명과 권한 안내, AI 연결이 끊긴 상태의 캐릭터 동작.
6. **비용 현실성:** 화면 변화율과 주의 시스템 호출이 모델별 사용량에 미치는 영향. 공식 ‘하루 2위안 미만’ 추정이 어떤 설정·사용량을 가정하는지.
