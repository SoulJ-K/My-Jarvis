# NekoAI 심층 분석 v0.1

- 조사일: **2026-09-25**
- 대상: [nucket/NekoAI](https://github.com/nucket/NekoAI) / [공식 사이트](https://nekoai.dev/)
- 공개 배포 기준: **v0.3.8**. GitHub Releases의 최신 표시와 해당 버전의 공개 소스를 기준으로 했다. [S1][S2]
- 조사 범위: 공식 사이트, README·변경 기록, v0.3.8의 일부 핵심 코드. **실제 설치·장기 사용·전 운영체제 실측은 하지 않았다.** 따라서 공개 자료의 작동 주장과 실제 사용 품질은 구분한다.
- 판정 표기: **확인** = 공식 자료 또는 공개 코드에서 직접 확인, **해석** = 확인된 사실을 바탕으로 한 제품 관점 판단, **추정/미확인** = 사용 실험이나 추가 코드 검토가 필요한 사항.

## 핵심 판단

NekoAI는 ‘화면 위에서 살아 움직이는 복고풍 펫’에 AI 대화와 가벼운 개인화를 얹은 제품이다. 이동·잠·기분 표현이 대화 모델 없이도 돌아가므로, AI 설정 전에도 펫의 존재감을 만들 수 있다. 반면 현재 공개 코드에서 확인되는 AI 사용 흐름은 **사용자가 질문 → 선택된 한 AI가 답변 → 말풍선에 표시**하는 구조다. 여러 AI를 작업별로 조율하거나, 펫이 권한을 얻어 실제 업무를 끝내는 경험은 확인되지 않는다. 이는 Jarvis Pet의 차별화 *가능 영역*을 보여주지만, 시장 전체에서 유일하다는 뜻은 아니다. [S3][S4][S5][S6]

## 1) 제품 한 줄 정의

**확인:** 1990~2000년대 화면 펫의 움직임과 캐릭터성을 현대 데스크톱에 되살리고, 말풍선 AI 대화·로컬 기억·상황 반응을 더한 오픈소스 데스크톱 동반자. 공식 문구도 향수와 ‘현대적인 두뇌’를 결합해 소개한다. **해석:** 출발점은 비서 업무 자동화보다 *늘 보이는 귀여운 동반자*다. [S2][S3]

## 2) 핵심 사용자

**확인:** 공식 자료가 직접 겨냥하는 장면은 옛 Neko·eSheep·Shimeji를 기억하는 사람, 화면에 펫을 띄워 두고 짧게 질문하는 사람, 로컬 Ollama 또는 개인 AI 제공자를 연결하려는 사용자다. 코딩 중 휴식 알림 예시와 VS Code 맥락도 반복된다. **추정:** 초기 매력은 개발자·복고풍 데스크톱 꾸미기 사용자에게 특히 클 수 있지만, 실제 이용자 구성과 잔존율 자료는 확인하지 못했다. [S2][S3]

## 3) 핵심 UX

**확인:** 설치 후 펫이 화면을 돌아다니고 커서를 따라간다. 펫을 클릭하면 말풍선으로 대화하며, 우클릭 메뉴와 트레이에서 펫 종류·크기·AI 설정을 바꾼다. 집 모양 위젯은 펫의 출발점이자 귀환점이다. Ollama가 이미 실행 중이면 첫 설정 과정에서 감지한다. 최근 대화 일부는 말풍선을 다시 열었을 때 보인다. [S3][S7]

**해석:** 핵심 경험은 ‘일을 맡기기 위해 앱을 여는 것’보다 ‘평소 시야에 있는 존재에게 즉석에서 묻기’에 가깝다. 작은 말풍선과 응답 길이 조절은 이 사용 방식에 맞는다. v0.3.8에서 답변 길이와 말풍선 높이를 늘린 변경은 실제 대화의 잘림과 읽기 불편을 제품 팀이 다뤘다는 근거다. [S1][S7]

## 4) AI 없이 가능한 기능

**확인:** 화면 이동, 8방향 커서 추적, 여러 픽셀 펫 선택, 크기 조절, 집·트레이 조작, 시간·유휴 상태에 따른 기분과 하품·수면 같은 동작은 AI 대화 호출과 분리되어 있다. AI 키가 없을 때 대화는 설정 안내로 돌아가지만 펫 자체의 동작은 별개다. **해석:** ‘AI가 꺼져도 펫은 살아 있다’는 기본 품질을 만든다. Jarvis Pet의 초기 성장 단계와 장애 상황 설계에 직접 참고할 만하다. [S3][S5][S7]

## 5) 감정/행동 시스템

**확인:** 에너지·행복·호기심 상태를 쓴다. 공개 코드에서 에너지는 시간대와 컴퓨터 유휴 시간, 행복은 시간대, 호기심은 활성 앱의 분류에 따라 계산된다. 기분은 애니메이션과 AI 답변의 말투에 반영된다. 활성 앱은 코딩·브라우징·소통·음악·기타로 분류한다. [S3][S5][S8]

**해석:** 이 ‘감정’은 사용자의 감정을 정교하게 읽은 결과라기보다 환경 신호를 캐릭터 반응으로 번역하는 규칙 기반 상태다. 따라서 예측 가능하고 비용이 낮다. **추정:** 장기 관계에 따른 감정 누적이나 사건별 감정 기억은 현재 공개 근거에서 보이지 않는다. 실제 표현의 자연스러움은 실행 관찰이 필요하다. [S5][S8]

## 6) 기억 시스템

**확인:** 대화 기록은 로컬 SQLite 데이터베이스에 저장하고, 다음 대화 때 최근 20개 메시지를 AI 문맥에 넣는다. 말풍선 재개 시에는 최근 6개를 표시한다. 별도 `user_facts`에는 이름·프로젝트·사용 언어를 저장한다. v0.3.8의 공개 `memory.ts`는 영어·일부 스페인어 문장 패턴으로 이 세 항목을 추출하며, 사용자 발화와 AI 답변을 합쳐 검사한다. [S3][S6][S7][S9]

**해석:** 현재 ‘기억’은 짧은 대화 연속성과 제한된 사용자 사실의 재사용에 강점이 있다. 그러나 프로젝트의 상태 변화, 여러 사람·작업의 관계, 사실의 출처·유효기간·수정 이력까지 다루는 장기 기억으로 보기는 어렵다. 답변 텍스트까지 사실 추출 대상으로 삼는 점은 잘못된 사실이 저장될 가능성을 만든다. **미확인:** 기억을 사용자가 UI에서 검토·삭제·정정하는 흐름은 이번 조사에서 확인하지 못했다. [S6][S9]

## 7) 성장 개념

**확인:** 현재 공개 기능과 향후 계획에는 펫 선택·꾸미기·미니게임이 있지만, 사용 기간이나 신뢰에 따라 **같은 펫의 역할·권한·업무 능력이 단계적으로 커지는 성장 체계**는 명시되지 않는다. 꾸미기·미니게임도 로드맵 항목이다. [S3]

**해석:** NekoAI의 변주는 ‘어떤 캐릭터를 데리고 다닐지’와 ‘현재 어떤 기분인지’에 더 가깝다. Jarvis Pet이 성장 자체를 제품의 중심 경험으로 만들면 다른 축을 세울 수 있다. 다만 성장의 조건과 변화가 사용자에게 체감되지 않으면 단순 기능 잠금 해제로 보일 위험이 있다.

## 8) AI Provider 구조

**확인:** Anthropic, OpenAI, Google Gemini, NVIDIA NIM, Ollama를 선택할 수 있다. `AIProvider` 연결 규약은 메시지와 시스템 지시를 받아 답변 문자열 하나를 돌려주는 형태다. 설정값에 따라 제공자 구현체 하나를 생성한다. Ollama는 기기에서 모델을 돌리는 경로다. [S3][S4][S10]

**해석:** ‘여러 제공자 지원’은 선택·교체의 유연성이지, 한 요청에서 여러 모델을 비교·분업·전환하는 오케스트레이션의 증거가 아니다. Jarvis Pet의 여러 AI 조율 가설은 제공자 수가 아니라 **언제 왜 어느 AI를 선택했는지, 결과를 어떻게 합치는지**로 정의해야 한다. **미확인:** 제공자 전환 시 대화 품질·비용·실패 복구 경험은 실행 검증이 필요하다.

## 9) 선제적 개입

**확인:** 공식 사이트와 README는 ‘90분 코딩 후 스트레칭’ 같은 부드러운 알림을 현재 기능으로 소개한다. 활성 앱과 유휴 시간을 읽는 코드도 있다. 다만 이번 범위에서 해당 90분 조건, 알림 빈도 제한, 방해 금지 시간, 사용자의 거절 학습이 실제로 어떻게 연결되는지는 확인하지 못했다. 그러므로 **선제적 알림은 공식 주장으로 확인, 작동 품질은 미검증**으로 둔다. [S2][S3][S8]

**해석:** NekoAI가 먼저 말을 거는 순간은 ‘화면 펫’이 동반자로 보이는 중요한 계기다. 동시에 빈도가 높거나 맥락이 틀리면 방해가 된다. Jarvis Pet에는 알림의 목적·발생 근거·사용자 제어를 함께 설계하는 편이 낫다.

## 10) Tool/Agent 기능

**확인:** 현재 대화 연결 규약은 텍스트 응답을 반환한다. 공식 로드맵에서는 동작 플러그인 체계, 음성, 화면 캡처·주석 기능을 향후 계획으로 둔다. v0.3.8의 공개 자료에서 일정 등록, 파일 정리, 앱 조작 같은 사용자 업무를 AI가 도구 호출로 완수하는 흐름은 확인되지 않는다. [S3][S4][S10]

**해석:** 현재의 ‘도움’은 주로 답변·설명에 해당한다. 펫의 이동과 창 감지는 캐릭터를 위한 운영체제 기능이지, 사용자의 업무를 실행하는 비서 권한과는 다르다. **미확인:** 저장소 전체의 모든 실험 코드까지 부재를 증명한 것은 아니므로 ‘에이전트 기능이 절대 없다’고 단정하지 않는다.

## 11) 데이터 저장 방식

**확인:** 설정은 로컬 `config.toml`, 대화와 사용자 사실은 로컬 SQLite `memory.db`에 둔다. 휴대용 실행 모드에서는 실행 파일 옆 `data/`에 저장한다. 공식 자료는 중앙 백엔드가 없고, 사용자가 설정한 AI 제공자 호출만 외부로 나간다고 설명한다. 코드에서는 운영체제의 설정·데이터 경로를 선택한다. [S2][S3][S9]

**해석:** 사용자 데이터의 지속성과 제공자 교체 가능성을 만들되 운영 서버 비용을 낮춘다. 다만 **로컬 저장 = 자동 암호화**는 아니다. 설정 파일에 API 키가 저장되는 구조이므로 기기 접근자, 백업, 삭제·내보내기 UX와 운영체제별 비밀 저장소 사용 여부를 따로 평가해야 한다. ‘Ollama 사용 시 로컬 모델 처리’와 ‘클라우드 제공자를 선택하면 대화 문맥이 그 제공자에게 전송’도 구분해야 한다. [S3][S9]

## 12) 비용/무료 사용 구조

**확인:** 앱은 MIT 라이선스의 무료 오픈소스다. 운영자가 구독료를 받는 구조는 공식 자료에서 보이지 않는다. Ollama 사용 시 NekoAI 측 API 사용료는 없고, 클라우드 모델은 각 제공자의 키·무료 사용량·요금 조건에 따른다. 공식 사이트는 무료 키나 무료 사용 구간을 소개하지만, 이는 제공자 정책이 바뀔 수 있으므로 **2026-09-25 현재 이 문서에서 가격·한도를 보장하지 않는다.** [S2][S3]

**해석:** 제품 설치 장벽은 낮지만, 클라우드 대화에는 사용자의 별도 설정과 비용 판단이 남는다. 로컬 실행은 금전적 API 비용을 줄이는 대신 사용자 컴퓨터의 성능·전력·모델 설치 부담이 있다.

## 13) 강점

1. **AI 전에도 존재감이 있다.** 움직임, 집, 수면, 기분 변화로 펫의 기본 가치를 확보한다. [S3][S5]
2. **대화 진입이 빠르다.** 늘 화면에 있는 캐릭터를 클릭해 짧게 묻고 바로 말풍선으로 답을 받는다. [S2][S7]
3. **개인화의 최소 조합이 명확하다.** 최근 대화 + 소수의 저장 사실 + 현재 기분으로 ‘나를 조금 아는 펫’을 만든다. [S3][S6][S7]
4. **제공자 선택과 로컬 모델 경로가 있다.** 사용자 비용·프라이버시 선호에 맞춰 선택할 수 있다. [S3][S4]
5. **배포·설정·운영체제 문제를 다뤄 왔다.** v0.3.x의 여러 수정과 설치 파일은 데스크톱 펫에서 구현보다 실제 화면 품질이 어렵다는 점을 보여준다. [S1][S11]

## 14) 약점/한계

1. **기억의 깊이가 제한적이다.** 공개 코드의 사실 추출은 세 종류의 정규식 패턴에 의존한다. 언어·문장 형태가 달라지면 기억이 기대처럼 쌓이지 않을 수 있다. [S6]
2. **성장과 업무 권한은 현재 핵심 경험이 아니다.** 캐릭터 변화가 ‘더 유능한 비서가 됨’으로 이어지는 구조는 확인되지 않는다. [S3][S4]
3. **여러 AI는 선택지다.** 현재 연결 규약과 호출 흐름에는 작업별 모델 분업이나 결과 통합이 나타나지 않는다. [S4][S7]
4. **공식 설명과 구현을 더 맞춰 봐야 한다.** README는 펫별 `system_prompt`를 설명하지만, 확인한 v0.3.8 대화 경로는 `buildContextBlock('NekoAI', …)`를 호출하고 공통 문구를 만든다. 실제 펫별 말투가 대화에 적용되는지는 추가 확인이 필요하다. [S3][S7][S10]
5. **운영체제별 경험 차이가 있다.** 공식 변경 기록은 macOS·Linux에서 커서 추적과 렌더링 문제를 수정해 왔음을 보여준다. v0.3.8에서 모든 환경의 동일한 동작 품질을 보장하는 자료는 없다. [S11]

## 15) Jarvis Pet과 겹치는 부분

Jarvis Pet의 현재 PRD·결정 기록과 비교하면, **움직이는 데스크톱 펫, AI가 없어도 돌아가는 기본 행동, 감정 표현, 대화, 로컬 기억, AI 제공자 교체 가능성, 사용자 상황에 따른 개입**이 겹친다. 따라서 이 항목들은 단독 차별점으로 내세우기 어렵다. 특히 ‘AI가 바뀌어도 펫이 기억한다’는 구조도 NekoAI의 로컬 기억·제공자 선택과 겹친다. 이는 기능의 유사성 판단이며, 두 제품의 실제 사용 품질이 같다는 뜻은 아니다. [S3][S4][S9][J1][J2]

## 16) Jarvis Pet이 참고할 부분

- **AI 없이 성립하는 첫 5분:** 펫이 등장하고 걷고 쉬는 경험을 먼저 완성하면, AI 연결이 늦어져도 제품이 비어 보이지 않는다. [S3][J2]
- **보이는 기억의 작은 효용:** 이름·현재 프로젝트처럼 재사용 가치가 큰 사실 몇 개를 잘 기억해도 대화의 연속성이 생긴다. 다만 사용자가 확인·정정할 수 있게 개선할 여지가 있다. [S6][J2]
- **말풍선과 방해의 균형:** 짧은 답변을 기본으로 두고 길이를 조절하게 한 결정은 상주형 펫의 화면 점유와 대화 품질 사이 균형을 보여준다. [S1]
- **데스크톱 품질 우선순위:** 커서·투명 창·고해상도·Linux 세션 차이는 핵심 UX 자체를 좌우한다. 기능 수보다 운영체제별 기본 동작 검증이 먼저다. [S11]
- **사용자가 선택하는 AI 비용:** 자체 서버를 운영하지 않는 초기 제품 모델의 참고 사례다. 단, 키 보관과 제공자 정책은 별도 설계가 필요하다. [S2][S9][J2]

## 17) Jarvis Pet이 피하거나 다르게 가져갈 부분

- **‘기억한다’의 범위를 넓게 광고하지 않기:** 저장되는 정보 종류와 기억의 신뢰도, 정정 방법을 사용자에게 분명히 보여준다. NekoAI의 패턴 추출은 빠른 시작에는 좋지만 깊은 사용자 이해와 같지 않다. [S6]
- **기분 점수를 성장으로 오인하지 않기:** 시간·유휴 상태 기반 감정과, 관계·숙련·권한의 지속적 변화는 구별해 설계한다. [S5][J2]
- **여러 제공자 수를 차별점으로 삼지 않기:** 제공자를 나열하는 것보다 업무 단계별 선택 이유와 실패 시 대체 경로를 사용자에게 보이는 경험이 중요하다. [S4][J2]
- **먼저 말을 거는 행동을 통제 가능하게 만들기:** 알림 끄기, 빈도, 조용한 시간, 발생 근거를 명시해야 상주형 펫이 방해물로 바뀌지 않는다. 이는 제품 제안이며 NekoAI가 해당 기능을 제공하지 않는다는 확정 판정은 아니다. [S2][S3]
- **‘로컬’ 표현을 세분화하기:** 파일의 로컬 저장, 로컬 모델 추론, 클라우드 AI 호출, API 키 보관은 각각 다른 약속이다. [S3][S9]

## 18) 현재 Jarvis Pet 차별화 가설에 주는 영향

현재 가설은 **‘펫의 성장 = Agency(스스로 판단해 일할 범위)·사용자 위임 권한·비서 능력의 성장’**과 **‘여러 AI·도구의 조율’**이다. NekoAI는 기본 펫의 생동감, 다중 AI *선택*, 로컬 기억까지 이미 보여 준다. 그러므로 Jarvis Pet은 ‘AI가 붙은 펫’이나 ‘여러 모델 지원’으로 차별화를 주장할 수 없다. [S3][S4][J2]

반면 v0.3.8 공개 근거에서 NekoAI는 대답 중심이고, 단계별 위임·권한 확대·업무 완료·모델 간 분업을 핵심 여정으로 제시하지 않는다. 따라서 Jarvis Pet의 가설은 **NekoAI와 비교해서는 유효한 탐색 방향**이다. 아직 경쟁 제품 3개와 실제 사용자 검증을 거치지 않았으므로 **확정된 시장 차별점은 아니다.** [S3][S4][S7][J2]

제품 경험으로 검증하려면 ‘알 → 성장 → 더 많은 책임’이라는 이야기만이 아니라, 예를 들어 **처음에는 사용자가 직접 요청한 알림만 제안 → 신뢰가 쌓인 뒤 일정 후보를 정리 → 명시적으로 허용한 범위에서 실제 등록**처럼 사용자에게 보이는 위임 단계가 필요하다. 각 단계에서 펫이 무엇을 **볼 수 있고, 제안할 수 있고, 실행할 수 있는지**를 구분해야 한다. 여러 AI 조율도 모델 이름보다 **어떤 일을 어느 AI·도구에 맡겼고 비용·시간·결과가 어땠는지**로 체감되어야 한다. 이는 Jarvis Pet에 대한 **제품 설계 제안**이며, 현재 구현 사실이 아니다. [J2]

## 19) 추가 코드 분석이 필요한 지점

1. **선제 알림 실체:** ‘90분 코딩’ 조건이 실제 어느 코드에서 발동하는지, 반복·중단·조용한 시간 설정이 있는지 추적. README의 완료 표시와 실행 경로를 대조한다. [S3][S8]
2. **펫별 성격 연결:** `pet.json`의 `system_prompt`가 대화 요청에 들어가는지, 현재 공통 `buildContextBlock`과 어떤 관계인지 확인. [S3][S7][S10]
3. **기억의 정확성과 제어:** 추출된 사실의 덮어쓰기·오인 저장, 사용자 정정·삭제 UI, 다국어 처리, 장기 대화가 커졌을 때의 검색 방식을 검토. [S6][S9]
4. **제공자 실패 처리:** 오류·속도 제한·비용 한도·모델 변경 시 맥락 유지, 로컬 Ollama 감지 후 사용자가 무엇을 확인하는지 추적. [S4][S7]
5. **개인정보 경계:** API 키 파일 권한, 클라우드 호출에 포함되는 최근 대화·사용자 사실, 백업·삭제·휴대용 모드의 동작을 확인. [S7][S9]
6. **운영체제별 맥락 품질:** 활성 앱·유휴 시간 수집이 Windows/macOS/Linux에서 어디까지 가능한지, 읽기 실패 시 감정·알림이 어떻게 바뀌는지 실측. [S8][S11]
7. **도구 실행 확장 여지:** 현재 텍스트 응답 규약에서 도구 호출, 승인, 실행 기록을 넣으려면 어떤 경계가 바뀌어야 하는지 분석. 이는 Jarvis Pet 아키텍처 비교에도 직접 유용하다. [S4]
